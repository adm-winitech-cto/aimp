## 1. 전제와 용어

**전제**

- 언어는 Python이다. 저장소의 `gitignore.txt`가 Python 템플릿이다.
- 웹 프레임워크는 FastAPI와 Pydantic이다.
- 시스템은 LLM을 호출할 때 LangChain(`langchain-openai`)을 쓴다.
    - LangChain은 `llm_client.py`의 `LlmClient` 구현 안에서만 쓴다. 다른 모듈은 LangChain을 import하지 않는다.
- 시스템은 LangGraph, LangMem, 외부 프롬프트 관리 서비스를 쓰지 않는다.
    - 시스템은 요청 한 건당 LLM을 최대 2회 호출한다: 환자 상태 판단(A1)에서 1회, 최종 선정(E)에서 1회.
    - 처리 흐름의 분기는 네 곳뿐이다.
        - 환자 상태 판단 LLM이 실패하면 시스템은 환자를 외상으로 보고, 필수 진료과·중증응급질환 조건 없이 진행한다.
        - 시스템은 4대 중증 환자에게 중증도 판정을 건너뛴다.
        - 후보가 0곳이면 시스템은 다음 레벨 조건으로 후보 필터를 다시 실행한다.
        - 최종 선정 LLM이 실패하면 시스템은 fallback으로 응답한다.
- 패키지 이름 `transfer_recommender`는 임시 이름이다.

**용어**

- 단계 코드(A0, A1, A2, B, C0, C, E, F, G): design.md '전체 처리 플로우'의 단계 이름 앞에 붙은 코드다. 이 문서는 "중증·특수 자원 판단(A0)"처럼 단계 이름과 코드를 함께 쓴다.
- L0, L1: L0은 지침의 원칙 조건, L1은 의료지도를 받아야 적용할 수 있는 완화 조건이다.
- N, M, X: N은 추천 개수(기본 3), M은 LLM 프롬프트에 넣는 후보 수(10~15), X는 우회 판정 거리 기준(km, 미정)이다.
- 환자 상태 판단: 환자 정보로 외상 여부, 필수·보조 진료과, 중증응급질환 코드를 판단하는 LLM 호출 단계(A1)다. 입력과 출력은 design.md '환자 상태 판단의 입력과 출력' 항목에 있다.
- fallback: 최종 선정 LLM 출력이 검증을 통과하지 못하거나 LLM 호출이 제한 시간을 넘기면, 시스템이 직선거리 순으로 N개를 골라 응답하는 처리다.
- ETA: 환자 위치에서 병원까지의 도착 예상 시간이다.

## 2. 구조

### 2.1 설계 방향

- **모듈은 design.md의 처리 단계 단위로 나눈다.** design.md 섹션, 코드 모듈, 테스트가 같은 단위로 대응하므로, 지침이나 설계가 바뀌면 개발팀이 고칠 모듈을 바로 찾을 수 있다.
- **인터페이스는 design.md가 구현 교체를 명시한 세 곳에만 둔다.**
    - `HospitalRepository`: 병원 조회 방법이 정해지지 않았고, 개발팀은 구현 초기에 mock 병원 DB를 쓴다.
    - `EtaProvider`: 시스템은 ETA를 직선거리로 추정하고, 개발팀은 나중에 도로 기반 계산으로 교체한다.
    - `LlmClient`: 개발팀은 평가에서 두 후보 모델을 비교하고, 테스트에서 LLM 호출 실패와 제한 시간 초과를 일부러 일으킨다. 환자 상태 판단과 최종 선정이 같은 인터페이스를 쓴다.
- **코드 수정 없이 바꿔야 하는 데이터는 `src/` 밖 `config/`에 둔다.**
    - 규칙 설정 파일: 개발팀이 119구급대 운영지침 개정에 맞춰 수정한다.

### 2.3 처리 단계와 모듈

| design.md 처리 단계 | 모듈 |

| 요청 수신, 입력 검증 | `api/routes.py`, `api/request.py` |

| 119 이송지침 규칙 엔진 (B) | `rules.py`, `config/transfer_rules.yaml` |
| 병원 데이터 조회 (C0) | `hospitals/`, `geo.py` |
| 후보 필터 (C) | `filtering.py` |

### 2.4 처리 순서

`pipeline.py`는 다음 순서로 단계를 호출한다.

```python
warnings   = []                                                    # 각 단계가 경고를 이 목록에 추가
if not req.vital_signs:                                            # 4대 중증 환자를 포함한 모든 환자
    warnings.append("활력징후 없음")
judgment   = severe_resource.judge(req)                            # A0
assessment = patient_assessment.assess(req, llm_client, warnings)  # A1, 모든 환자. LLM이 실패하면 None
category   = judgment.category or severity.judge(req, assessment)  # A2, 4대 중증이 아닐 때만
special    = severity.special_situations(req, category, assessment)  # 외상 환자만. 항목이 있으면 "직접의료지도 필요"
levels     = rules.levels_for(category)                            # B: [L0 조건, L1 조건]
hospitals  = repository.find_by_categories(categories_of(levels))  # C0: L0·L1 병원 분류를 합쳐 한 번 조회, 직선거리 포함
for level in levels:                                               # C: 후보가 0곳이면 다음 레벨
    candidates = filtering.apply(hospitals, level, judgment, assessment, warnings)
    if candidates:
        break
# L1 조건으로도 0곳이면 추천하지 않음 (직접의료지도 요청은 나중에 추가)
picked = selection.select(...)                            # E, 실패하면 fallback
etas   = eta_provider.estimate(picked)                    # F: 선정된 N개만
return Recommendation(...)                                # api/response.py가 응답 JSON으로 변환
```

### 2.5 프롬프트 관리

- **환자 상태 판단 프롬프트도 최종 선정 프롬프트와 같은 방식으로 관리한다.** 이 섹션은 최종 선정을 예로 설명한다. 환자 상태 판단에서는 다음 파일이 같은 역할을 한다.
    - 시스템 프롬프트: `classification/prompts/patient_assessment_v1.md`
    - LLM 입력 객체 생성과 메시지 조립: `patient_assessment.py`
    - 출력 스키마: `domain/patient.py`의 환자 상태 판단 결과 모델
- **개발팀은 시스템 프롬프트 파일에 고정 지시문만 적고, 요청 데이터는 `prompt.py`가 JSON으로 만든다.**
    - `selection/prompts/final_selection_v1.md`에는 요청마다 바뀌지 않는 지시만 적는다: 순위 원칙, 심폐정지 예외, 우회 사유 선택지, `unknown` 병상 처리, `ref` 작성법.
    - `prompt.py`는 환자 상태, 환자 상태 판단 결과, 적용 규칙, 후보 M개, 비고 원문을 LLM 입력 객체 하나로 모으고, 이 객체를 JSON 문자열로 바꿔 user 메시지에 넣는다. 비고가 비어 있으면 `prompt.py`는 비고 키를 넣지 않는다.
    - `prompt.py`는 `string.Template`으로 템플릿 자리표시자(`$n`, `$output_schema`)를 채운다.
        - `str.format`과 LangChain `ChatPromptTemplate`의 기본 형식은 중괄호를 자리표시자로 해석한다. 프롬프트 파일에 JSON 예시를 넣으면 치환 오류가 나므로 `prompt.py`는 이 둘을 쓰지 않는다.
    - `prompt.py`는 LangChain을 import하지 않고, OpenAI chat 형식의 메시지 목록(`[{"role": "system", "content": ...}, {"role": "user", "content": ...}]`)을 반환한다.
        - 이 형식은 vLLM `/v1/chat/completions`가 받는 형식이다. 개발팀은 감사 로그에 남긴 메시지 목록을 vLLM에 그대로 다시 보내 호출을 재현할 수 있다.
        - LangChain `ChatOpenAI`도 이 형식의 메시지 목록을 그대로 받는다.
- **프롬프트와 출력 검증은 같은 LLM 입력 객체를 쓴다.**
    - 프롬프트는 LLM에게 추천 사유의 `ref`를 LLM 입력 객체 안의 경로(예: `candidates.<병원ID>.er_beds`)로 쓰게 한다.
    - `validator.py`는 그 경로가 LLM 입력 객체에 있는지 확인한다.
- **출력 스키마는 `output_schema.py`의 Pydantic 모델 하나에서만 만든다.**
    - vLLM structured outputs는 생성되는 토큰을 스키마에 맞게 제한할 뿐, 스키마를 모델에게 보여 주지 않는다. 그래서 `prompt.py`는 `model_json_schema()`로 만든 스키마를 프롬프트에도 넣는다.
    - `llm_client.py`는 같은 Pydantic 모델을 `with_structured_output()`에 넘긴다.
- **버전은 파일 이름으로 구분한다.**
    - 개발팀은 프롬프트를 고칠 때 기존 파일을 덮어쓰지 않고 `final_selection_v2.md`처럼 새 파일을 만든다. `settings.py`가 사용할 버전을 정한다.
        - 예외: 2026-10-22 중증외상 기준 항목을 추가할 때 개발팀은 `patient_assessment_v1.md`를 바로 고쳤다. v1은 아직 평가셋으로 평가하지 않은 프롬프트라서, 평가 결과를 비교할 이전 버전이 없었기 때문이다. 이 예외는 이번 한 번만 적용한다.
    - 개발팀은 프롬프트를 바꾸면 평가셋으로 지침 위반 건수, 스키마 검증 실패율, 비고 반영 정확도를 확인한 뒤 배포한다. 환자 상태 판단 프롬프트를 바꾸면 환자 상태 판단 정확도와 스키마 검증 실패율을 확인한다.

### 2.6 이 구조에 넣지 않은 것

design.md '나중에 추가할 항목'은 지금 모듈을 만들지 않는다. 각 항목을 추가할 때 들어갈 위치는 다음과 같다.

- 직접의료지도 요청(L2): `pipeline.py`의 레벨 진행 루프 바로 뒤
- 감사 로그: `pipeline.py`의 마지막 단계. 프롬프트 버전, LLM 입력 객체, LLM 원문 출력을 함께 저장한다.
- 사례 집계: 새 `cases/` 모듈. 집계 결과를 `selection/prompt.py`의 LLM 입력 객체에 추가한다.
- 지역에 따라 달라지는 지침: `rules.py`와 `config/transfer_rules.yaml`

결과 반환 및 적재(G단계)의 `transport_case` 적재도 넣지 않았다. 이유는 '결정이 필요한 사항'의 '`transport_case` 적재' 항목에 있다.

#### 요청 스키마와 검증

- 산출물: `api/request.py`, `api/routes.py`, `main.py`의 검증 오류 처리기, `tests/test_request.py`, `tests/test_routes.py`
- 작업
    - `request.py`는 interface.md '병원 추천 요청'의 필드 표를 Pydantic 모델로 정의한다.
    - 필수 필드의 키가 없거나 `null`을 허용하지 않는 필드의 값이 `null`이면, 시스템은 400을 반환한다.
        - FastAPI는 요청 검증 오류에 기본으로 422를 반환한다. `main.py`는 검증 오류 처리기를 등록해 400을 반환한다.
        - 오류 응답에는 필드 위치(`loc`), 메시지(`msg`), 오류 종류(`type`)만 넣는다. Pydantic 기본 오류의 `input` 항목은 환자 정보가 담긴 요청 본문을 그대로 되돌려 주므로 뺀다.
        - `request.py`는 타입에 `null`이 있거나 '생략 시 처리'가 `null`인 필드만 `null`을 받는다. '생략 시 처리'가 `[]`나 `1`인 optional 필드(`symptoms`, `vitalSigns`, `medicalHistory`, `medications`, `preKtas.assessmentRound`)에 `null`이 오면 시스템은 400을 반환한다.
        - `request.py`는 숫자 필드에 JSON 숫자만 받는다. 불리언, 문자열(예: `"65"`), `NaN`, `Infinity`가 오면 시스템은 400을 반환한다.
        - 명세에 없는 키가 오면 시스템은 400을 반환한다. 키 이름에 오타가 나서 값이 기본값으로 바뀌는 것을 막는다.
        - `patientInfo.age`는 interface.md 타입(number)대로 소수(예: 생후 6개월 0.5세)도 받는다.
        - `majorSevereType`은 4대 중증 4종(심정지, 중증외상, 뇌졸중, 심근경색)만 받는다. 다른 값이 오면 시스템은 400을 반환한다. 시스템이 모르는 값을 무시하면 4대 중증 환자를 일반 환자로 분류하기 때문이다.
    - optional 필드의 키가 생략되면, 시스템은 interface.md '생략 시 처리' 열의 값을 넣는다.
    - `specialPatientInfo` 키가 없으면 시스템은 400을 반환한다. 하위 필드 값이 `null`이면 시스템은 "해당 없음"으로 처리한다.
- 완료 기준: interface.md '필수 여부 규칙'의 경우마다 테스트가 있다.
    - 필수 키 누락 → 400
    - `null`을 허용하지 않는 필드에 `null` → 400
    - optional 키 생략 → 기본값
    - `specialPatientInfo` 키 누락 → 400, 하위 필드 `null` → 정상 처리
    - `majorSevereType`에 4대 중증 4종이 아닌 값 → 400
- 미결 사항: 엔드포인트 경로, 문자열 필드의 값 목록, `medications`·`pregnancyInfo`·`newbornInfo`의 객체 구조 ('미결 사항과 영향받는 일감' 참고)

        - 중증외상 기준 항목 열거형: [severe-trauma-criteria.md](severe-trauma-criteria.md)의 신체검사 소견, 손상기전, 특수상황 항목. 위험한 나이 항목은 `severity.py`가 나이로 판정하므로 뺀다.
    - 개발팀은 중증외상 기준 항목을 고르는 지시문을 `patient_assessment_v1.md`에 추가한다. 새 버전 파일을 만들지 않고 v1을 바로 고치는 것은 이번 한 번만의 예외다('프롬프트 관리' 섹션 참고).
        - 지시문: LLM은 Pre-KTAS 평가내용, 주호소, 증상, 비고에 적힌 내용에 해당하는 항목만 고른다. 적혀 있지 않은 손상기전이나 소견을 추측해 고르지 않는다.
    - `llm_client.py`는 `LlmClient` 인터페이스를 정의한다. `LlmClient`는 OpenAI chat 형식의 메시지 목록(`messages`), 출력 모델(`response_format`), 제한 시간(`timeout`)을 받아, 파싱한 출력과 LLM 원문 출력을 반환하거나 실패 사유(호출 실패, 검증 실패, 제한 시간 초과, vLLM 대기 요청 초과)를 반환한다. 호출 실패는 연결 오류처럼 vLLM이 응답하지 못한 경우다. 매개변수 이름은 OpenAI SDK의 `chat.completions.parse()`와 같다. LangChain 기반 vLLM 구현은 'LlmClient와 vLLM 연동' 일감에서 만든다.
    - `LlmClient`가 실패 사유를 반환하면 `patient_assessment.py`는 결과 없음(`None`)을 반환하고 "환자 상태 판단 실패" 경고를 추가한다.
    - 개발팀은 테스트용 가짜 `LlmClient`를 `tests/`에 만든다. 가짜 클라이언트는 테스트 설정에 따라 정상 출력이나 실패 사유를 반환한다.
- 완료 기준
    - 발등 개방성 골절 예시로 만든 메시지를 기대 파일과 비교하는 테스트
    - LLM 입력 객체에 비고와 임산부 정보가 들어가는 테스트
    - 가짜 클라이언트의 실패 사유마다 결과 없음과 "환자 상태 판단 실패" 경고가 나오는 테스트
    - 출력 모델이 목록 밖의 중증외상 기준 항목을 거부하는 테스트
- 미결 사항
    - 진료과 값 목록, 환자 상태 판단 LLM 제한 시간(임시값 3초) ('미결 사항과 영향받는 일감' 참고)
    - 프롬프트의 외상 여부 기준, 진료과 선택 기준, 중증외상 기준 항목 선택 기준은 의료진 검토가 필요하다.

#### 중증도 판정 (A2)

- 산출물: `classification/severity.py`, `config/transfer_rules.yaml`의 활력징후 임계치(외상, 비외상)와 정상 의식상태 목록
- 작업
    - `pipeline.py`는 4대 중증 구분이 없는 환자에게만 중증도 판정(`severity.judge`)을 호출한다.
    - 활력징후 기록이 여러 건이면 `severity.py`는 항목마다 가장 나쁜 값으로 판정한다. 개발팀은 항목마다 어느 방향이 나쁜 값인지 설정 파일에 적는다(예: 수축기혈압은 낮을수록 나쁨, 호흡수는 낮은 쪽과 높은 쪽 모두 나쁨).
    - 개발팀은 외상 환자와 비외상 환자의 활력징후 임계치를 설정 파일에 따로 적는다.
        - 외상 환자: "다발성/중증손상" 지침 값. 수축기혈압 90mmHg 미만, 호흡수 분당 10회 미만 또는 29회 초과, 의식상태가 "명료"가 아님(AVPU의 V 이하).
        - 비외상 환자: 임시값. 수축기혈압 90mmHg 미만, 산소포화도 90% 미만, 의식상태가 "명료"가 아님.
        - 의식상태는 `vitalSigns`와 별개인 필수 필드다. 그래서 활력징후가 빈 배열이어도 `severity.py`는 의식상태로 판정한다.
    - `severity.py`는 외상 여부와 중증도로 적용 규칙(중증외상, 경증외상, 비외상 중증, 비외상 경증)을 정한다.
    - 비외상 환자: `severity.py`는 Pre-KTAS 단계(1~2단계면 중증)와 비외상 임계치로 각각 중증도를 판정하고, 두 판정이 다르면 더 중증인 쪽을 택한다.
    - 외상 환자: `severity.py`는 "다발성/중증손상" 지침 기준 중 하나라도 해당하면 중증외상으로 판정한다.
        - 생리학적 기준: 외상 임계치로 판정한다.
        - 신체검사 소견 기준, 손상기전 기준: 환자 상태 판단 결과의 중증외상 기준 항목에 이 두 분류의 항목이 하나라도 있으면 중증외상이다. 특수상황 항목은 중증외상 판정에 쓰지 않는다.
        - 수축기혈압과 호흡수 측정값이 하나도 없으면 `severity.py`는 Pre-KTAS 단계도 쓴다. 이때 1~2단계면 중증외상이다.
        - 발등 개방성 골절 예시(Pre-KTAS 2단계, 활력징후 안정, 중증외상 기준 항목 없음)는 경증외상이다.
    - 환자 상태 판단 결과가 없으면 `severity.py`는 환자를 외상으로 본다. Pre-KTAS 1~2단계이거나 외상 임계치를 넘으면 중증외상, 아니면 경증외상이다.
    - 특수상황 판정: `severity.py`는 적용 규칙이 중증외상이나 경증외상인 환자의 특수상황 항목 목록을 반환한다. 목록이 비어 있지 않으면 `pipeline.py`는 응답에 "직접의료지도 필요" 표시와 항목을 넣는다.
        - 위험한 나이(55세 이상, 10세 이하): `severity.py`가 `patientInfo.age`로 판정한다.
        - 나머지 항목: `severity.py`는 환자 상태 판단 결과의 중증외상 기준 항목 중 특수상황 항목을 가져온다. 환자 상태 판단 결과가 없으면 위험한 나이만 판정한다.
        - `pipeline.py`는 4대 중증 환자에게도 특수상황 판정을 호출한다. 4대 중증 구분이 중증외상인 환자는 중증도 판정을 건너뛰지만 특수상황 판정 대상이기 때문이다.
- 완료 기준
    - Pre-KTAS 단계는 경증인데 활력징후가 임계치를 넘으면 중증으로 판정하는 테스트
    - 활력징후 기록 여러 건 중 가장 나쁜 값으로 판정하는 테스트
    - 발등 개방성 골절 예시를 경증외상으로 판정하고, 특수상황 항목으로 위험한 나이를 반환하는 테스트
    - Pre-KTAS 3~5단계 외상 환자도 외상 임계치를 넘으면 중증외상으로 판정하는 테스트 (호흡수 10회 미만, 29회 초과 각각)
    - 외상 환자는 산소포화도가 90% 미만이어도 다른 기준에 해당하지 않으면 경증외상으로 판정하는 테스트
    - 활력징후가 정상이어도 신체검사 소견이나 손상기전 항목이 있으면 중증외상, 특수상황 항목만 있으면 경증외상으로 판정하는 테스트
    - 환자 상태 판단 결과가 없으면 환자를 외상으로 보고 판정하는 테스트
    - 특수상황 판정: 나이 경계(10, 10.5, 54.9, 55), 비외상 적용 규칙이면 빈 목록, 4대 중증 구분이 중증외상인 환자도 판정
- 미결 사항: 비외상 환자의 활력징후 임계치 값(의료진 확인 전까지 임시값), `consciousnessLevel` 값 목록(AVPU 대응)

#### 규칙 설정 파일과 규칙 엔진 (B)

- 산출물: `config/transfer_rules.yaml`, `rules.py`, `domain/types.py`의 병원 분류 열거형
- 작업
    - 개발팀은 design.md '119 이송지침 규칙 엔진'의 분류별 규칙 표 7행을 설정 파일에 작성한다. 각 행은 적용 규칙, L0 병원 등급 조건, L1 병원 등급 조건(없으면 비움)을 가진다.
    - 개발팀은 레벨마다 병원 등급 조건을 허용하는 병원 분류(`HospitalCategory`) 목록으로 적는다. 예: "지역응급의료센터 이상" = 권역응급의료센터, 지역응급의료센터
        - 개발팀은 `domain/types.py`에 병원 분류 4종(권역응급의료센터, 지역응급의료센터, 지역응급의료기관, 권역외상센터)을 정의한다. 병원 하나가 여러 분류에 속할 수 있다(예: 권역응급의료센터이면서 권역외상센터). 전문응급의료센터는 소아, 화상처럼 특정 환자군만 맡으므로 넣지 않는다.
        - 지침 문구에 "이상"이 없는 조건(예: 경증외상의 "지역응급의료기관")은 그 등급만 허용한다.
        - 뇌졸중 선별검사 양성 규칙의 "즉시 혈전용해 치료 가능" 조건은 병원 데이터에 필드가 없다. 그래서 개발팀은 이 규칙에 등급 목록만 적는다.
    - 개발팀은 설정 파일에 버전 필드를 둔다. 응답의 적용 규칙 정보에 이 버전이 들어간다.
    - `rules.py`는 앱 시작 시 설정 파일을 읽고 형식을 검사한다(필수 키 누락, 정의되지 않은 병원 분류). 형식이 틀리면 앱이 기동되지 않는다.
    - `rules.py`는 적용 규칙을 받아 [L0 조건, L1 조건] 목록을 반환한다.
- 완료 기준
    - 분류별 규칙 표의 각 행에 대한 단위 테스트 (design.md '구현 순서' 1단계의 검증 항목)
    - 형식이 틀린 설정 파일을 읽으면 실패하는 테스트

### 3.3 병원 조회·후보 필터·전체 흐름

design.md '구현 순서' 2단계에 해당한다.

#### 병원 데이터 조회와 mock 병원 DB (C0)

- 산출물: `domain/hospital.py`, `hospitals/repository.py`, `hospitals/mock.py`, `geo.py`, `tests/fixtures/mock_hospitals.json`
- 작업
    - `repository.py`는 `HospitalRepository` 인터페이스를 정의한다. 인터페이스는 선택한 병원 분류 중 하나 이상에 속하는 병원을 시·도 구분 없이 반환한다.
        - `pipeline.py`는 적용 규칙의 L0 조건과 L1 조건에 나오는 병원 분류를 합쳐 한 번만 조회한다. 레벨 진행은 조회한 목록 안에서 한다.
    - `geo.py`는 WGS84 좌표 두 점 사이의 직선거리(km)를 계산한다.
    - `repository.py`는 조회 결과의 병원마다 환자 위치와의 직선거리를 계산해 넣는 함수를 둔다. mock 구현과 Postgres 구현이 같은 함수를 쓴다.
    - `hospital.py`는 병원의 진료과를 환자 상태 판단 결과와 같은 진료과 열거형으로 나타낸다. 그래야 후보 필터가 두 값을 비교할 수 있다.
    - 개발팀은 mock 병원 데이터를 만든다.
        - 예시 환자 위치(경도 128.5911, 위도 35.8714) 주변 병원 15곳 정도를 넣는다.
        - 후보 필터의 조건마다 그 조건으로 제거되는 병원을 1곳 이상 넣는다.
        - 다른 시·도의 권역외상센터와 병상 데이터가 오래된 병원을 넣는다.
- 완료 기준
    - 알려진 두 지점 사이의 직선거리가 허용 오차 안에 드는 테스트
    - mock 데이터에 후보 필터 조건마다 제거 대상 병원이 있는지 확인하는 테스트

#### 후보 필터 (C)

- 산출물: `filtering.py`
- 작업
    - `filtering.py`는 레벨 하나의 조건을 받아 design.md '후보 필터의 조건' 표의 조건을 적용한다.
        - 병원 등급: 규칙 엔진이 정한 레벨 조건
        - 중증응급질환 수용가능 = Y: 중증응급질환 코드가 있는 환자
        - 필수 진료과 보유, 해당 진료과의 진료불가 메시지 없음: 필수 진료과가 있는 환자
        - 특수 자원 보유: 특수 자원 목록이 비어 있지 않은 환자
        - 응급실 가용병상 > 0: 심폐정지를 제외한 모든 환자
        - 중환자실 가용병상 > 0: 중증 환자, `settings.py`의 적용 여부 설정을 따름
    - 심폐정지 환자에게 `filtering.py`는 병원 등급 조건만 적용한다.
    - 환자 상태 판단 결과가 없으면 `filtering.py`는 중증응급질환 수용가능 조건과 필수 진료과 조건을 적용하지 않는다.
    - `filtering.py`는 입력일시(`hvidate`)가 신선도 임계치보다 오래된 병상 값을 `unknown`으로 바꾼다. `filtering.py`는 병상 값이 `unknown`인 병원을 제거하지 않고 "병상 정보 오래됨" 경고를 추가한다.
- 완료 기준
    - 조건마다 mock 데이터의 제거 대상 병원이 후보에서 제거되는 테스트
    - 심폐정지 환자에게 병원 등급 조건만 적용하는 테스트
    - 환자 상태 판단 결과가 없으면 중증응급질환·필수 진료과 조건을 적용하지 않는 테스트
    - 오래된 병상 값을 `unknown`으로 바꾸고 병원을 남기는 테스트
- 미결 사항: 진료불가 메시지를 진료과에 연결하는 방법('결정이 필요한 사항' 참고)

#### ETA 계산 (F)

- 산출물: `eta.py`
- 작업
    - `eta.py`는 `EtaProvider` 인터페이스와 직선거리 기반 구현을 둔다. 직선거리 기반 구현은 직선거리를 `settings.py`의 추정 속도로 나눠 ETA를 계산한다.
    - `EtaProvider`는 ETA와 함께 계산 방식 이름을 반환한다. 응답은 이 이름으로 ETA 계산 방식을 표시한다.
- 완료 기준
    - 직선거리 기반 ETA 단위 테스트
    - 전체 흐름 테스트에서 선정된 N개 병원에만 ETA가 계산되는지 확인

#### fallback 선정

- 산출물: `selection/fallback.py`
- 작업
    - `fallback.py`는 후보를 직선거리 순으로 정렬해 N개를 고른다.
    - `fallback.py`는 병원마다 정해진 문장 틀로 근거를 만든다.
        - 문장 틀에는 규칙 ID, 직선거리, 응급실 가용병상 수가 들어간다. 예: "지역응급의료센터 이상 조건 충족, 직선거리 4.2km, 응급실 가용병상 4"
        - 병상 값이 `unknown`이면 병상 수 대신 "가용병상 확인 안 됨"을 넣는다.
    - `fallback.py`는 fallback 사유(호출 실패, 검증 실패, 제한 시간 초과, vLLM 대기 요청 초과)를 결과에 넣는다.
    - `remark` 값이 있으면 `fallback.py`는 "비고 미반영" 경고를 추가한다.
- 완료 기준: 직선거리 정렬, 문장 틀, "비고 미반영" 경고에 대한 단위 테스트
- 참고: design.md '구현 순서'는 fallback을 3단계에 두었지만, 이 문서는 2단계로 옮겼다. 2단계의 전체 흐름 검증에도 병원을 고르는 단계가 필요하기 때문이다.

#### 응답 스키마 초안

- 산출물: `domain/recommendation.py`(추천 사유 출처 열거형 포함), `api/response.py`, interface.md 'Response Body' 섹션 초안
- 작업
    - 개발팀은 design.md '나중에 추가할 항목'의 '응답 스키마'에 나열된 내용을 필드로 정한다.
        - 추천 병원 목록: 병원 ID, 병원명, 순위, 직선거리, ETA, 추천 사유 목록
        - 우회 표시와 우회 사유
        - "의료지도 필요" 표시: L1 조건으로 후보를 고른 경우
        - "직접의료지도 필요" 표시와 특수상황 항목: 외상 환자가 "다발성/중증손상" 지침의 특수상황에 해당하는 경우
        - 경고 목록
        - fallback 여부와 fallback 사유
        - ETA 계산 방식
        - 적용 규칙 정보: 적용 규칙, 레벨, 규칙 설정 파일 버전
    - 후보가 0곳이면 응답은 빈 추천 목록과 추천하지 않은 이유를 담는다.
    - 개발팀은 초안을 interface.md 'Response Body' 섹션에 적고 병원선정서비스 담당자와 합의한다.
- 완료 기준: 병원선정서비스 담당자와 필드를 합의하고 interface.md를 갱신한다.
- 미결 사항: 2단계 응답 여부('미결 사항과 영향받는 일감' 참고)

#### 처리 파이프라인과 전체 흐름

- 산출물: `pipeline.py`, `api/routes.py`와 연결
- 작업
    - `pipeline.py`는 '처리 순서' 섹션의 순서로 단계를 호출한다.
    - L0 조건으로 후보가 0곳이면, `pipeline.py`는 L1 조건으로 후보 필터를 다시 실행하고 결과에 "의료지도 필요" 표시를 넣는다.
    - L1 조건으로도 후보가 0곳이거나 적용 규칙에 L1 조건이 없으면, `pipeline.py`는 추천 없이 응답한다.
    - `pipeline.py`는 각 단계가 낸 경고를 모아 응답에 넣는다.
    - 특수상황 항목이 있으면 `pipeline.py`는 응답에 "직접의료지도 필요" 표시와 항목을 넣는다.
    - 활력징후가 빈 배열이면 `pipeline.py`는 4대 중증 여부와 관계없이 "활력징후 없음" 경고를 추가한다. 중증도 판정(A2)은 4대 중증 환자를 건너뛰므로 이 경고를 넣지 않는다.
    - 이 묶음에서는 LLM 연동이 없으므로 `pipeline.py`가 최종 선정 대신 fallback 선정을 호출한다.
    - 이 묶음의 전체 흐름 테스트는 가짜 `LlmClient`로 환자 상태 판단 결과를 준다.
- 완료 기준 (design.md '구현 순서' 2단계의 검증 항목)
    - 발등 개방성 골절 예시 요청을 보내면 200 응답이 오고, 정형외과 진료가 불가능한 병원이 추천에 없다. 적용 규칙의 기대값은 경증외상이고, 응답에 "직접의료지도 필요" 표시(위험한 나이)가 있다.
    - L0 조건으로 후보가 0곳이면 L1 조건의 후보를 "의료지도 필요" 표시와 함께 추천한다.
    - L1 조건으로도 후보가 0곳이면 추천하지 않는다.
    - 4대 중증 환자도 활력징후가 빈 배열이면 "활력징후 없음" 경고를 받는다.

### 3.4 LLM 최종 선정

design.md '구현 순서' 3단계에 해당한다.

#### 출력 스키마와 프롬프트 v1

- 산출물: `selection/output_schema.py`, `selection/prompt.py`, `selection/prompts/final_selection_v1.md`
- 작업
    - `output_schema.py`는 LLM 출력 Pydantic 모델을 정의한다.
        - 추천 병원마다: 병원 ID, 순위, 추천 사유 목록(`reasons: [{type: rule|realtime|remark, ref, text}]`)
        - 우회 사유: LLM은 1순위 병원이 우회일 때 이 필드를 채운다. `output_schema.py`는 이 필드의 값을 가용병상 여건, 진료과 적합성, 환자 희망, 거절 이력 4개로 제한한다.
    - `prompt.py`는 LLM 입력 객체를 만든다.
        - 환자 상태: 나이, 성별, 주호소, 증상, 의식상태, 활력징후, 과거력, 투여약물, Pre-KTAS 평가 결과
        - 환자 상태 판단 결과: 외상 여부, 필수·보조 진료과. 환자 상태 판단이 실패했으면 `prompt.py`는 이 키를 넣지 않는다.
        - 적용 규칙과 레벨
        - 직선거리 상위 M개 후보: 병원 ID, 병원명, 등급, 직선거리, 가용병상, 중증질환 수용가능, 진료불가 메시지
        - 비고 원문: 비고가 비어 있으면 `prompt.py`는 비고 키를 넣지 않는다.
    - 개발팀은 `final_selection_v1.md`를 작성한다. 내용은 '프롬프트 관리' 섹션의 고정 지시문 항목을 따른다.
    - `prompt.py`는 템플릿 자리표시자를 채우고 LLM 입력 객체를 JSON 문자열로 바꿔 system·user 메시지 목록을 반환한다. 방법은 '프롬프트 관리' 섹션을 따른다.
- 완료 기준
    - 발등 개방성 골절 예시로 만든 메시지를 기대 파일과 비교하는 테스트
    - 비고가 비어 있으면 LLM 입력 객체에 비고 키가 없는 테스트

#### LlmClient와 vLLM 연동

- 산출물: `llm_client.py`의 LangChain 기반 vLLM 구현, `compose.yaml`
- 작업
    - 개발팀은 `llm_client.py`에 LangChain 기반 vLLM 구현을 추가한다. `LlmClient` 인터페이스는 '환자 상태 판단' 일감에서 만든다. 환자 상태 판단과 최종 선정이 이 구현을 함께 쓴다.
        - `ChatOpenAI`에 vLLM 주소, 모델 이름, `temperature=0`, 제한 시간, `max_retries=0`을 지정한다. `max_retries`를 0으로 두지 않으면 재시도 때문에 제한 시간을 넘길 수 있다. 제한 시간은 호출하는 단계(환자 상태 판단, 최종 선정)마다 `settings.py`의 값을 쓴다.
        - `with_structured_output(출력 모델, method="json_schema", include_raw=True)`로 구조화 출력을 요청한다. `include_raw=True`는 나중에 감사 로그에 저장할 LLM 원문 출력을 보존한다. LangChain이 파싱에 실패하면(`parsing_error` 값이 있으면) 구현은 실패 사유 '검증 실패'를 반환한다.
        - `llm_client.py`는 호출 전에 vLLM `/metrics`의 `vllm:num_requests_waiting` 값을 읽는다. 값이 상한을 넘으면 `llm_client.py`는 LLM을 호출하지 않고 "대기 요청 초과"를 반환한다.
    - 개발팀은 `compose.yaml`에 앱과 vLLM 서비스를 정의한다.
- 완료 기준
    - 운영할 vLLM 버전에서 `method="json_schema"` 요청이 환자 상태 판단과 최종 선정의 출력 모델로 동작한다(출력 모델마다 예시 요청 1건으로 확인).
- 미결 사항: 후보 모델 세부 사양, vLLM 대기 요청 상한 값

#### LLM 출력 검증과 우회 판정

- 산출물: `selection/validator.py`, `selection/detour.py`
- 작업
    - `detour.py`는 1순위 병원의 직선거리가 후보 중 직선거리 최단 병원보다 X km 넘게 멀면 우회로 판정한다.
    - `validator.py`는 LLM 출력을 다음 항목으로 검증한다.
        - 병원 ID: LLM 입력 객체의 후보 목록에 있음, 중복 없음, 개수 N
        - 우회 규칙: 우회면 우회 사유가 있음, 심폐정지 환자는 우회 없음
        - 추천 사유 `ref`: LLM 입력 객체에 그 경로가 있음. `type`이 `remark`면 인용 문구가 비고 원문에 있음
    - 스키마 검사는 `validator.py`가 아니라 `LlmClient`가 한다('LlmClient와 vLLM 연동' 일감 참고). `validator.py`는 파싱된 출력만 받는다.
- 완료 기준
    - 검증 항목마다 실패 사례 테스트
    - 직선거리 차이가 X km와 같을 때와 X km를 넘을 때의 우회 판정 테스트
- 미결 사항: X 값, 거절 병원 정보를 받을 경로('미결 사항과 영향받는 일감' 참고)

#### 최종 선정 통합

- 산출물: `pipeline.py` 수정
- 작업
    - `pipeline.py`는 환자 상태 판단과 최종 선정에 LangChain 기반 vLLM 구현을 쓴다.
    - `pipeline.py`는 후보 필터 결과에서 직선거리 상위 M개를 골라 프롬프트를 만들고 `LlmClient`를 호출한다.
    - LLM 출력이 검증을 통과하면, `pipeline.py`는 `detour.py`의 판정 결과를 우회 표시로 넣어 응답한다.
    - 검증 실패, 제한 시간 초과, vLLM 대기 요청 초과 중 하나가 생기면, `pipeline.py`는 fallback 선정을 호출한다.
- 완료 기준 (design.md '구현 순서' 3단계의 검증 항목)
    - LLM 호출 실패와 제한 시간 초과를 일부러 일으키면 시스템이 fallback으로 응답한다.
    - 환자 상태 판단 LLM 호출 실패를 일부러 일으키면 시스템이 필수 진료과·중증응급질환 조건 없이 "환자 상태 판단 실패" 경고와 함께 응답한다.
    - 가짜 클라이언트의 정상 출력으로 발등 개방성 골절 예시의 전체 흐름이 통과한다.

### 3.5 모델 평가

design.md '구현 순서' 4단계에 해당한다.

#### 평가셋 구축

- 산출물: `eval/` 평가셋 생성 스크립트, 평가셋
- 작업
    - 개발팀은 과거 이송 기록에서 환자 식별 정보를 제거하고, interface.md 요청 형식으로 바꾼다. 개발팀은 실제로 환자를 수용한 병원을 정답으로 기록한다.
    - 개발팀은 사례마다 이송 시점의 병원 실시간 데이터(가용병상, 중증질환 수용가능)를 함께 저장한다. 평가를 실행할 때 mock 저장소가 이 데이터를 반환한다.
    - 평가 담당자는 비고가 있는 사례마다 기대하는 반영 결과를 라벨로 기록한다(예: 환자가 희망한 병원, "FAST 음성" 같은 부정 표현의 올바른 해석).
    - 평가 담당자는 사례마다 외상 여부, 필수 진료과, 중증응급질환 코드, 중증외상 기준 항목의 정답을 라벨로 기록한다. 리포트는 이 라벨로 환자 상태 판단 정확도를 계산한다.
- 완료 기준: 팀이 평가셋의 규모와 구성을 확정한다.
- 미결 사항: 과거 시점 병원 실시간 데이터가 남아 있는지('결정이 필요한 사항' 참고), 비고 라벨과 환자 상태 라벨을 달 담당자

#### 평가 실행과 리포트

- 산출물: `eval/` 실행 스크립트, 리포트
- 작업
    - 개발팀은 후보 모델과 프롬프트 버전의 조합마다 평가셋을 실행한다.
    - 리포트는 design.md '평가' 섹션의 지표 6개를 계산한다.
        - 실제로 환자를 수용한 병원이 추천 N개 안에 들어간 비율
        - 지침을 위반한 추천 건수: 추천 병원이 규칙 엔진의 레벨 조건을 만족하는지 다시 검사해 센다.
        - 환자 상태 판단 정확도: 평가셋의 환자 상태 라벨과 비교한다.
        - LLM 출력이 스키마 검증에 실패한 비율 (환자 상태 판단, 최종 선정 각각)
        - 비고 반영 정확도: 평가셋의 비고 라벨과 비교한다.
        - 응답 지연 시간의 95번째 백분위 값
- 완료 기준: 두 후보 모델을 비교한 리포트

### 3.6 데이터 준비

구현 순서와 별도로 진행한다.

#### Postgres HospitalRepository 구현

- 산출물: `hospitals/postgres.py`
- 작업
    - `postgres.py`는 [erd_hospital.mmd](erd_hospital.mmd)의 `tapi_*` 테이블을 조회해 `Hospital`로 바꾼다.
        - 응급의료기관 등급: 응급의료기관목록정보조회 `dutyemcls`
        - 권역외상센터 지정: 외상센터위치정보조회 `dutylvkl`
        - 진료과목: 응급의료기관목록정보조회 `qd`. `postgres.py`는 `qd` 값을 진료과 열거형으로 바꾼다.
        - 좌표: `wgs84lon`, `wgs84lat`. 두 컬럼이 문자열 타입이므로 `postgres.py`는 값을 숫자로 변환한다.
        - 가용병상과 입력일시: 응급실시간가용병상정보조회 `hvec`(응급실 일반), `hvicc`(중환자실 일반), `hv28`(소아), `hvidate`(입력일시)
        - 중증질환 수용가능: 중증질환환자수용가능정보조회 `mkioskty*`
        - 진료불가 메시지: 응급실및중증질환메시지조회 `symblkmsg`
    - 주의: 같은 컬럼명이 테이블마다 다른 뜻으로 쓰인다.
        - 중증질환환자수용가능정보조회의 `mkioskty1`은 "[재관류중재술] 심근경색"이다.
        - 응급의료기관기본정보조회의 `mkioskty1`은 "뇌출혈수술"이다.
        - design.md '판정 규칙' 표의 컬럼은 중증질환환자수용가능정보조회 기준이다.
- 완료 기준: mock 구현에 쓴 인터페이스 테스트를 Postgres 구현도 테스트 DB에서 통과한다.
- 미결 사항: 병원 데이터 조회 방법, DB에 응급의료기관 등급·권역외상센터 지정 여부·혈전용해 치료 가능 여부·진료불가 메시지 필드가 있는지

## 5. 결정이 필요한 사항

구조와 일감을 정리하면서 새로 찾은 항목이다.

- **심폐정지 환자의 특수 자원**
    - 중증·특수 자원 판단(A0)은 15세 미만이거나 임산부인 심정지 환자에게도 소아 응급 진료나 분만 자원을 붙인다.
    - design.md는 "심폐정지 환자에게 병원 등급 조건만 적용한다"고 정했다. 이대로면 후보 필터는 심정지 환자에게 특수 자원 조건을 적용하지 않는다.
    - 후보 필터가 심폐정지 환자에게도 특수 자원 조건을 적용할지 정해야 한다. 영향받는 일감은 '후보 필터 (C)'다.
- **진료불가 메시지와 진료과 연결**
    - 후보 필터는 "해당 진료과의 실시간 진료불가 메시지"가 없는지 확인해야 한다.
    - ERD의 응급실및중증질환메시지조회 테이블에는 진료과 컬럼이 없다. 중증질환구분(`symtypcod`)과 자유 텍스트 메시지(`symblkmsg`)만 있다.
    - 메시지를 진료과에 어떻게 연결할지 정해야 한다.
- **과거 시점 병원 실시간 데이터**
    - 평가셋을 만들려면 과거 이송 시점의 가용병상과 중증질환 수용가능 정보가 필요하다.
    - 이 데이터가 DB에 이력으로 남아 있는지 확인해야 한다. 남아 있지 않으면 평가 방법을 다시 정해야 한다.
- **fallback 구현 시점**
    - design.md '구현 순서'는 fallback을 3단계에 두었지만, 이 문서는 2단계로 옮겼다. 2단계의 전체 흐름 검증에 병원을 고르는 단계가 필요하기 때문이다.
- **레벨 진행 루프 위치**
    - design.md는 "규칙 엔진은 L1 조건으로 후보 필터를 다시 실행한다"고 적었다.
    - 이 문서의 구조에서는 `pipeline.py`가 레벨 진행 루프를 실행한다. 규칙 엔진은 레벨별 조건 목록만 반환하고, 후보 필터는 레벨 하나의 조건만 처리한다. 그래서 개발팀은 두 모듈을 따로 테스트할 수 있다.
- **`transport_case` 적재**
    - design.md 기준으로 결과 반환 및 적재(G단계)는 감사 로그를 거쳐 실제 이송 결과를 요청과 연결하는데, 감사 로그는 '나중에 추가할 항목'에 있다.
    - 실제 이송 결과를 읽을 테이블도 정해지지 않았다. ERD의 `tamp_trnshsp_slctn`(이송병원선정)이 후보로 보인다.
    - 이 문서는 적재를 일감에 넣지 않았다. design.md '구현 순서'에도 적재가 없다.
- **직선거리 기반 ETA의 추정 속도**
    - design.md는 ETA를 "직선거리로 추정해서 시작"한다고만 적었다. ETA를 계산하려면 추정 속도 값이 필요하다.

## 6. 결정한 사항

개발팀이 정한 항목이다. 날짜를 적지 않은 항목은 2026-10-20에 정했다. 각 결정은 이름을 적은 일감의 작업 항목에 반영했다.

- **발등 개방성 골절 예시의 기대 분류:** 경증외상으로 본다.
    - 잠정 중증외상 규칙("Pre-KTAS 1~2단계 + 외상이면 중증외상")을 그대로 적용하면 예시 환자(Pre-KTAS 2단계, 외상)는 중증외상이 된다. design.md '예시: 65세 남성, 발등 개방성 골절, Pre-KTAS 2단계' 섹션은 이 환자를 경증외상으로 설명한다.
    - 그래서 외상 환자의 중증외상 판정을 활력징후 기준으로 바꿨다. Pre-KTAS 3~5단계 외상 환자도 활력징후가 임계치를 넘으면 중증외상이다.
    - 2026-10-22: '중증외상 판정 기준' 결정에서 "다발성/중증손상" 지침 기준이 이 활력징후 기준을 대체했다. 지침 기준으로도 이 환자는 경증외상이다.
    - 반영한 일감: '중증도 판정 (A2)'
- **중증외상 판정 기준 (2026-10-22):** 시스템은 외상 환자의 중증외상 여부를 "다발성/중증손상" 지침([severe-trauma-criteria.md](severe-trauma-criteria.md))의 기준으로 판정한다.
    - 생리학적 기준은 `severity.py`가 활력징후와 의식상태로 판정한다. 지침에 없는 산소포화도는 외상 환자 기준에서 뺐다. 비외상 환자의 임계치는 바꾸지 않았다.
    - 신체검사 소견 기준과 손상기전 기준은 요청에 정형 필드가 없고, 병원선정서비스는 입력 필드를 바꾸지 않는다. 그래서 환자 상태 판단 LLM이 Pre-KTAS 평가내용, 주호소, 증상, 비고에서 해당 항목을 고르고, `severity.py`가 그 항목으로 판정한다.
        - 이 정보는 비고에만 적힐 수 있으므로 시스템은 비고를 환자 상태 판단 LLM에도 넣는다.
        - 고르지 않은 대안: 생리학적 기준만 적용하면 활력징후가 정상인 가슴 자상 환자가 경증외상이 된다. "Pre-KTAS 1~2단계 외상 환자는 중증외상"을 다시 넣으면 발등 개방성 골절 예시가 중증외상이 되어 앞의 결정과 충돌한다.
        - 받아들인 대가: 텍스트에 손상기전이나 소견이 적혀 있지 않으면 시스템은 중증외상 환자를 경증외상으로 분류할 수 있다. 입력 필드가 바뀌지 않으므로 이 한계는 계속 남는다.
    - 특수상황('의학적 질병상태 및 특수상황')에 해당하는 외상 환자에게 시스템은 추천을 그대로 반환하고 "직접의료지도 필요" 표시를 넣는다. 지침은 이 환자의 이송병원을 직접의료지도로 정하라고 규정하고, 지도의사는 추천 목록을 참고할 수 있다.
    - 수축기혈압과 호흡수 측정값이 없거나 환자 상태 판단이 실패하면, 시스템은 Pre-KTAS 1~2단계를 중증외상으로 보는 보수적 기준을 함께 쓴다.
    - 결과에 붙이던 잠정 규칙 표시는 뺐다. 기준 문서를 받기 전에만 쓰려던 표시였다.
    - 반영한 일감: '환자 상태 판단 (A1)', '중증도 판정 (A2)', '응답 스키마 초안', '처리 파이프라인과 전체 흐름', '평가셋 구축'
- **환자 상태 판단 방식:** 시스템은 Pre-KTAS 조회 테이블 대신 LLM으로 외상 여부, 필수·보조 진료과, 중증응급질환 코드를 판단한다.
    - 조회 테이블을 쓰면 병원선정서비스가 보낼 수 있는 모든 평가내용 문구가 테이블에 있어야 하고, 테이블에 없는 문구로는 판단할 수 없다.
    - 시스템은 후보 필터 전에 LLM을 따로 호출한다. 필수 진료과와 중증응급질환 코드는 지금처럼 후보 필터의 완화할 수 없는 조건으로 쓴다.
    - 환자 상태 판단이 실패하면 시스템은 환자를 외상으로 보고, 필수 진료과·중증응급질환 조건 없이 진행하고, "환자 상태 판단 실패" 경고를 추가한다. 이 처리는 먼저 정한 "평가내용 미등록 환자는 외상으로 본다"는 결정을 이어받았다.
    - 중증응급질환 코드는 중증질환환자수용가능정보조회의 `mkioskty1`~`mkioskty27`을 쓴다.
    - 처음에는 비고를 환자 상태 판단 LLM에 넣지 않기로 했다. 2026-10-22 '중증외상 판정 기준' 결정에서 넣기로 바꿨다.
    - 반영한 일감: '환자 상태 판단 (A1)', '중증도 판정 (A2)', '병원 데이터 조회와 mock 병원 DB (C0)', '후보 필터 (C)', '처리 파이프라인과 전체 흐름', '출력 스키마와 프롬프트 v1', 'LlmClient와 vLLM 연동', 'LLM 출력 검증과 우회 판정', '최종 선정 통합', '평가셋 구축', '평가 실행과 리포트', 'Postgres HospitalRepository 구현'
- **병원 분류 범위:** 병원 분류는 권역응급의료센터, 지역응급의료센터, 지역응급의료기관, 권역외상센터 4종이다. 전문응급의료센터는 넣지 않는다. 지침 문구에 "이상"이 없는 조건은 그 등급만 허용한다.
    - 반영한 일감: '규칙 설정 파일과 규칙 엔진 (B)'
- **뇌졸중 선별검사 양성 규칙의 혈전용해 조건:** 병원 데이터에 필드가 없으므로 개발팀은 설정 파일에 등급 목록만 적는다.
    - 반영한 일감: '규칙 설정 파일과 규칙 엔진 (B)'
- **`majorSevereType` 값 검증:** 4대 중증 4종이 아닌 값이 오면 시스템은 400을 반환한다.
    - 반영한 일감: '요청 스키마와 검증'
- **활력징후 임계치 임시값:** 수축기혈압 90mmHg 미만, 산소포화도 90% 미만, 의식상태가 "명료"가 아니면 중증이다. 의료진이 확인하기 전까지 쓴다.
    - 2026-10-22: 이 임시값은 비외상 환자에게만 쓴다. 외상 환자는 '중증외상 판정 기준' 결정에 따라 지침 값을 쓴다.
    - 반영한 일감: '중증도 판정 (A2)'
- **"활력징후 없음" 경고 범위:** 활력징후가 빈 배열이면 시스템은 4대 중증 여부와 관계없이 모든 환자에게 이 경고를 넣는다. 중증도 판정(A2)이 아니라 `pipeline.py`가 경고를 추가한다.
    - interface.md는 이 경고를 조건 없이 넣는다고 적었다. 최종 선정 LLM도 활력징후 없이 판단하므로, 구급대원은 4대 중증 환자의 경우에도 이 사실을 알아야 한다.
    - 반영한 일감: '중증도 판정 (A2)', '처리 파이프라인과 전체 흐름'
