## 1. 브랜치 전략

### 1.1 브랜치 타입 (3종)

브랜치 prefix는 아래 3개만 사용합니다.

- `feat`: 기능 추가
- `fix`: 버그 수정
- `chore`: 그 외 작업 (문서/테스트/리팩터링/CI/설정 포함)

`refactor`, `test`, `docs`, `perf`, `ci`는 **브랜치 타입이 아니라 커밋 타입**으로 씁니다.

### 1.2 브랜치명 규칙

```text
<type>/<module>-<short-desc>
```

- 길이: `type/` 이후 전체 60자 이내 권장
- 소문자 + 숫자 + `-` + `.`만 사용
- 1단계 평면 구조만 사용 (중첩 금지)
- 브랜치는 항상 최신 `main`에서 땁니다(§1.5)

### 1.3 모듈 목록

브랜치·커밋의 모듈은 아래 목록만 씁니다. 모듈은 [PRD_v0.1.md](../00_기획/PRD_v0.1.md) §4 '기술 스택'의 코드 구조에 있는 패키지·파일 이름을 기준으로 나눴습니다. 작업자는 바꾼 파일의 경로를 보고 모듈을 고릅니다.

| 모듈 | 범위 | PRD 기능 요구사항 |
|---|---|---|
| `api` | `api/`(라우터, 요청 스키마, 응답 스키마), `main.py` | F-01 요청 수신과 검증, F-11 결과 반환 |
| `classification` | `classification/` — 중증·특수 자원 판단, 환자 상태 판단과 그 프롬프트, 중증도 판정과 특수상황 판정 | F-02 중증·특수 자원 판단, F-03 환자 상태 판단, F-04 중증도 판정과 특수상황 판정 |
| `engines` | `engines/` — 규칙 엔진 4개, `config/transfer_rules.yaml` | F-05 119구급대 운영지침 규칙 엔진, F-13 진료 역량 규칙 엔진, F-14 ML 모델 규칙 엔진, F-15 도착시간·거리 규칙 엔진 |
| `pipeline` | `pipeline.py` — 처리 단계 호출 순서, 규칙 엔진 호출과 활성화, 레벨 진행, 실패 처리, 경고 수집 | F-07 규칙 엔진 적용과 레벨 진행 |
| `selection` | `selection/` — 최종 선정과 그 프롬프트, LLM 출력 검증, 우회 판정, 최종 선정 fallback | F-08 최종 선정, F-09 최종 선정 fallback |
| `adapters` | `ports/`, `adapters/` — 외부 시스템 인터페이스와 구현(병원정보 검색 API, Tmap ETA API, vLLM, ML 모델), `config/settings.yaml`의 `vllm_model` | F-06 병원정보 조회, F-10 ETA 계산, F-03·F-08·F-14가 쓰는 외부 호출 |
| `eval` | `eval/` — 평가셋 생성 스크립트, 평가 실행 스크립트, `eval_set/` — 평가셋 | F-12 모델 평가 |
| `shared` | `domain/` — 단계 사이에 주고받는 데이터 타입, `common/` — 설정 읽기, 로깅 설정 | — |
| `infra` | `Dockerfile`, `compose.yaml`, `requirements.txt`, `requirements-dev.txt`, vLLM 컨테이너 구성, 모델 가중치 반입 | — |
| `docs` | `docs/` 아래 문서만 바꾸는 작업 | — |

- 여러 모듈이 함께 바뀌면 **주 모듈 하나**로 정하고, PR 본문에 영향받는 모듈을 적습니다.
- 목록에 없는 모듈 이름을 지어내지 않습니다. 필요하면 이 문서를 먼저 고칩니다.
- 이 목록은 v0.1 초안입니다. 코드 구조(패키지·서비스 이름)가 정해지면 그 이름에 맞춰 고칩니다.
- 범위는 PRD §4 '기술 스택'의 코드 구조를 따르므로 아직 없는 파일도 들어 있습니다(예: `pipeline.py`). 임시 구현 `selection/static_selection.py`와 `selection/static_hospitals.py`는 `selection` 모듈입니다.
- 테스트 파일(`tests/`)만 바꾸면 그 테스트가 검사하는 코드의 모듈을 씁니다.
- 프롬프트 파일을 바꾸면 그 프롬프트를 쓰는 모듈을 씁니다. `classification/prompts/`는 `classification`, `selection/prompts/`는 `selection`입니다. `llm`이 아닙니다.
- 설정값(`config/settings.yaml`)을 바꾸면 그 값을 쓰는 모듈을 씁니다. 예: 추천 개수 N과 LLM에 넣을 병원 수 M은 `selection`, 병상 데이터 신선도 임계치는 `pipeline`, ETA 추정 속도는 `eta`, `vllm_model`은 `llm`입니다.
- 문서와 코드를 함께 바꾸면 `docs`가 아니라 코드 쪽 주 모듈을 씁니다.

### 1.4 브랜치 예시

```text
feat/adapters-hospital-search-api
fix/selection-rejected-hospital-dup
chore/infra-vllm-compose
chore/docs-prd-v0.2
```

### 1.5 작업 시작 전

작업을 시작하기 전에 반드시 `main`을 fetch하고 `origin/main`에서 브랜치를 땁니다.

```bash
git fetch origin
git switch -c <브랜치> origin/main
# 워크트리로 작업할 때
git worktree add -b <브랜치> <워크트리 경로> origin/main
```

## 2. 커밋 메시지

### 2.1 기본 형식

```text
<type>(<module>): <description>

[선택] 본문
[선택] 바닥글
```

### 2.2 커밋 타입

| 타입 | 설명 |
|---|---|
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 리팩터링 (동작 변경 없음) |
| `test` | 테스트 추가/수정 |
| `docs` | 문서 추가/수정 |
| `chore` | 빌드/설정/의존성/기타 관리 작업 |
| `perf` | 성능 개선 (추천 품질이 아니라 실행 속도·자원 사용) |
| `ci` | CI/CD 설정 변경 |

추천 품질(PRD F-12 '모델 평가'의 지표)을 개선한 변경은 `perf`가 아니라 `feat`입니다.

### 2.3 모듈 표기

- 가능하면 모듈을 씁니다 (`feat(engines): ...`).
- 공통 작업은 모듈을 생략할 수 있습니다 (`chore: ...`, `docs: ...`).
- 모듈을 쓸 때는 §1.3 목록만 씁니다.

### 2.4 설명 작성 규칙

- 50자 이내 권장
- 명령형 현재형
- 마침표 없음
- 한글/영문 혼용 최소화

### 2.5 본문

- 무엇을 왜 바꿨는지 목록으로 적습니다. 리뷰어가 diff를 열기 전에 범위를 알 수 있어야 합니다.
- 마지막 줄에 `관련 이슈: #N`을 적습니다.

### 2.6 AI 작성 커밋 트레일러

AI 도구가 작성한 커밋에는 아래 트레일러를 붙입니다.

```text
Co-Authored-By: Claude <모델명> <noreply@anthropic.com>
```

### 2.7 예시

```text
feat(adapters): 병원정보 검색 API로 병원 정보와 실시간 가용병상 조회

- HospitalRepository의 병원정보 검색 API 구현(adapters/)을 추가해 검색 API 응답을 Hospital로 변환
- 진료과목 qd는 진료과 열거형으로, 문자열 좌표 wgs84lon·wgs84lat는 숫자로 변환
- 가용병상과 입력일시(hvidate)를 함께 읽어 진료 역량 규칙 엔진이 병상 데이터 신선도를 판정할 수 있게 함

관련 이슈: #12
```

## 3. 푸시 규칙

### 3.1 main에는 직접 푸시하지 않습니다

모든 변경은 브랜치 → PR → 리뷰 → 머지로 `main`에 들어갑니다.
예외는 **빈 저장소의 초기화 커밋**(PR의 기준 브랜치를 만들기 위한 빈 커밋) 하나뿐입니다.

### 3.2 본인 계정으로 푸시합니다

- `gh auth status`로 확인한 **본인 GitHub 계정**으로 푸시합니다. 공용 계정·남의 토큰으로 올리면 누가 올렸는지 남지 않습니다.
- 토큰을 원격 URL에 저장하지 않습니다. `.env` 같은 토큰 파일은 커밋하지 않습니다.

### 3.3 푸시 전에 확인합니다

- `git status`로 의도하지 않은 파일이 섞였는지 봅니다. `git add -A` 대신 **경로를 지정해** 올립니다.
- 커밋 금지 파일(§5.2)이 없는지 봅니다.
- 민감 정보가 없는지 검사합니다.

  ```bash
  git diff --cached | grep -n -i -E 'password|passwd|secret|api[_-]?key|token|PRIVATE KEY'
  ```

- **이미 머지된 PR의 브랜치에 계속 푸시하지 않습니다.** 머지된 PR에 얹은 커밋은 `main`에 들어가지 않습니다. 푸시 전에 PR 상태를 확인합니다.

  ```bash
  gh pr view <브랜치명> --json state --jq .state   # OPEN 이어야 푸시
  ```

- **작업이 끝나면 앱 컨테이너를 재시작해 변경을 확인합니다.** 앱 컨테이너는 메인 checkout의 `src/`, `config/`를 마운트하므로, 메인 checkout에서 작업 브랜치로 바꾼 뒤 재시작합니다.

  ```bash
  # 메인 checkout에서
  git switch --detach <작업 브랜치>
  docker compose restart app
  curl -s http://127.0.0.1:8091/healthz
  curl -s -X POST http://127.0.0.1:8091/api/v1/recHosp \
    -H 'Content-Type: application/json' -d @tests/fixtures/example_request.json

  # 확인이 끝나면
  git switch main && git pull --ff-only
  docker compose restart app
  ```

### 3.4 강제 푸시

- 리뷰 요청 전, **본인 브랜치에서만** `git push --force-with-lease`를 씁니다.
- `main`과 리뷰 중인 브랜치에는 강제 푸시하지 않습니다. 리뷰 중이면 커밋을 더 얹습니다.

## 4. PR 작성

### 4.1 기본 원칙

- **1 작업 = 1 브랜치 = 1 PR**
- 분리는 필수가 아니라 예외적으로 허용합니다.
- 연속 패치가 필요하면 별도 브랜치/PR을 허용합니다.

### 4.2 PR 제목

커밋 메시지 형식을 그대로 씁니다.

```text
feat(adapters): 병원정보 검색 API로 병원 정보와 실시간 가용병상 조회
```

### 4.3 PR 본문 템플릿

```markdown
Dispatcher: @<github-handle>   <!-- AI 작성 PR인 경우 필수 -->
AI-Tool: <tool-name>           <!-- AI 작성 PR인 경우 권장 -->
Scope: <이 PR이 다루는 범위 1줄>

## Summary
- 무엇을 변경했는가?
- 왜 변경했는가?

## Changes
- 주요 변경 1
- 주요 변경 2

## 설계 문서
- 고친 설계 문서: docs/00_기획/PRD_v0.1.md, docs/10_설계/interface.md (또는 `영향 없음` — 외부 동작이 안 바뀌는 변경)

## 모델 평가 결과   <!-- 프롬프트·규칙 설정·LLM 모델·선정 로직을 바꾼 PR만. 아니면 섹션 삭제 -->
- 평가셋: <평가셋 버전>
- 프롬프트 버전: assessment_prompt_version <값>, prompt_version <값>
- vllm_model: <값>
- 지표: main <PRD F-12 '모델 평가'의 지표 6개> → 변경 <…>
- 재현: <실행 명령·설정 파일 경로>

## Related Issues
- 관련 이슈: #123   <!-- 구현 일감 sub-issue면 `Closes #123` -->
- 상위 이슈: #12    <!-- sub-issue를 다룰 때만. 기능 이슈는 Closes로 걸지 않는다 -->

## Testing
- 실행한 테스트와 결과

## Checklist
- [ ] `CHANGELOG.md`의 `## [Unreleased]` 갱신 (해당 없으면 `no-changelog` 라벨 + 근거)
- [ ] 에어갭: 외부 호출을 넣지 않았고, 새 이미지·라이브러리는 `requirements.txt`·`Dockerfile`에 반영 (해당 없으면 `영향 없음`)
```

**동작이 바뀌는 PR은 같은 PR에서 `CHANGELOG.md`를 고칩니다.** 쓰는 법과 면제 기준은 [34_체인지로그_정책.md](34_체인지로그_정책.md)를 봅니다.

**이슈 연결에 `Closes #N`·`Fixes #N`을 쓰지 않습니다.** PR이 머지되는 순간 이슈가 자동으로 닫혀, 운영 배포·운영 확인 단계가 추적에서 사라집니다. 이슈는 운영 확인까지 끝난 뒤 직접 닫습니다.
예외: 아래 두 경우는 `Closes #N`을 써도 됩니다. 자세한 내용은 [32_이슈_등록가이드.md](32_이슈_등록가이드.md) §6을 봅니다.

- 문서·로컬 개발 도구처럼 **배포가 필요 없는 작업**
- **구현 일감 sub-issue**. 운영 배포와 운영 확인은 상위 기능 이슈(F-xx)에서 추적하므로, PR이 머지될 때 sub-issue가 닫혀도 그 단계가 추적에서 빠지지 않습니다. 상위 기능 이슈는 `Closes`로 걸지 않고 `상위 이슈: #N`으로 적습니다.

**구현을 바꾸는 PR은 같은 PR에서 설계 문서를 고칩니다.** 처리 흐름·단계·저장소·요청·응답 형식이 바뀌면 `docs/00_기획/PRD_v0.1.md`(§5 기능 요구사항, §8 '결정 필요')와 `docs/10_설계/interface.md`(요청·응답 형식)를 함께 고치고, 「설계 문서」에 적습니다. 외부 동작이 안 바뀌면 `영향 없음`이라고 적습니다.

### 4.4 모델 평가 결과 쓰는 법

프롬프트(`classification/prompts/`, `selection/prompts/`)·규칙 설정(`config/transfer_rules.yaml`)·LLM 모델(`config/settings.yaml`의 `vllm_model`)·규칙 엔진과 선정 로직을 바꾼 PR은 「모델 평가 결과」를 채웁니다. 코드가 맞아도 추천 결과가 나빠질 수 있기 때문입니다.

- **같은 조건으로 비교합니다.** 같은 평가셋 버전, 같은 `vllm_model`과 설정으로 `main`과 변경을 비교합니다. 평가셋 버전이 다른 숫자끼리는 비교하지 않습니다.
- **평균만 적지 않습니다.** 같은 평가셋을 여러 번 실행한 결과의 차이를 함께 적어, 차이가 흔들림보다 큰지 보이게 합니다.
- **평가셋은 튜닝에 쓰지 않습니다.** 평가셋([PRD_v0.1.md](../00_기획/PRD_v0.1.md) F-12 '모델 평가') 지표를 적을 때는 튜닝에 쓰지 않았다고 밝힙니다. 평가셋 사례를 프롬프트 예시로 넣지 않습니다.
- **재현 방법을 적습니다.** 숫자만 적으면 리뷰어가 확인할 수 없습니다. 실행 명령·설정 파일 경로·프롬프트 버전·`vllm_model`·`config/transfer_rules.yaml`의 `version`을 적습니다.
- **데이터 자체는 붙이지 않습니다.** 행·환자 정보는 붙이지 않고 집계 지표와 분포만 적습니다(§5.2, 이슈 가이드 §8).

### 4.5 등록된 이슈 확인과 코멘트

커밋·PR을 올릴 때는 **항상 이 작업에 등록된 이슈가 있는지 먼저 확인합니다.**

```bash
gh issue list --state open --assignee @me
gh issue list --state open --search "<키워드>"
```

**이슈가 있으면 그 이슈에 코멘트를 남깁니다.**

- **PR을 올릴 때** — PR 번호, 무엇을 바꿨는지, 어떻게 검증했는지, 남은 것을 적습니다. 이슈 본문 `## 진행`의 `구현 PR #` 줄에 번호도 채웁니다(이슈 가이드 §6.1).
- **올린 PR에 커밋을 더 얹을 때**(리뷰 반영, 추가 수정 등) — 커밋 해시와 무엇을 고쳤는지 적습니다.
- PR 본문의 `관련 이슈: #N`만으로는 이슈 쪽에 무엇이 바뀌었는지 남지 않습니다. 코멘트가 이슈의 작업 기록입니다.

```markdown
PR #15 올림 — 병원정보 검색 API 병원 조회

- 변경: <주요 변경>
- 검증: <실행한 테스트와 결과>
- 남은 것: <리뷰·배포·운영 확인 등>
```

```markdown
PR #15 커밋 추가 `94cae2ad` — <무엇을 고쳤는지(리뷰 반영 등)>
```

```bash
gh issue comment 12 --body-file comment.md
```

본문은 파일로 넘깁니다. `--body "..."`에 여러 줄 마크다운을 넣으면 백틱이 셸 명령으로 실행되거나 따옴표가 깨집니다.

**이슈가 없으면** 먼저 등록한 뒤 PR을 올립니다(이슈 가이드 §1).

### 4.6 PR 크기

- 권장: 바뀐 줄 500 이내
- 500을 넘으면 리뷰어·dispatcher가 분리를 요청할 수 있습니다.
- 생성 코드·잠금 파일처럼 사람이 읽지 않는 파일은 줄 수 계산에서 빼고, 본문에 무엇을 바꿨는지 적습니다.

## 5. AI 작업자 운영 규칙

### 5.1 책임 분리

- AI는 브랜치 생성·커밋·PR 생성을 할 수 있습니다.
- **PR 머지, 운영 배포, 이슈 닫기, 요청 범위를 넓히는 작업은 실행 전에 맡긴 사람에게 확인합니다.** 되돌리기 어렵거나 팀에 영향을 주는 단계이기 때문입니다.

### 5.2 범위 통제와 커밋 금지 파일

- PR 본문에 적은 scope 밖 변경은 하지 않습니다.
- **데이터·모델 파일은 커밋하지 않습니다.** LLM 모델 가중치는 vLLM 서버에 두고, 저장소에는 `config/settings.yaml`의 `vllm_model` 이름만 남깁니다.
  - RAW 데이터·데이터셋(CSV·Parquet 등), 요청 로그(`main.py`가 남기는 요청 본문)
  - LLM 가중치 파일(`*.safetensors` 등)
  - 평가 리포트(`eval/reports/`)와 평가 실행이 만드는 중간 산출물
- **평가셋은 이름에 `synthetic`이 들어간 합성 평가셋만 커밋합니다.** `eval/`에는 평가셋 생성 스크립트와 실행 스크립트를 둡니다. `eval_set/`에는 평가셋을 두고, 그중 이름에 `synthetic`이 들어간 합성 평가셋만 커밋합니다. 그 밖의 `eval_set/` 파일(과거 이송 기록으로 만든 평가셋)은 `.gitignore`로 커밋을 막습니다. 판정은 파일 이름으로 합니다 — 폴더 이름에만 `synthetic`이 있으면 막힙니다. 평가 리포트는 `eval/reports/`에 두고 커밋하지 않습니다.
- 구급 데이터에는 환자 정보가 들어 있습니다. 위 규칙은 저장소가 비공개여도 똑같이 지킵니다.

### 5.3 검증

- CI 통과는 필요조건입니다(CI가 생긴 뒤부터).
- 사람 리뷰어 1명 이상의 승인이 필수입니다.

## 6. 코드 리뷰 기준

리뷰어는 아래를 우선 확인합니다.

- **모듈 경계** — LangChain은 `adapters/`의 vLLM 구현(`LlmClient` 구현) 안에서만 쓰고, 다른 모듈은 LangChain을 import하지 않습니다. 처리 단계 모듈은 `domain/`의 타입으로 데이터를 주고받습니다([PRD_v0.1.md](../00_기획/PRD_v0.1.md) §4 '기술 스택').
- **출력 스키마·프롬프트 일치** — 출력 스키마를 Pydantic 모델 하나에서 만들어 프롬프트와 `with_structured_output()`이 같은 모델을 쓰는지, 프롬프트를 고칠 때 기존 파일을 덮어쓰지 않고 새 버전 파일을 만들었는지 봅니다(PRD N-01 '프롬프트 관리').
- **평가셋 누수** — 평가셋 사례나 정답 병원을 프롬프트에 넣지 않았는지, 이송 시점 이후의 병원 데이터를 평가에 쓰지 않았는지 봅니다(PRD F-12 '모델 평가').
- **재현성** — 프롬프트 버전·`vllm_model`·`config/transfer_rules.yaml`의 `version`·평가셋 버전이 기록되는지 봅니다.
- **실패 처리** — LLM 호출 실패·제한 시간 초과 때 실패 사유를 남기는지, 그때도 시스템이 환자 상태 판단 실패 처리와 PRD F-09 'fallback'으로 항상 응답하는지 봅니다(PRD §3 '시스템 구성').
- **테스트 유의미성** — 신규 기능·버그 재현 테스트가 포함됐는지, 그 테스트가 구현 없이 실패했을지, 리팩터링 전에 특성 테스트로 동작을 고정했는지 봅니다.
- **범위·문서** — 변경 범위가 PR scope와 맞는지, 설계 문서·보안 영향이 반영됐는지 봅니다.
- **에어갭** — 외부 URL 호출, 실행 중 다운로드·설치, CDN 자원이 없는지, 새 이미지·라이브러리가 `requirements.txt`·`Dockerfile`에 반영됐는지 봅니다.

## 7. 머지 전략

### 7.1 머지 방식

- 기본: **Squash and Merge**

### 7.2 머지 전 체크

- CI 통과 (CI가 생긴 뒤부터)
- 사람 승인 1명 이상
- 충돌 해결 완료
- 커밋/PR 제목 컨벤션 준수
- 관련 이슈에 PR 코멘트 등록 (§4.5)
- 동작이 바뀌었으면 `CHANGELOG.md` `## [Unreleased]` 갱신, 아니면 `no-changelog` 라벨 + 근거 ([34_체인지로그_정책.md](34_체인지로그_정책.md))
- 구현이 바뀌었으면 같은 PR에 설계 문서(`docs/00_기획/PRD_v0.1.md`, `docs/10_설계/interface.md`) 갱신 포함. 영향 없으면 PR 본문 「설계 문서」에 `영향 없음`
- 프롬프트·규칙 설정·LLM 모델·선정 로직을 바꿨으면 「모델 평가 결과」 기재 (§4.4)
- 이미지·의존성을 바꿨으면 `requirements.txt`·`Dockerfile` 반영과 에어갭 점검 통과

## 8. 작업 흐름 예시

### 8.1 기능 추가

```bash
# 0) 이슈 등록 (이슈 가이드)
gh issue create --title "[외부연동] 병원정보 검색 API로 병원 기본 정보와 실시간 가용병상을 조회한다" \
  --label enhancement --assignee @me --body-file issue.md

# 1) 최신 main에서 브랜치 생성
git fetch
git switch -c feat/adapters-hospital-search-api origin/main

# 2) 테스트 작성 → 3) 구현 → CHANGELOG.md [Unreleased] 에 항목 추가 (34_체인지로그_정책.md)

# 4) 경로를 지정해 커밋하고 체인지로그 검사, 앱 컨테이너 재시작으로 확인(§3.3)
git add <바꾼 경로>
git commit    # 형식은 §2.7
git diff --name-only origin/main...HEAD | python3 scripts/check_changelog.py --changed -

# 5) 푸시 전 확인(§3.3) 후 푸시, PR 생성
git push -u origin feat/adapters-hospital-search-api
gh pr create --title "feat(adapters): 병원정보 검색 API로 병원 정보와 실시간 가용병상 조회" \
  --label enhancement --assignee @me --body-file pr.md

# 6) 등록된 이슈에 PR 코멘트 (§4.5)
gh issue comment <이슈번호> --body-file comment.md
```

### 8.2 버그 수정

```bash
git fetch
git switch -c fix/selection-rejected-hospital-dup origin/main

# 실패 테스트 추가 → 수정 → 테스트 실행

git commit    # 형식은 §2.7
git push -u origin fix/selection-rejected-hospital-dup
gh issue comment <이슈번호> --body-file comment.md
```

### 8.3 로컬 stale 브랜치 정리

```bash
git fetch --prune
git branch -vv | awk '/: gone]/{print $1}' | xargs -r git branch -D
```

## 9. FAQ

### Q1. 문서 작업인데 브랜치를 `docs/...`로 쓰면 안 되나요?

A. 브랜치 타입은 3개만 쓰므로 `chore/...`를 씁니다. 커밋 타입은 `docs`를 그대로 씁니다.

### Q2. vLLM 모델만 바꿨습니다. PR이 필요한가요?

A. 예. `vllm_model`을 바꾸는 PR을 올리고 「모델 평가 결과」에 PRD F-12 '모델 평가'의 지표 6개를 적습니다.

### Q3. 여러 모듈이 함께 바뀌면 어떻게 하나요?

A. 주 모듈 기준으로 커밋·브랜치명을 정하고, PR 본문에 영향 모듈을 적습니다.

### Q4. AI가 작성한 PR은 자동 머지할 수 있나요?

A. 아닙니다. 사람 승인 후 머지합니다.
