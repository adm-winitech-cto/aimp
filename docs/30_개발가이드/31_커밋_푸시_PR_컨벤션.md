## 1. 브랜치 전략

### 1.1 브랜치 타입 (3종)

브랜치 prefix는 아래 3개만 사용합니다.

- `feat`: 기능 추가
- `fix`: 버그 수정
- `chore`: 그 외 작업 (문서/테스트/리팩터링/CI/설정 포함)

`refactor`, `test`, `docs`, `perf`, `ci`는 **브랜치 타입이 아니라 커밋 타입**으로 씁니다.

### 1.2 브랜치명 규칙

```text
<type>/<module>-<short-desc>
```

- 길이: `type/` 이후 전체 60자 이내 권장
- 소문자 + 숫자 + `-` + `.`만 사용
- 1단계 평면 구조만 사용 (중첩 금지)
- 브랜치는 항상 최신 `main`에서 땁니다: `git fetch` → `git switch -c <브랜치> origin/main`

### 1.3 모듈 목록

브랜치·커밋의 모듈은 아래 목록만 씁니다. [시스템아키텍처v2.drawio](../50_설계/시스템아키텍처v2.drawio)의 섹션을 기준으로 나눴습니다.

## 2. 커밋 메시지

### 2.1 기본 형식

```text
<type>(<module>): <description>

[선택] 본문
[선택] 바닥글
```

### 2.2 커밋 타입

| 타입 | 설명 |
|---|---|
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 리팩터링 (동작 변경 없음) |
| `test` | 테스트 추가/수정 |
| `docs` | 문서 추가/수정 |
| `chore` | 빌드/설정/의존성/기타 관리 작업 |
| `perf` | 성능 개선 (모델 성능이 아니라 실행 속도·자원 사용) |
| `ci` | CI/CD 설정 변경 |

모델 성능(지표)을 개선한 변경은 `perf`가 아니라 `feat`입니다.

### 2.3 모듈 표기

- 가능하면 모듈을 씁니다 (`feat(train): ...`).
- 공통 작업은 모듈을 생략할 수 있습니다 (`chore: ...`, `docs: ...`).
- 모듈을 쓸 때는 §1.3 목록만 씁니다.

### 2.4 설명 작성 규칙

- 50자 이내 권장
- 명령형 현재형
- 마침표 없음
- 한글/영문 혼용 최소화

### 2.5 본문

- 무엇을 왜 바꿨는지 목록으로 적습니다. 리뷰어가 diff를 열기 전에 범위를 알 수 있어야 합니다.
- 마지막 줄에 `관련 이슈: #N`을 적습니다.

### 2.6 AI 작성 커밋 트레일러

AI 도구가 작성한 커밋에는 아래 트레일러를 붙입니다.

```text
Co-Authored-By: Claude <모델명> <noreply@anthropic.com>
```

## 3. 푸시 규칙

### 3.1 main에는 직접 푸시하지 않습니다

모든 변경은 브랜치 → PR → 리뷰 → 머지로 `main`에 들어갑니다.
예외는 **빈 저장소의 초기화 커밋**(PR의 기준 브랜치를 만들기 위한 빈 커밋) 하나뿐입니다.

### 3.2 본인 계정으로 푸시합니다

- `gh auth status`로 확인한 **본인 GitHub 계정**으로 푸시합니다. 공용 계정·남의 토큰으로 올리면 누가 올렸는지 남지 않습니다.
- 토큰을 원격 URL에 저장하지 않습니다. `.env` 같은 토큰 파일은 커밋하지 않습니다.

### 3.3 푸시 전에 확인합니다

- `git status`로 의도하지 않은 파일이 섞였는지 봅니다. `git add -A` 대신 **경로를 지정해** 올립니다.
- 커밋 금지 파일(§5.2)이 없는지 봅니다.
- 민감 정보가 없는지 검사합니다.

  ```bash
  git diff --cached | grep -n -i -E 'password|passwd|secret|api[_-]?key|token|PRIVATE KEY'
  ```

- **이미 머지된 PR의 브랜치에 계속 푸시하지 않습니다.** 머지된 PR에 얹은 커밋은 `main`에 들어가지 않습니다. 푸시 전에 PR 상태를 확인합니다.

  ```bash
  gh pr view <브랜치명> --json state --jq .state   # OPEN 이어야 푸시
  ```

### 3.4 강제 푸시

- 리뷰 요청 전, **본인 브랜치에서만** `git push --force-with-lease`를 씁니다.
- `main`과 리뷰 중인 브랜치에는 강제 푸시하지 않습니다. 리뷰 중이면 커밋을 더 얹습니다.

### 4.1 기본 원칙

- **1 작업 = 1 브랜치 = 1 PR**
- 분리는 필수가 아니라 예외적으로 허용합니다.
- 연속 패치가 필요하면 별도 브랜치/PR을 허용합니다.

### 4.6 등록된 이슈 확인과 코멘트

커밋·PR을 올릴 때는 **항상 이 작업에 등록된 이슈가 있는지 먼저 확인합니다.**

```bash
gh issue list --state open --assignee @me
gh issue list --state open --search "<키워드>"
```

**이슈가 있으면 그 이슈에 코멘트를 남깁니다.**

- **PR을 올릴 때** — PR 번호, 무엇을 바꿨는지, 어떻게 검증했는지, 남은 것을 적습니다. 이슈 본문 `## 진행`의 `구현 PR #` 줄에 번호도 채웁니다(이슈 가이드 §6.1).
- **올린 PR에 커밋을 더 얹을 때**(리뷰 반영, 추가 수정 등) — 커밋 해시와 무엇을 고쳤는지 적습니다.
- PR 본문의 `관련 이슈: #N`만으로는 이슈 쪽에 무엇이 바뀌었는지 남지 않습니다. 코멘트가 이슈의 작업 기록입니다.

```markdown
PR #15 올림 — 재학습 실패 사유 기록

- 변경: <주요 변경>
- 검증: <실행한 테스트와 결과>
- 남은 것: <리뷰·배포·운영 확인 등>
```
> TOFIX: 코멘트 예시 제목 'PR #15 올림 — 재학습 실패 사유 기록'의 작업 이름을 agent 작업 이름으로 바꾼다(안: 'PR #15 올림 — Postgres 병원 데이터 조회').

```markdown
PR #15 커밋 추가 `94cae2ad` — <무엇을 고쳤는지(리뷰 반영 등)>
```

```bash

```

본문은 파일로 넘깁니다. `--body "..."`에 여러 줄 마크다운을 넣으면 백틱이 셸 명령으로 실행되거나 따옴표가 깨집니다.

**이슈가 없으면** 먼저 등록한 뒤 PR을 올립니다(이슈 가이드 §1).

### 5.1 책임 분리

### 7.1 머지 방식

- 기본: **Squash and Merge**
- 머지 후 브랜치 자동 삭제를 기본 정책으로 씁니다.

### 7.2 머지 전 체크

- CI 통과
- 사람 승인 1명 이상
- 충돌 해결 완료
- 커밋/PR 제목 컨벤션 준수
- 관련 이슈에 PR 코멘트 등록 (§4.6)
- 동작이 바뀌었으면 `CHANGELOG.md` `## [Unreleased]` 갱신, 아니면 `no-changelog` 라벨 + 근거 ([34_체인지로그_정책.md](34_체인지로그_정책.md))
- 구현이 바뀌었으면 같은 PR에 설계 문서(`docs/50_설계`, `docs/50_설계/시스템아키텍처v2.drawio`) 갱신 포함. 영향 없으면 PR 본문 「설계 문서」에 `영향 없음`
- 데이터 처리·피처·학습·평가 로직을 바꿨으면 「실험·성능 결과」 기재 (§4.4)
- 이미지·의존성·모델·설치 구성을 바꿨으면 `install/` 반영과 에어갭 점검 통과 ([36_에어갭_설치_가이드.md](36_에어갭_설치_가이드.md) §7.2)

## 10. FAQ

### Q1. 문서 작업인데 브랜치를 `docs/...`로 쓰면 안 되나요?

A. 브랜치 타입은 3개만 쓰므로 `chore/...`를 씁니다. 커밋 타입은 `docs`를 그대로 씁니다.

### Q2. 노트북으로 실험만 했습니다. 어떻게 올리나요?
> TOFIX: 이 절 전체를 뺀다 — agent 저장소에는 노트북 실험과 `experiment` 모듈이 없다. agent는 후보 모델과 프롬프트를 PRD F-12 '모델 평가'의 평가셋 실행으로 비교하고, 그 결과를 §4.4 '실험·성능 결과 쓰는 법'을 고친 「모델 평가 결과」에 적는다.

A. 결과가 코드·설정 변경으로 이어질 때만 올립니다. `experiment` 모듈 브랜치에서 노트북 출력을 지우고 올리고, 결과는 PR 본문 「실험·성능 결과」에 적습니다. 결론만 남기면 되는 탐색은 이슈 코멘트로 남깁니다.

### Q3. 모델만 새로 학습해 배포했습니다. PR이 필요한가요?

A. 아닙니다. 모델 재학습·배포는 MLOps 시스템의 기능으로 하는 운영 작업이고, 기록은 모델 레지스트리와 학습 이력에 남습니다. 코드·설정·학습 스펙이 바뀔 때만 PR을 올립니다.
> TOFIX: Q3의 질문 제목과 이 답을 바꾼다. agent는 모델을 학습하지 않고, 쓸 모델 이름은 `config/settings.yaml`의 `vllm_model`에 있으므로 모델 교체는 설정 변경이라 PR이 필요하다. 질문을 'vLLM 모델만 바꿨습니다. PR이 필요한가요?'로, 답을 '예. `vllm_model`을 바꾸는 PR을 올리고 「모델 평가 결과」에 PRD F-12 '모델 평가'의 지표 6개를 적는다'로 바꾼다.

### Q4. 여러 모듈이 함께 바뀌면 어떻게 하나요?

A. 주 모듈 기준으로 커밋·브랜치명을 정하고, PR 본문에 영향 모듈을 적습니다.

### Q5. AI가 작성한 PR은 자동 머지할 수 있나요?

A. 아닙니다. 사람 승인 후 머지합니다.
