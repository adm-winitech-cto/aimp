## 1. 릴리즈를 관리하는 이유

이 저장소의 코드(MLOps 시스템, 파이프라인, 서빙 전처리)는 구급 시스템의 이송 병원 선정에 쓰입니다. 운영에 나간 것이 정확히 어느 코드인지 알아야 장애 원인을 찾고, 되돌리고, 업그레이드를 판단할 수 있습니다. 그래서 운영에 나가는 코드는 **git 태그와 GitHub Release로 고정**합니다.
> TOFIX: 이 저장소의 코드 '(MLOps 시스템, 파이프라인, 서빙 전처리)'를 agent 코드 '(병원 추천 API, 프롬프트, 규칙 설정)'로, '구급 시스템의 이송 병원 선정'을 '병원선정서비스의 이송 병원 추천'으로 바꾼다. agent는 에어갭 현장에 납품되므로 '운영에 나간 것이 정확히 어느 코드인지'에 '현장에 납품한 것이 정확히 어느 코드인지'를 덧붙인다.

| 목적 | 내용 |
|---|---|
| 공식 버전 | 어떤 커밋이 운영에 나갔는지 태그로 고정한다 |
| 되돌리기 기준점 | 문제가 생기면 돌아갈 이전 버전을 태그로 가리킨다 |
| 변경 공유 | 무엇이 바뀌었는지 운영자·QA·모델 담당에게 Release 본문(= CHANGELOG)으로 전달한다 |
| 원인 분석 | 장애·성능 저하가 어느 버전부터 시작됐는지 추적한다 |
> TOFIX: '변경 공유' 행의 전달 대상 '운영자·QA·모델 담당'을 '운영자·QA·병원선정서비스 담당자·프롬프트와 규칙 설정 담당'으로 바꾼다.

## 3. Release와 CHANGELOG의 관계

릴리즈 하나는 아래 네 가지가 1:1로 대응합니다.

```text
git 태그 vX.Y.Z  =  GitHub Release vX.Y.Z  =  CHANGELOG.md 의 ## [X.Y.Z] 섹션  =  릴리즈 준비 PR 하나
```

```text
main
 ├── commit
 ├── commit ── v0.1.0-alpha   ← CHANGELOG [0.1.0-alpha] 섹션 = Release 본문
 ├── commit
 └── commit                   ← CHANGELOG [Unreleased] 에 쌓이는 중
```

- **Release 본문은 CHANGELOG 해당 섹션의 원문을 그대로 씁니다.** 두 곳에 따로 쓰지 않습니다.
- GitHub의 **"Generate release notes"(자동 생성)는 쓰지 않습니다.** PR 제목(커밋 형식) 목록이라 운영자가 읽을 문장이 아니고, CHANGELOG와 내용이 두 벌이 됩니다.
- CHANGELOG 하단의 compare 링크는 **실제로 발행된 태그만** 가리킵니다. 없는 태그를 가리키면 404가 됩니다.

## 4. 버전 번호 (SemVer)

[Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html)을 따릅니다.

```text
MAJOR . MINOR . PATCH [-접미사]
  1   .   4   .   2              예: 1.4.2, 0.3.0-alpha
```

| 자리 | 이름 | 올리는 경우 | 아래 자리 | 예 |
|---|---|---|---|---|
| 1번째 | MAJOR | 호환이 깨지는 변경 (§4.1) | MINOR·PATCH를 `0`으로 | 서빙 입력 스키마 변경, MQ 메시지 필드 제거 |
| 2번째 | MINOR | 호환을 지키며 기능 추가 | PATCH를 `0`으로 | 드리프트 알림 목록 조회 추가, 새 모델 종류 지원 |
| 3번째 | PATCH | 호환에 영향 없는 버그 수정 | 없음 | 재학습 실패 사유가 기록되지 않던 문제 수정 |
> TOFIX: '예' 열의 mlops 예를 agent 예로 바꾼다: MAJOR '서빙 입력 스키마 변경, MQ 메시지 필드 제거'를 '병원 추천 요청의 필수 필드 추가, 응답 필드 제거(`docs/interface.md`)'로, MINOR '드리프트 알림 목록 조회 추가, 새 모델 종류 지원'을 '응답에 ETA 추가(`docs/PRD_v0.1.md` F-10 'ETA 계산'), 새 프롬프트 버전 추가'로, PATCH '재학습 실패 사유가 기록되지 않던 문제 수정'을 '거절한 병원이 추천 목록에 다시 들어가던 문제 수정'으로 바꾼다.

| 바꾸기 전 | 이유 | 바꾼 뒤 |
|---|---|---|
| `1.2.3` | 버그 수정만 | `1.2.4` |
| `1.2.4` | 호환되는 기능 추가 | `1.3.0` |
| `1.3.0` | 호환이 깨지는 변경 | `2.0.0` |

한 릴리즈에 여러 종류가 섞이면 **가장 높은 자리를 한 번만** 올립니다. PATCH를 올린 뒤 다시 MINOR를 올리지 않습니다.

### 4.1 호환이 깨지는 변경 (MAJOR)

아래 중 하나라도 해당하면 MAJOR를 올립니다.

- **MLOps 시스템 REST API** 응답 필드 제거·타입 변경 (필드 추가는 해당하지 않는다)
- **MQ 메시지**(MLOps 시스템 ↔ 파이프라인) 필드 제거·타입·의미 변경 — 한쪽만 배포되면 다른 쪽이 메시지를 읽지 못한다
- **서빙 입력 스키마** 변경 — 구급 시스템이 보내는 요청 형식이 함께 바뀌어야 하는 경우
- **학습 스펙·모델 레지스트리 형식** 변경으로 이전 학습 스펙이나 등록된 모델을 그대로 읽을 수 없는 경우
- **기존 학습 스펙 버전의 피처 계산·전처리를 바꾸는 경우** — 운영 중인 모델이 학습 때와 다른 입력을 받게 된다(학습-서빙 불일치)
- **데이터셋 저장 형식** 변경으로 이전 기간 데이터셋을 다시 만들어야 하는 경우
- **되돌릴 수 없는 DB 마이그레이션**
- 설정·환경변수의 **필수 키 삭제·이름 변경**
> TOFIX: MAJOR 조건 8항목을 고친다. (1) 'MLOps 시스템 REST API 응답 필드 제거·타입 변경'을 '병원 추천 API(`POST /api/v1/recHosp`) 응답 필드 제거·타입 변경(`docs/interface.md`)'으로 바꾼다. (2) 'MQ 메시지' 항목을 뺀다 — agent에는 MQ가 없다. (3) '서빙 입력 스키마 변경 — 구급 시스템이 보내는 요청 형식이 함께 바뀌어야 하는 경우'를 '요청 스키마 변경 — 병원선정서비스가 보내는 요청 형식이 함께 바뀌어야 하는 경우'로 바꾼다. (4) '학습 스펙·모델 레지스트리 형식' 항목을 뺀다 — agent에는 학습 스펙과 모델 레지스트리가 없다. (5) '기존 학습 스펙 버전의 피처 계산·전처리를 바꾸는 경우' 항목을 뺀다 — agent에는 학습-서빙 불일치가 생길 학습 스펙이 없다. 프롬프트 파일을 같은 이름으로 고치는 일은 MAJOR로 다루지 않고 `docs/PRD_v0.1.md` N-01 '프롬프트 관리'가 금지한다(아래 문단). (6) '데이터셋 저장 형식' 항목을 뺀다 — agent는 데이터셋을 저장하지 않는다. (7) '되돌릴 수 없는 DB 마이그레이션' 항목을 뺀다 — agent는 DB를 관리하지 않는다. (8) '설정·환경변수의 필수 키 삭제·이름 변경'은 그대로 둔다.

### 4.2 재학습이 필요한 변경

호환은 지키지만 **같은 데이터로 학습해도 결과가 달라지는** 변경입니다. 피처 계산(새 학습 스펙 버전에 붙인 경우), 정제 규칙, 학습·평가 로직이 여기에 해당합니다.
> TOFIX: 하위 절 제목 '재학습이 필요한 변경'과 이 문단을 agent 내용으로 바꾼다. agent에는 학습이 없으므로, 제목을 '평가가 필요한 변경'(안)으로, 정의를 '호환은 지키지만 같은 요청에 추천 결과가 달라지는 변경 — 프롬프트 새 버전, 규칙 설정(`config/transfer_rules.yaml`) 변경, `vllm_model` 변경, 후보 필터·선정 로직 변경'으로 바꾼다.

- 버전은 기능이면 MINOR, 버그 수정이면 PATCH로 올립니다.
- CHANGELOG 항목에 `**재학습 필요**` 표기를 붙입니다([34_체인지로그_정책.md](34_체인지로그_정책.md) §6.2). 배포만으로 끝나지 않고 ③ 재학습과 성능 확인이 뒤따라야 하기 때문입니다.
> TOFIX: 두 번째 항목의 표기 `**재학습 필요**`를 `34_체인지로그_정책.md` §6.2 '표기'에서 정할 agent 표기(안: `**평가 필요**`)로 바꾸고, 이유 '배포만으로 끝나지 않고 ③ 재학습과 성능 확인이 뒤따라야 하기 때문'을 '배포 전에 `docs/PRD_v0.1.md` F-12 '모델 평가'의 평가셋으로 지표를 확인해야 하기 때문(PRD N-01 '프롬프트 관리')'으로 바꾼다.

### 4.3 개발 단계(0.x)와 프리릴리즈 접미사

정식 운영(`1.0.0`) 전에는 `0.x.x`를 쓰고, 상태에 따라 접미사를 붙입니다.

```text
0.1.0-alpha   내부 개발 — 기능이 자주 바뀐다
0.x.0-beta    연동 시험 — 구급 시스템과 붙여 시험할 수 있다
1.0.0-rc.1    운영 투입 직전 후보
1.0.0         정식 운영
1.0.1         정식 운영 이후 패치
```
> TOFIX: '0.x.0-beta    연동 시험 — 구급 시스템과 붙여 시험할 수 있다'의 '구급 시스템'을 '병원선정서비스'로 바꾼다.

- **첫 릴리즈는 `0.1.0-alpha`** 입니다.
- `0.x`에서는 SemVer 규칙상 MINOR를 올리면서 호환이 깨질 수 있습니다. 그래서 `0.x`에서 호환이 깨지면 CHANGELOG 항목에 `**BREAKING**`을 붙입니다.
- **MAJOR가 `0`이거나 접미사가 있으면** GitHub Release를 pre-release로 발행합니다(§6.1 C-8).

## 5. 버전이 있는 위치

버전의 **단일 기준은 git 태그**입니다. 코드에 버전 문자열을 하드코딩하지 않습니다. 애플리케이션이 자기 버전을 알아야 하면 빌드할 때 태그 값을 주입합니다.

| 위치 | 형식 | 맞추는 시점 |
|---|---|---|
| git 태그 | `vX.Y.Z[-접미사]` | 절차 B-7 |
| CHANGELOG 헤더 | `## [X.Y.Z] - YYYY-MM-DD` | 절차 A-3 |
| CHANGELOG compare 링크 | 파일 하단 `[X.Y.Z]: …` | 절차 A-4 |
| 서비스 이미지 태그(4개) | `X.Y.Z[-접미사]` — `install/.env`의 `MLOPS_VERSION`, `install/.env.example` 기본값 | 절차 A-5 |
> TOFIX: '서비스 이미지 태그(4개)' 행을 agent 위치 'agent 앱 이미지 태그 — `compose.yaml`의 `image: agent-app:X.Y.Z[-접미사]`'로 바꾼다. `install/.env`와 `MLOPS_VERSION`은 agent 저장소에 없다. 지금 `compose.yaml`에는 릴리즈 태그 없이 `agent-app:0.1.0`이 적혀 있으므로 첫 릴리즈(§4.3 '개발 단계(0.x)와 프리릴리즈 접미사'의 `0.1.0-alpha`) 때 맞춘다. `compose.yaml`이 `./src`를 바인드 마운트해 이미지에 코드가 들어가지 않으므로, 이미지 태그가 코드 버전을 가리키게 하려면 바인드 마운트를 없앨지 정해야 한다. `config/transfer_rules.yaml`의 `version`은 규칙 설정의 버전이라 이 표에 넣지 않는다는 문장을 추가한다.

패키지 메타데이터(예: `pyproject.toml`의 `version`)나 컨테이너 이미지 태그처럼 **버전이 들어가는 곳이 새로 생기면 이 표에 추가**하고, 절차 A-5에서 함께 맞춥니다.

## 6. 릴리즈 절차

### 6.0 시작 조건

아래를 만족하지 않으면 릴리즈하지 않습니다.

1. 릴리즈할 변경이 모두 `main`에 머지돼 있다. CI가 있으면 대상 커밋에서 통과했다.
2. 체인지로그 검사가 통과한다: `python3 scripts/check_changelog.py`
3. `**BREAKING**`·`**재학습 필요**` 항목이 있으면 영향과 대응(재학습 계획, 연동 시스템 일정)을 릴리즈 준비 PR 본문에 적었다.
> TOFIX: 3번 항목의 표기 `**재학습 필요**`를 agent 표기(안: `**평가 필요**`)로, 대응의 예 '재학습 계획, 연동 시스템 일정'을 '평가셋 결과(`docs/PRD_v0.1.md` F-12 '모델 평가'), 병원선정서비스 일정'으로 바꾼다.

### 6.1 절차

릴리즈 한 번은 **준비 PR(A) → 태그(B) → Release(C) → 확인(D)** 입니다.

#### A. 릴리즈 준비 PR

1. `CHANGELOG.md`의 `## [Unreleased]`를 검토·정리한다 — 분류, 중복, 표기(`**BREAKING**`·`**재학습 필요**`), 운영자가 읽을 수 있는 문장인지.
2. §4로 버전을 정한다.
3. `## [Unreleased]`를 `## [X.Y.Z] - YYYY-MM-DD`로 바꾸고, 그 위에 빈 `## [Unreleased]`를 새로 만든다.
4. 파일 하단 compare 링크를 고친다 — `[unreleased]`의 기준을 이번 태그로 바꾸고 `[X.Y.Z]` 줄을 더한다.

   ```markdown
   [unreleased]: https://github.com/adm-winitech-cto/mlops/compare/vX.Y.Z...HEAD
   [X.Y.Z]: https://github.com/adm-winitech-cto/mlops/compare/v<직전 버전>...vX.Y.Z
   ```

   첫 릴리즈는 비교할 직전 태그가 없으므로 `[X.Y.Z]: https://github.com/adm-winitech-cto/mlops/releases/tag/vX.Y.Z`로 둔다.
5. §5 표의 다른 위치가 있으면 이번 버전으로 맞춘다.
6. `docs: CHANGELOG vX.Y.Z 릴리즈 준비` 커밋으로 PR을 올리고, 담당 외 1명의 승인을 받아 Squash 머지한다(§7).
> TOFIX: 두 곳을 바꾼다. (1) 1번 항목의 표기 `**재학습 필요**`를 agent 표기(안: `**평가 필요**`)로 바꾼다. (2) 4번 항목 코드 블록과 그 아래 문장의 URL `https://github.com/adm-winitech-cto/mlops/...`를 `https://github.com/adm-winitech-cto/aimp/...`로 바꾼다.

#### B. 태그

7. `main`에서 태그를 만들어 올린다.

   ```bash
   git switch main && git pull
   git tag -a vX.Y.Z -m "vX.Y.Z"
   git push origin vX.Y.Z
   ```

#### C. GitHub Release

8. CHANGELOG의 `[X.Y.Z]` 섹션을 본문으로 Release를 만든다.

   ```bash
   VERSION=X.Y.Z
   awk -v v="$VERSION" '
     index($0, "## [" v "]") == 1 { f = 1; next }
     f && (/^## \[/ || /^\[[^]]+\]: /) { exit }
     f
   ' CHANGELOG.md > release-notes.md

   # MAJOR 가 0 이거나 접미사가 있으면 --prerelease 를 붙인다 (§4.3)
   gh release create "v$VERSION" --verify-tag --title "v$VERSION" \
     --notes-file release-notes.md --prerelease
   ```

   - `--verify-tag`는 태그가 원격에 없으면 멈춘다. B-7을 건너뛰고 Release가 새 태그를 만드는 일을 막는다.
   - `release-notes.md`가 비어 있으면 A-3이 빠진 것이다. Release를 만들지 말고 A부터 다시 한다.

#### D. 확인

9. Release 화면에서 본문이 CHANGELOG 섹션과 같은지, pre-release 표시가 맞는지 본다.
10. A-4·A-5가 반영됐는지 되짚는다. 검사 스크립트는 릴리즈 섹션마다 compare 링크가 있는지도 본다.

    ```bash
    python3 scripts/check_changelog.py
    ```

    빠졌으면 **후속 PR로 채운다.** 태그를 지우고 다시 만들지 않는다(§8).

#### 요약

| # | 단계 | 빠뜨리면 |
|---|---|---|
| A-3 | CHANGELOG 절단 | Release 본문이 비고, 다음 릴리즈 항목과 섞인다 |
| A-4 | compare 링크 | CHANGELOG에서 이번 버전의 변경 범위를 열 수 없다 |
| A-5 | 버전 위치 맞추기 | 코드·패키지가 옛 버전을 말한다 |
| A-6 | 준비 PR 승인 | 혼자 판단한 버전·분류가 그대로 나간다 |
| B-7 | `main`에서 태그 | 머지되지 않은 코드가 릴리즈된다 |
| C-8 | CHANGELOG 본문으로 Release | Release와 CHANGELOG가 두 벌이 된다 |
| D-10 | 되짚기 | 다음 릴리즈 담당이 잘못된 기준을 물려받는다 |

### 6.2 패치 릴리즈(핫픽스)

1. `fix/<module>-<desc>` 브랜치에서 수정하고 실패를 재현하는 테스트를 더한다.
2. 같은 PR에서 `CHANGELOG.md`의 `[Unreleased]` → `### Fixed`에 항목을 쓴다.
3. 머지 뒤 바로 PATCH 릴리즈를 한다. 급하면 A-1·A-2를 짧게 하되 **A-3·A-4와 D는 줄이지 않는다** — 급한 릴리즈일수록 절단과 되짚기를 건너뛰기 쉽다.

### 6.3 릴리즈 브랜치

`0.x`에서는 릴리즈 브랜치를 두지 않습니다. 다음 MINOR가 `main`에 들어간 뒤 이전 버전에 핫픽스가 필요하면, 최신 버전으로 올리도록 안내합니다. **`1.0.0` 시점에 `release/X.Y` 브랜치 도입을 다시 검토**합니다.

## 7. 책임과 승인

- **릴리즈 담당**: 릴리즈 준비 PR을 올린 사람이 그 릴리즈의 담당입니다. §6.0 확인과 §6.1 전 단계를 합니다.
- **승인**: 릴리즈 준비 PR은 담당 외 **1명 이상**의 승인을 받습니다.
- **태그·Release**: 릴리즈 담당이 만듭니다.
- **AI 작업자**: 릴리즈 준비 PR까지 만들 수 있습니다. 태그와 Release는 맡긴 사람이 확인한 뒤에 만듭니다([31_커밋_푸시_PR_컨벤션.md](31_커밋_푸시_PR_컨벤션.md) §5.1).

## 8. 태그 규칙

- 릴리즈 태그는 **`main`에서만** 만듭니다.
- 이름은 `vX.Y.Z[-접미사]`입니다. 예: `v0.1.0-alpha`, `v1.2.0`
- **발행한 태그는 지우거나 옮기지 않습니다.** 이미 그 태그로 코드를 받아 간 사람이 있을 수 있습니다. 코드가 잘못 나갔으면 다음 PATCH로 고칩니다. Release 본문만 틀렸으면 CHANGELOG를 고쳐 머지한 뒤 Release 본문을 교체합니다.
- 저장소 관리자는 `refs/tags/v*` 대상 tag ruleset으로 태그 삭제·강제 이동을 막고, 생성 권한을 릴리즈 담당으로 제한합니다.
- 머지는 Squash로 합니다([31_커밋_푸시_PR_컨벤션.md](31_커밋_푸시_PR_컨벤션.md) §7). CHANGELOG와 Release가 PR 단위로 쓰이므로 커밋 이력도 PR 단위여야 추적하기 쉽습니다.

## 9. FAQ

**Q1. 모델을 새로 학습해서 배포했습니다. 릴리즈인가요?**
A. 아닙니다. 모델 버전은 모델 레지스트리와 학습 이력에 남습니다(§2.2). 코드가 바뀌지 않았으면 태그도 CHANGELOG도 없습니다.
> TOFIX: Q1의 질문과 답을 바꾼다. agent는 모델을 학습하지 않고, 쓸 모델 이름은 `config/settings.yaml`의 `vllm_model`에 있다. 질문을 'vLLM 모델을 바꿨습니다. 릴리즈인가요?'로, 답을 '예. 모델 교체는 `vllm_model` 설정 변경이라 릴리즈 대상이다(§2.1). 가중치 파일은 vLLM 서버에 두고 태그를 달지 않는다(§2.2)'로 바꾼다.

**Q2. 피처셋(학습 스펙)을 새로 확정했습니다. 릴리즈인가요?**
A. 학습 스펙 확정 자체는 아닙니다(§2.2). 그 과정에서 **피처 계산 코드**를 바꿨다면 그 코드 변경이 릴리즈 대상이고, §4.1·§4.2에 따라 버전을 정합니다.
> TOFIX: Q2의 질문과 답을 바꾼다. agent에는 피처셋(학습 스펙)이 없다. 질문을 '프롬프트를 새 버전으로 바꿨습니다. 릴리즈인가요?'로, 답을 '예. 프롬프트 파일과 `config/settings.yaml`의 프롬프트 버전은 저장소 안에 있으므로 릴리즈 대상이고, §4.2 '재학습이 필요한 변경'을 고친 기준에 따라 버전을 정한다'로 바꾼다.

**Q3. 코드에 현재 버전을 적어 둬야 하나요?**
A. 아닙니다. git 태그가 기준입니다(§5). 버전을 알아야 하면 빌드할 때 주입합니다.

**Q4. MAJOR를 올려야 할지 애매합니다.**
A. §4.1을 먼저 봅니다. 그래도 애매하면 릴리즈 준비 PR에서 리뷰어와 정합니다. "한쪽만 배포되면 깨지는가", "운영 중인 모델이 다른 입력을 받게 되는가"로 판단합니다.
> TOFIX: 판단 기준 '"운영 중인 모델이 다른 입력을 받게 되는가"'를 '"병원선정서비스가 요청·응답 형식을 함께 바꿔야 하는가"'로 바꾼다 — agent에는 학습-서빙 불일치가 없다.

**Q5. Release를 잘못 만들었습니다.**
A. 본문이 틀렸으면 CHANGELOG를 고쳐 머지한 뒤 `gh release edit vX.Y.Z --notes-file release-notes.md`로 본문을 교체합니다. 태그가 틀렸으면(다른 커밋을 가리킴) 태그를 옮기지 말고 다음 PATCH로 바로잡습니다(§8).
