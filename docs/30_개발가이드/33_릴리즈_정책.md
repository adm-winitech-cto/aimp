## 1. 릴리즈를 관리하는 이유

이 저장소의 코드(병원 추천 API, 프롬프트, 규칙 설정)는 병원선정서비스의 이송 병원 추천에 쓰입니다. 운영에 나간 것이 정확히 어느 코드인지, 현장에 납품한 것이 정확히 어느 코드인지 알아야 장애 원인을 찾고, 되돌리고, 업그레이드를 판단할 수 있습니다. 그래서 운영에 나가는 코드는 **git 태그와 GitHub Release로 고정**합니다.

| 목적 | 내용 |
|---|---|
| 공식 버전 | 어떤 커밋이 운영에 나갔는지 태그로 고정한다 |
| 되돌리기 기준점 | 문제가 생기면 돌아갈 이전 버전을 태그로 가리킨다 |
| 변경 공유 | 무엇이 바뀌었는지 운영자·QA·병원선정서비스 담당자·프롬프트와 규칙 설정 담당에게 Release 본문(= CHANGELOG)으로 전달한다 |
| 원인 분석 | 장애·성능 저하가 어느 버전부터 시작됐는지 추적한다 |

## 2. 릴리즈 대상

### 2.1 대상: 저장소의 코드와 설정

- 병원 추천 API(`src/transfer_recommender/`)
- 프롬프트(`classification/prompts/`, `selection/prompts/`)
- 설정과 스키마 — `config/settings.yaml`(`vllm_model` 포함), `config/transfer_rules.yaml`, 요청·응답 형식(`docs/interface.md`)
- 배포 구성 — `Dockerfile`, `compose.yaml`

### 2.2 대상이 아닌 것: 저장소 밖의 가중치·병원 데이터·평가셋

아래 항목은 agent 저장소 밖에 있거나 저장소에 커밋하지 않습니다. **git 태그를 달지 않고 CHANGELOG에도 적지 않습니다.**

| 항목 | 관리하는 곳 |
|---|---|
| LLM 가중치 파일 | vLLM 서버 |
| 병원 데이터 | 구급 DB (agent는 읽기만 한다) |
| 평가셋 중 이름에 `synthetic`이 없는 것 | `eval_set/` — `.gitignore`가 커밋을 막는다([31_커밋_푸시_PR_컨벤션.md](31_커밋_푸시_PR_컨벤션.md) §5.2) |

반대로 쓸 모델 이름(`config/settings.yaml`의 `vllm_model`), 프롬프트 파일, 규칙 설정의 `version`은 저장소 안에 있으므로 릴리즈 대상입니다(§2.1).

대신 **코드 릴리즈가 이 항목들에 주는 영향**은 버전 규칙(§4.1·§4.2·§4.3)에 반영하고 CHANGELOG에 적습니다. 예를 들어 요청 형식(`docs/interface.md`)이 바뀌어 평가셋을 새 형식으로 다시 만들어야 하는 변경, vLLM 서버에 새 가중치 파일을 반입해야 하는 `vllm_model` 변경입니다.

## 3. Release와 CHANGELOG의 관계

릴리즈 하나는 아래 네 가지가 1:1로 대응합니다.

```text
git 태그 vX.Y.Z  =  GitHub Release vX.Y.Z  =  CHANGELOG.md 의 ## [X.Y.Z] 섹션  =  릴리즈 준비 PR 하나
```

```text
main
 ├── commit
 ├── commit ── v0.1.0-alpha   ← CHANGELOG [0.1.0-alpha] 섹션 = Release 본문
 ├── commit
 └── commit                   ← CHANGELOG [Unreleased] 에 쌓이는 중
```

- **Release 본문은 CHANGELOG 해당 섹션의 원문을 그대로 씁니다.** 두 곳에 따로 쓰지 않습니다.
- GitHub의 **"Generate release notes"(자동 생성)는 쓰지 않습니다.** PR 제목(커밋 형식) 목록이라 운영자가 읽을 문장이 아니고, CHANGELOG와 내용이 두 벌이 됩니다.
- CHANGELOG 하단의 compare 링크는 **실제로 발행된 태그만** 가리킵니다. 없는 태그를 가리키면 404가 됩니다.

## 4. 버전 번호 (SemVer)

[Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html)을 따릅니다.

```text
MAJOR . MINOR . PATCH [-접미사]
  1   .   4   .   2              예: 1.4.2, 0.3.0-alpha
```

| 자리 | 이름 | 올리는 경우 | 아래 자리 | 예 |
|---|---|---|---|---|
| 1번째 | MAJOR | 호환이 깨지는 변경 (§4.1) | MINOR·PATCH를 `0`으로 | 병원 추천 요청의 필수 필드 추가, 응답 필드 제거(`docs/interface.md`) |
| 2번째 | MINOR | 호환을 지키며 기능 추가, 또는 반입물 변경 (§4.3) | PATCH를 `0`으로 | 응답에 ETA 추가(`docs/PRD_v0.1.md` F-10 'ETA 계산'), 새 프롬프트 버전 추가, `vllm_model` 교체 |
| 3번째 | PATCH | 호환에 영향 없는 버그 수정. 소스·설정만 바뀌고 반입물은 그대로 | 없음 | 거절한 병원이 추천 목록에 다시 들어가던 문제 수정 |

| 바꾸기 전 | 이유 | 바꾼 뒤 |
|---|---|---|
| `1.2.3` | 버그 수정만 | `1.2.4` |
| `1.2.4` | 호환되는 기능 추가 | `1.3.0` |
| `1.3.0` | 호환이 깨지는 변경 | `2.0.0` |

한 릴리즈에 여러 종류가 섞이면 **가장 높은 자리를 한 번만** 올립니다. PATCH를 올린 뒤 다시 MINOR를 올리지 않습니다.

### 4.1 호환이 깨지는 변경 (MAJOR)

아래 중 하나라도 해당하면 MAJOR를 올립니다.

- **병원 추천 API**(`POST /api/v1/recHosp`) 응답 필드 제거·타입 변경(`docs/interface.md`) (필드 추가는 해당하지 않는다)
- **요청 스키마** 변경 — 병원선정서비스가 보내는 요청 형식이 함께 바뀌어야 하는 경우
- 설정·환경변수의 **필수 키 삭제·이름 변경**

프롬프트를 고칠 때는 **기존 버전 파일을 그대로 두고 새 버전 파일(`final_selection_v2.md` 등)을 만든 뒤 `config/settings.yaml`의 프롬프트 버전을 바꿉니다**([PRD_v0.1.md](../PRD_v0.1.md) N-01 '프롬프트 관리'). 그러면 설정만 되돌려 이전 프롬프트로 돌아갈 수 있고, 호환이 깨지지 않으므로 MAJOR가 아닙니다(§4.2).

### 4.2 평가가 필요한 변경

호환은 지키지만 **같은 요청에 추천 결과가 달라지는** 변경입니다. 프롬프트 새 버전, 규칙 설정(`config/transfer_rules.yaml`) 변경, `vllm_model` 변경, 후보 필터·선정 로직 변경이 여기에 해당합니다.

- 버전은 기능이면 MINOR, 버그 수정이면 PATCH로 올립니다. 다만 `vllm_model` 변경은 새 가중치를 반입해야 하므로 MINOR입니다(§4.3).
- CHANGELOG 항목에 `**평가 필요**` 표기를 붙입니다([34_체인지로그_정책.md](34_체인지로그_정책.md) §6.2). 배포 전에 [PRD_v0.1.md](../PRD_v0.1.md) F-12 '모델 평가'의 평가셋으로 지표를 확인해야 하기 때문입니다(PRD N-01 '프롬프트 관리').

### 4.3 반입물이 바뀌는 변경 (MINOR)

agent는 에어갭 현장에 납품합니다. 소스·설정 파일 말고 현장에 따로 들고 가는 것(반입물)이 바뀌면 버그 수정이라도 MINOR를 올립니다. 그래야 버전만 보고 현장에서 할 일을 알 수 있습니다.

- 반입물: agent 앱 이미지, vLLM 이미지, 모델 가중치
- 해당하는 변경: `requirements.txt`·`Dockerfile` 변경(앱 이미지를 다시 빌드), vLLM 이미지 교체, `vllm_model` 교체
- PATCH만 올랐으면 소스와 설정 파일만 바꿔 넣으면 됩니다. 이미지와 가중치는 그대로 씁니다.

### 4.4 개발 단계(0.x)와 프리릴리즈 접미사

정식 운영(`1.0.0`) 전에는 `0.x.x`를 쓰고, 상태에 따라 접미사를 붙입니다.

```text
0.1.0-alpha   내부 개발 — 기능이 자주 바뀐다
0.x.0-beta    연동 시험 — 병원선정서비스와 붙여 시험할 수 있다
1.0.0-rc.1    운영 투입 직전 후보
1.0.0         정식 운영
1.0.1         정식 운영 이후 패치
```

- **첫 릴리즈는 `0.1.0-alpha`** 입니다.
- `0.x`에서는 SemVer 규칙상 MINOR를 올리면서 호환이 깨질 수 있습니다. 그래서 `0.x`에서 호환이 깨지면 CHANGELOG 항목에 `**BREAKING**`을 붙입니다.
- **MAJOR가 `0`이거나 접미사가 있으면** GitHub Release를 pre-release로 발행합니다(§6.1 C-8).

## 5. 버전이 있는 위치

버전의 **단일 기준은 git 태그**입니다. 코드에 버전 문자열을 하드코딩하지 않습니다. 애플리케이션이 자기 버전을 알아야 하면 빌드할 때 태그 값을 주입합니다.

| 위치 | 형식 | 맞추는 시점 |
|---|---|---|
| git 태그 | `vX.Y.Z[-접미사]` | 절차 B-7 |
| CHANGELOG 헤더 | `## [X.Y.Z] - YYYY-MM-DD` | 절차 A-3 |
| CHANGELOG compare 링크 | 파일 하단 `[X.Y.Z]: …` | 절차 A-4 |
| agent 앱 이미지 태그 | `X.Y.0[-접미사]` — `compose.yaml`의 `app.image`(`agent-app:X.Y.0`) | 앱 이미지가 바뀌는 릴리즈(§4.3)에서만 절차 A-5 |

agent는 파이썬 소스를 이미지에 넣지 않고 `compose.yaml`의 `./src` 바인드 마운트로 그대로 반입합니다. 앱 이미지에는 파이썬과 의존성만 들어갑니다. 그래서 앱 이미지 태그는 **이미지를 마지막으로 다시 빌드한 릴리즈의 버전**이고, 이미지가 바뀌지 않는 릴리즈에서는 올리지 않습니다. 현장에서 돌아가는 코드의 버전은 반입한 소스의 git 태그로 확인합니다.

패키지 메타데이터(예: `pyproject.toml`의 `version`)나 컨테이너 이미지 태그처럼 **버전이 들어가는 곳이 새로 생기면 이 표에 추가**하고, 절차 A-5에서 함께 맞춥니다.

`config/transfer_rules.yaml`의 `version`은 규칙 설정의 버전이라 이 표에 넣지 않습니다.

## 6. 릴리즈 절차

### 6.0 시작 조건

아래를 만족하지 않으면 릴리즈하지 않습니다.

1. 릴리즈할 변경이 모두 `main`에 머지돼 있다. CI가 있으면 대상 커밋에서 통과했다.
2. 체인지로그 검사가 통과한다: `python3 scripts/check_changelog.py`
3. `**BREAKING**`·`**평가 필요**` 항목이 있으면 영향과 대응(평가셋 결과(PRD F-12 '모델 평가'), 병원선정서비스 일정)을 릴리즈 준비 PR 본문에 적었다.

### 6.1 절차

릴리즈 한 번은 **준비 PR(A) → 태그(B) → Release(C) → 확인(D)** 입니다.

#### A. 릴리즈 준비 PR

1. `CHANGELOG.md`의 `## [Unreleased]`를 검토·정리한다 — 분류, 중복, 표기(`**BREAKING**`·`**평가 필요**`), 운영자가 읽을 수 있는 문장인지.
2. §4로 버전을 정한다.
3. `## [Unreleased]`를 `## [X.Y.Z] - YYYY-MM-DD`로 바꾸고, 그 위에 빈 `## [Unreleased]`를 새로 만든다.
4. 파일 하단 compare 링크를 고친다 — `[unreleased]`의 기준을 이번 태그로 바꾸고 `[X.Y.Z]` 줄을 더한다.

   ```markdown
   [unreleased]: https://github.com/adm-winitech-cto/aimp/compare/vX.Y.Z...HEAD
   [X.Y.Z]: https://github.com/adm-winitech-cto/aimp/compare/v<직전 버전>...vX.Y.Z
   ```

   첫 릴리즈는 비교할 직전 태그가 없으므로 `[X.Y.Z]: https://github.com/adm-winitech-cto/aimp/releases/tag/vX.Y.Z`로 둔다.
5. §5 표의 다른 위치가 있으면 이번 버전으로 맞춘다.
6. `docs: CHANGELOG vX.Y.Z 릴리즈 준비` 커밋으로 PR을 올리고, 담당 외 1명의 승인을 받아 Squash 머지한다(§7).

#### B. 태그

7. `main`에서 태그를 만들어 올린다.

   ```bash
   git switch main && git pull
   git tag -a vX.Y.Z -m "vX.Y.Z"
   git push origin vX.Y.Z
   ```

#### C. GitHub Release

8. CHANGELOG의 `[X.Y.Z]` 섹션을 본문으로 Release를 만든다.

   ```bash
   VERSION=X.Y.Z
   awk -v v="$VERSION" '
     index($0, "## [" v "]") == 1 { f = 1; next }
     f && (/^## \[/ || /^\[[^]]+\]: /) { exit }
     f
   ' CHANGELOG.md > release-notes.md

   # MAJOR 가 0 이거나 접미사가 있으면 --prerelease 를 붙인다 (§4.4)
   gh release create "v$VERSION" --verify-tag --title "v$VERSION" \
     --notes-file release-notes.md --prerelease
   ```

   - `--verify-tag`는 태그가 원격에 없으면 멈춘다. B-7을 건너뛰고 Release가 새 태그를 만드는 일을 막는다.
   - `release-notes.md`가 비어 있으면 A-3이 빠진 것이다. Release를 만들지 말고 A부터 다시 한다.

#### D. 확인

9. Release 화면에서 본문이 CHANGELOG 섹션과 같은지, pre-release 표시가 맞는지 본다.
10. A-4·A-5가 반영됐는지 되짚는다. 검사 스크립트는 릴리즈 섹션마다 compare 링크가 있는지도 본다.

    ```bash
    python3 scripts/check_changelog.py
    ```

    빠졌으면 **후속 PR로 채운다.** 태그를 지우고 다시 만들지 않는다(§8).

#### 요약

| # | 단계 | 빠뜨리면 |
|---|---|---|
| A-3 | CHANGELOG 절단 | Release 본문이 비고, 다음 릴리즈 항목과 섞인다 |
| A-4 | compare 링크 | CHANGELOG에서 이번 버전의 변경 범위를 열 수 없다 |
| A-5 | 버전 위치 맞추기 | 코드·패키지가 옛 버전을 말한다 |
| A-6 | 준비 PR 승인 | 혼자 판단한 버전·분류가 그대로 나간다 |
| B-7 | `main`에서 태그 | 머지되지 않은 코드가 릴리즈된다 |
| C-8 | CHANGELOG 본문으로 Release | Release와 CHANGELOG가 두 벌이 된다 |
| D-10 | 되짚기 | 다음 릴리즈 담당이 잘못된 기준을 물려받는다 |

### 6.2 패치 릴리즈(핫픽스)

1. `fix/<module>-<desc>` 브랜치에서 수정하고 실패를 재현하는 테스트를 더한다.
2. 같은 PR에서 `CHANGELOG.md`의 `[Unreleased]` → `### Fixed`에 항목을 쓴다.
3. 머지 뒤 바로 PATCH 릴리즈를 한다. 급하면 A-1·A-2를 짧게 하되 **A-3·A-4와 D는 줄이지 않는다** — 급한 릴리즈일수록 절단과 되짚기를 건너뛰기 쉽다.

### 6.3 릴리즈 브랜치

`0.x`에서는 릴리즈 브랜치를 두지 않습니다. 다음 MINOR가 `main`에 들어간 뒤 이전 버전에 핫픽스가 필요하면, 최신 버전으로 올리도록 안내합니다. **`1.0.0` 시점에 `release/X.Y` 브랜치 도입을 다시 검토**합니다.

---

## 7. 책임과 승인

- **릴리즈 담당**: 릴리즈 준비 PR을 올린 사람이 그 릴리즈의 담당입니다. §6.0 확인과 §6.1 전 단계를 합니다.
- **승인**: 릴리즈 준비 PR은 담당 외 **1명 이상**의 승인을 받습니다.
- **태그·Release**: 릴리즈 담당이 만듭니다.
- **AI 작업자**: 릴리즈 준비 PR까지 만들 수 있습니다. 태그와 Release는 맡긴 사람이 확인한 뒤에 만듭니다([31_커밋_푸시_PR_컨벤션.md](31_커밋_푸시_PR_컨벤션.md) §5.1).

---

## 8. 태그 규칙

- 릴리즈 태그는 **`main`에서만** 만듭니다.
- 이름은 `vX.Y.Z[-접미사]`입니다. 예: `v0.1.0-alpha`, `v1.2.0`
- **발행한 태그는 지우거나 옮기지 않습니다.** 이미 그 태그로 코드를 받아 간 사람이 있을 수 있습니다. 코드가 잘못 나갔으면 다음 PATCH로 고칩니다. Release 본문만 틀렸으면 CHANGELOG를 고쳐 머지한 뒤 Release 본문을 교체합니다.
- 저장소 관리자는 `refs/tags/v*` 대상 tag ruleset으로 태그 삭제·강제 이동을 막고, 생성 권한을 릴리즈 담당으로 제한합니다.
- 머지는 Squash로 합니다([31_커밋_푸시_PR_컨벤션.md](31_커밋_푸시_PR_컨벤션.md) §7). CHANGELOG와 Release가 PR 단위로 쓰이므로 커밋 이력도 PR 단위여야 추적하기 쉽습니다.

## 9. FAQ

**Q1. vLLM 모델을 바꿨습니다. 릴리즈인가요?**
A. 예. 모델 교체는 `vllm_model` 설정 변경이라 릴리즈 대상입니다(§2.1). 가중치 파일은 vLLM 서버에 두고 태그를 달지 않습니다(§2.2).

**Q2. 프롬프트를 새 버전으로 바꿨습니다. 릴리즈인가요?**
A. 예. 프롬프트 파일과 `config/settings.yaml`의 프롬프트 버전은 저장소 안에 있으므로 릴리즈 대상이고, §4.2 '평가가 필요한 변경'의 기준에 따라 버전을 정합니다.

**Q3. 코드에 현재 버전을 적어 둬야 하나요?**
A. 아닙니다. git 태그가 기준입니다(§5). 버전을 알아야 하면 빌드할 때 주입합니다.

**Q4. MAJOR를 올려야 할지 애매합니다.**
A. §4.1을 먼저 봅니다. 그래도 애매하면 릴리즈 준비 PR에서 리뷰어와 정합니다. "한쪽만 배포되면 깨지는가", "병원선정서비스가 요청·응답 형식을 함께 바꿔야 하는가"로 판단합니다.

**Q5. Release를 잘못 만들었습니다.**
A. 본문이 틀렸으면 CHANGELOG를 고쳐 머지한 뒤 `gh release edit vX.Y.Z --notes-file release-notes.md`로 본문을 교체합니다. 태그가 틀렸으면(다른 커밋을 가리킴) 태그를 옮기지 말고 다음 PATCH로 바로잡습니다(§8).
