## 1. 무엇을 위해 쓰나

CHANGELOG는 **버전마다 무엇이 바뀌었는지를 사람이 읽는 문장으로** 남깁니다. GitHub Release 본문도 이 파일에서 그대로 나갑니다([33_릴리즈_정책.md](33_릴리즈_정책.md) §3).

| 읽는 사람 | 찾는 것 |
|---|---|
| agent 운영자(에어갭 현장 납품 담당) | 업그레이드할 가치가 있는지, 병원선정서비스와 호환이 깨지는지, 평가가 필요한지 |
| 프롬프트·규칙 설정 담당 | 프롬프트·규칙 설정·`vllm_model`·선정 로직이 바뀌어 추천 결과가 달라지는지 |
| 병원선정서비스 담당자 | 요청·응답 형식(`docs/interface.md`)이 바뀌는지 |
| QA | 이번 릴리즈에서 무엇을 회귀 테스트해야 하는지 |
| 개발자 | 어느 버전에 어떤 변경이 들어갔는지 |
| 장애 분석 | 문제가 어느 버전부터 생겼는지 |

커밋 로그로는 이 질문에 답할 수 없습니다. 커밋은 "무엇을 고쳤나"를 개발자 말로 적고, CHANGELOG는 "무엇이 달라졌나"를 쓰는 사람 말로 적습니다.

## 2. 파일과 형식

- 위치: 저장소 루트 [`CHANGELOG.md`](../../CHANGELOG.md)
- 형식: [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), 버전은 [SemVer](https://semver.org/spec/v2.0.0.html)
- **새 버전이 위, 오래된 버전이 아래**입니다. 맨 위는 항상 `## [Unreleased]`입니다.

```markdown
# Changelog

…머리말…

## [Unreleased]

### Added
- …

## [0.2.0] - 2026-12-01

### Fixed
- …

## [0.1.0-alpha] - 2026-11-03

### Added
- …

[unreleased]: https://github.com/adm-winitech-cto/aimp/compare/v0.2.0...HEAD
[0.2.0]: https://github.com/adm-winitech-cto/aimp/compare/v0.1.0-alpha...v0.2.0
[0.1.0-alpha]: https://github.com/adm-winitech-cto/aimp/releases/tag/v0.1.0-alpha
```

- 릴리즈 섹션 헤더는 `## [X.Y.Z] - YYYY-MM-DD` 형식입니다.
- 하단 compare 링크는 **실제로 발행된 태그만** 가리킵니다. 첫 릴리즈 전에는 링크를 두지 않습니다.

## 3. 언제 쓰나

**동작이 바뀌는 PR은 같은 PR에서 `CHANGELOG.md`를 고칩니다.** 머지한 뒤나 릴리즈 직전으로 미루지 않습니다.

몰아서 쓰면 반드시 빠집니다. 릴리즈를 자르는 시점에는 이미 무엇이 왜 바뀌었는지 아는 사람이 없고, 커밋을 하나씩 대조해 다시 써야 합니다.

- PR 본문 「Checklist」의 `CHANGELOG.md Unreleased 갱신`을 체크합니다([31_커밋_푸시_PR_컨벤션.md](31_커밋_푸시_PR_컨벤션.md) §4.3).
- 리뷰어는 코드와 함께 CHANGELOG 항목도 리뷰합니다. 항목이 코드와 맞지 않으면 승인하지 않습니다.

---

## 4. 어디에 쓰나

- **항상 `## [Unreleased]` 아래**에 씁니다.
- **릴리즈된 섹션(`## [0.1.0-alpha]` 등)은 릴리즈 담당 외에는 고치지 않습니다.** 이미 발행한 GitHub Release 본문과 어긋나기 때문입니다. 릴리즈된 내용에 오류가 있으면 릴리즈 담당에게 알리고, 담당이 섹션과 Release 본문을 함께 고칩니다.

## 5. 분류

[Keep a Changelog](https://keepachangelog.com/en/1.1.0/)의 6개 소제목을 씁니다.

| 소제목 | 쓰는 경우 |
|---|---|
| `### Added` | 새 기능 — API 요청·응답 필드, 처리 단계(`docs/PRD_v0.1.md` §5 '기능 요구사항'), 규칙, 평가 지표, 지원 LLM 모델 |
| `### Changed` | 기존 동작 변경 |
| `### Deprecated` | 곧 제거될 기능 |
| `### Removed` | 제거된 기능 |
| `### Fixed` | 버그 수정 |
| `### Security` | 보안 수정 — 인증·권한, 환자 정보 등 개인정보 처리 변경은 반드시 여기에 쓴다 |

- 커밋 타입(`feat`·`fix`·`refactor` …)과 소제목은 1:1로 대응하지 않습니다. **쓰는 사람 입장에서 무엇이 달라졌는지**로 고릅니다. 예: `refactor`라도 동작이 바뀌었으면 `Changed`입니다.
- 한 섹션 안에서 같은 소제목은 **한 번만** 씁니다. 두 블록으로 나뉘면 릴리즈를 자를 때 한쪽이 빠집니다.
- 쓸 항목이 없는 소제목은 만들지 않습니다.

## 6. 항목 작성 규칙

### 6.1 형식

```markdown
- **<증상·결과 중심 한 줄>**: <원인은 무엇이었고, 그래서 무슨 일이 있었고, 무엇을 했는지>
```

- **증상·결과부터 씁니다.** 읽는 사람은 자기가 겪은 현상으로 찾습니다. "`rejected_ids` 필터 추가"가 아니라 "거절한 병원이 추천 목록에 다시 들어가던 문제"입니다.
- **원인을 남깁니다**(`Fixed`). 같은 함정에 다시 빠지는 것을 막는 것이 이 파일의 가장 큰 값입니다.
- 코드 식별자·경로는 백틱으로 감쌉니다.
- **한국어, `~다` 체로 씁니다.** 소제목(`Added` 등 표준 키워드)과 코드 식별자만 원문 그대로 둡니다.
- 관련 이슈·PR 번호는 선택입니다. 본문만으로 이해되면 붙이지 않아도 됩니다.

### 6.2 표기

| 표기 | 붙이는 경우 | 본문에 쓸 것 |
|---|---|---|
| `**BREAKING**` | 호환이 깨지는 변경([33_릴리즈_정책.md](33_릴리즈_정책.md) §4.1). `0.x`에서도 붙인다 | 무엇이 깨지는지, 함께 바꿔야 하는 쪽(병원선정서비스), 옮기는 방법 |
| `**평가 필요**` | 같은 요청에 추천 결과가 달라지는 변경 — 프롬프트·규칙 설정·`vllm_model`·선정 로직([33_릴리즈_정책.md](33_릴리즈_정책.md) §4.2) | 어느 프롬프트 버전·규칙 설정 `version`·`vllm_model`부터 적용되는지, `docs/PRD_v0.1.md` F-12 '모델 평가'의 지표 결과 |

표기는 항목 맨 앞에 둡니다.

```markdown
- **BREAKING** · **<한 줄>**: …
- **평가 필요** · **<한 줄>**: …
```

### 6.3 쓰지 않는 것

- **운영 작업** — 현장 설치·재시작, vLLM 가중치 파일 반입, 평가셋 생성([33_릴리즈_정책.md](33_릴리즈_정책.md) §2.2). `vllm_model`·프롬프트 버전·규칙 설정을 바꾼 것은 저장소 변경이므로 CHANGELOG에 적습니다.
- **데이터** — 데이터 행, 평가셋의 행, 환자 정보, `incidentId`. 필요하면 건수·비율 같은 집계 값만 씁니다([32_이슈_등록가이드.md](32_이슈_등록가이드.md) §8).
- **비밀** — 토큰, 비밀번호, 접속 정보.
- **쓰는 사람에게 영향이 없는 변경** — 리팩터링, 테스트, 문서, CI 설정(§7).

### 6.4 예시

```markdown
## [Unreleased]

### Added
- **재학습 결과를 성공과 실패로 나누고 실패 사유를 남긴다**: 재학습이 실패해도 이유가 남지 않아
  같은 실패를 반복했다. 모델 테스트 뒤 성공 기준(테스트 mLogloss ≤ 운영 모델)을 판정하고, 실패하면
  사유 코드·실패 단계·상세 메시지를 학습 이력에 남긴다. 성공한 모델만 배포 후보로 등록한다.

### Fixed
- **재학습 필요** · **좌표가 없는 출동 건의 거리 피처가 0km로 들어가던 문제**: 좌표 결측을 0km로
  계산해 가장 가까운 병원 쪽 확률이 과하게 올라갔다. 결측은 결측으로 넣는다. 학습 스펙 v4부터
  적용하고, v3 이하의 계산은 그대로 두어 운영 중인 모델은 영향이 없다.
```
> TOFIX: 예시 항목 2개(재학습 결과 판정, 좌표가 없는 출동 건의 거리 피처)를 agent 항목 예시로 바꾼다(안: `### Added` '**병원 데이터를 Postgres에서 조회한다**: 정적 병원 목록으로만 추천해 실시간 가용병상을 반영하지 못했다. …', `### Fixed` '**평가 필요** · **거절한 병원이 추천 목록에 다시 들어가던 문제**: …'). agent에는 재학습, mLogloss, 학습 스펙 v3·v4가 없다.

## 7. 면제와 `no-changelog`

아래만 고친 PR은 항목이 필요 없습니다. 검사 스크립트(§8)도 자동으로 넘어갑니다.

- `docs/`, `README.md`, `LICENSE`, `.gitignore`, `.github/ISSUE_TEMPLATE/`
- 테스트 전용 — 경로 어디에 있든 `tests/`·`test/`, `test_*.py`, `*_test.py`, `*.test.ts(x)`, `*.spec.ts(x)`
- 개발용 파일 — `CLAUDE.md`(AI 작업자 지침), `pyproject.toml`(지금은 pytest 설정만 있다), `requirements-dev.txt`(테스트 의존성 — 운영 이미지에 들어가지 않는다), `scripts/`(개발용 검사 스크립트), `eval/`(평가셋 생성·실행 스크립트), `eval_set/`(합성 평가셋)

`.dockerignore`는 이미지에 들어갈 파일을 바꿀 수 있으므로 면제하지 않습니다.

그 밖에 정말 필요 없다고 판단되면(예: 동작이 그대로인 리팩터링, CI 설정) PR에 **`no-changelog` 라벨**을 붙이고 **판단 근거를 PR 본문에** 적습니다. 리뷰어가 근거를 보고 동의하지 않으면 항목을 쓰게 합니다. 라벨을 붙여도 구조·중복·링크 검사는 그대로 합니다.

## 8. 검사

[`scripts/check_changelog.py`](../../scripts/check_changelog.py)가 아래를 봅니다. 사람이 눈으로 읽어서는 잘 걸러지지 않는 것들입니다 — 항목 하나가 길고, 파일이 길고, 머지 충돌 화면에서는 더 안 보입니다.

| 검사 | 실패하는 경우 |
|---|---|
| 구조 | `## [Unreleased]`가 없거나 맨 위가 아님, 릴리즈 헤더가 `## [X.Y.Z] - YYYY-MM-DD` 형식이 아님 |
| 항목 중복 | `[Unreleased]`의 항목이 이미 릴리즈된 섹션에도 있음 — 릴리즈를 자른 뒤 되머지하면 생긴다 |
| 소제목 중복 | 한 섹션에 같은 소제목이 두 번 나옴 |
| compare 링크 | 릴리즈 섹션에 대응하는 링크 줄이 없음, 릴리즈가 있는데 `[unreleased]` 링크가 없음 |
| 항목 누락 | 면제(§7) 아닌 파일을 고쳤는데 `CHANGELOG.md`를 고치지 않음 — `--changed`를 줄 때만 |

```bash
python3 scripts/check_changelog.py                        # 구조·중복·링크
git diff --name-only origin/main...HEAD \
  | python3 scripts/check_changelog.py --changed -        # 항목 누락까지
git diff --name-only origin/main...HEAD \
  | python3 scripts/check_changelog.py --changed - --skip-entry-check   # no-changelog 라벨 PR
```

- PR을 올리기 전에 두 번째 명령을 돌립니다.
- CI가 생기면 PR 검사로 겁니다. `no-changelog` 라벨이 있으면 `--skip-entry-check`를 붙입니다.

## 9. 릴리즈 때 하는 일

릴리즈 담당만 합니다. 절차 전체는 [33_릴리즈_정책.md](33_릴리즈_정책.md) §6.1입니다.

1. `[Unreleased]`를 정리한다 — 분류, 중복, 표기, 문장.
2. `## [Unreleased]`를 `## [X.Y.Z] - YYYY-MM-DD`로 바꾸고 위에 빈 `## [Unreleased]`를 만든다.
3. 하단 compare 링크를 고친다.
4. `python3 scripts/check_changelog.py`가 통과하는지 본다.
5. 이 섹션 원문이 GitHub Release 본문이 된다.
