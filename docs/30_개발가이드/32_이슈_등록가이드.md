## 1. 왜 이슈부터 등록하나

PR은 머지되는 순간 닫힌다. 그런데 **PR이 머지되어도 일은 끝나지 않는다** — 운영 배포, 운영 확인이 남는다. MLOps는 여기에 하나가 더 있다. 코드가 맞게 배포돼도 **모델 성능이 실제로 나아졌는지는 라벨이 확정되는 2주 뒤에야** 알 수 있다.
> TOFIX: 'MLOps는 여기에 하나가 더 있다. 코드가 맞게 배포돼도 모델 성능이 실제로 나아졌는지는 라벨이 확정되는 2주 뒤에야 알 수 있다.' 두 문장을 뺀다 — agent에는 운영 중에 라벨을 확정하는 흐름이 없다. 실제 이송 결과 적재는 `docs/PRD_v0.1.md` §9 '결정 필요'의 '`transport_case` 적재' 항목에서 아직 정해지지 않았다.

그래서 **이슈를 추적 단위로 쓴다.** 이슈 하나가 요청 → 구현 PR → main 반영 → 운영 배포 → 운영 확인(→ 모델 성능 확인)까지 따라간다.
> TOFIX: 추적 흐름의 '(→ 모델 성능 확인)'을 뺀다 — 이 문서 §6.1 '진행 체크리스트'에서 '모델 성능 확인' 줄을 빼기 때문이다.

등록하는 시점:

- **새 기능·수정 작업을 시작할 때** — 브랜치를 만들기 전에 등록한다.
- **이미 진행 중인 작업** — 지금 등록한다. 진행한 만큼 체크리스트에 표시한다.
- **작업 중에 발견한 빈틈** — 지금 PR에서 고치지 않을 것이면 따로 이슈로 남긴다(§5.4).
- **드리프트 알림·성능 저하를 조치하기로 했을 때** — 코드나 학습 스펙을 바꿔야 하면 이슈로 남긴다(§5.5). 재학습만으로 끝나는 운영 조치는 MLOps 시스템의 알림 확인 처리·학습 이력에 남기고, 이슈를 만들지 않는다.
> TOFIX: 네 번째 항목 '드리프트 알림·성능 저하를 조치하기로 했을 때'를 agent 상황으로 바꾼다: '평가셋 실행(`docs/PRD_v0.1.md` F-12 '모델 평가')에서 지표가 나빠졌거나 현장에서 추천 품질 문제가 보고되어 조치하기로 했을 때 — 프롬프트·규칙 설정·LLM 모델을 바꿔야 하면 이슈로 남긴다(§5.5)'. 둘째 문장 '재학습만으로 끝나는 운영 조치는 MLOps 시스템의 알림 확인 처리·학습 이력에 남기고, 이슈를 만들지 않는다'는 뺀다 — agent에는 드리프트 알림, 재학습, 학습 이력이 없다.

### 3.2 요약 쓰는 법

- **기능(enhancement)은 완료됐을 때의 결과**를 적는다.
  - `[재학습] 재학습 결과를 성공과 실패로 나누고 실패 사유를 남긴다`
  - `[모니터링] 드리프트 알림 목록에서 알림을 선택해 상세를 조회한다`
- **버그(bug)는 지금 벌어지는 현상**을 적는다. 원인이 아니라 현상이다.
  - `[서빙] 좌표가 없는 출동 건의 거리 피처가 0으로 들어감`
  - `[모델배포] 헬스체크에 실패해도 교체한 인스턴스가 롤백되지 않음`
- 제목만 보고 무슨 일인지 알 수 있어야 한다. 아래와 같은 제목은 쓰지 않는다.
  - `확인 필요한사항`, `수정`, `개선 필요`, `버그`, `성능 이슈` — 무엇에 대한 것인지 없다.
  - `○○ 화면 개선 사항` 아래에 여러 건을 나열 — 한 이슈에 한 가지만 담는다. 3건이면 이슈 3개로 나눈다.
> TOFIX: 목록의 예시 제목 4개(`[재학습] ...`, `[모니터링] ...`, `[서빙] ...`, `[모델배포] ...`)를 agent 접두어와 agent 작업으로 바꾼다(안: 기능 `[병원조회] Postgres에서 병원 기본 정보와 실시간 가용병상을 조회한다`, `[결과반환] 추천 병원마다 ETA를 응답에 넣는다`, 버그 `[최종선정] 거절한 병원이 추천 목록에 다시 들어감`, `[결과반환] 활력징후가 빈 배열인데 '활력징후 없음' 경고가 빠짐`). 셋째 항목 '제목만 보고 무슨 일인지 알 수 있어야 한다'의 나쁜 예는 그대로 둔다.

## 4. 라벨·담당자

### 4.1 라벨

저장소의 기본 라벨만 쓴다. **도메인 라벨은 만들지 않는다** — 제목 접두어가 그 역할을 한다.

| 라벨 | 쓰는 경우 |
|---|---|
| `enhancement` | 새 기능, 기존 기능 확장, 동작 범위 변경, 모델 성능 개선(피처·학습 방식 변경) |
| `bug` | 의도한 동작과 다르게 동작함(데이터 누수·학습-서빙 불일치 포함) |
| `documentation` | 문서만 바뀌는 작업 |
| `question` | 방향이 정해지지 않아 결정이 먼저 필요함(지표 기준·임계값 등) |
> TOFIX: 라벨 표 설명의 mlops 예를 바꾼다: `enhancement` 행의 '모델 성능 개선(피처·학습 방식 변경)'을 '추천 품질 개선(프롬프트·규칙 설정·LLM 모델 변경)'으로, `bug` 행의 '(데이터 누수·학습-서빙 불일치 포함)'을 '(지침을 위반한 추천, LLM 출력 스키마 검증 실패 포함)'으로 바꾼다. 라벨 4개는 `adm-winitech-cto/aimp` 저장소에 이미 있다.

라벨이 애매하면 "작업이 끝났을 때 사용자가 새로 할 수 있게 되는 것이 있나"로 가른다. 있으면 `enhancement`, 원래 됐어야 하는 것이면 `bug`다.

### 4.2 담당자

- **작업하는 사람**을 지정한다. 본인이 할 일이면 본인을 지정한다.
- 누가 할지 정해지지 않았으면 비워 두고 등록한다. 담당이 정해지면 그때 지정한다.
- 이슈는 **본인 GitHub 계정**으로 등록한다. 공용 계정의 토큰으로 등록하면 누가 올렸는지 남지 않는다.
- AI 작업자(Claude 등)가 등록할 때는 작업을 맡긴 사람을 담당자로 지정한다.

## 5. 본문 템플릿

공통 원칙:

- **배경은 "왜"를 쓴다** — 지금 무엇이 안 되고, 그래서 누가 무엇을 못 하거나 번거롭게 하고 있는가.
- **요구사항은 확인할 수 있는 문장으로 쓴다** — "~할 수 있다", "~한다". "잘 되게", "개선", "성능 향상" 같은 말은 확인할 수 없다. 성능이면 지표와 기준을 적는다.
- **하지 않는 것도 적는다.** 범위 밖을 적어 두지 않으면 리뷰·확인 단계에서 매번 다시 논의하게 된다.
- **위치를 구체적으로 적는다** — 아키텍처 섹션과 단계 이름, 화면 이름, API·MQ 메시지 이름, 모듈·클래스 이름.
> TOFIX: 네 번째 항목 '위치를 구체적으로 적는다'의 예 '아키텍처 섹션과 단계 이름, 화면 이름, API·MQ 메시지 이름'을 agent 예 '`docs/PRD_v0.1.md`의 기능 요구사항 ID와 처리 단계 코드(A0~G), API 경로와 요청·응답 필드 이름(`docs/interface.md`)'으로 바꾼다. agent에는 화면과 MQ가 없다.

### 5.4 작업 중 발견한 빈틈

리뷰나 구현 중에 발견했지만 지금 PR의 범위가 아닌 것은 따로 이슈로 남긴다. 본문 끝에 **어디서 발견했는지** 한 줄을 붙인다.


지금 PR에 끼워 넣지 않는다 — PR의 범위가 흐려지고, 그 수정만 따로 되돌리거나 배포할 수 없게 된다.

## 6. 진행 체크리스트와 닫는 시점

### 6.1 진행 체크리스트

`## 진행`은 모든 작업 이슈에 둔다. 기본 줄은 아래와 같다.

```markdown
## 진행
- [ ] 구현 PR #
- [ ] main 반영                ← 스택 PR일 때만
- [ ] 운영 배포: <무엇을>
- [ ] 운영 확인: <무엇을>
- [ ] 모델 성능 확인: <무엇을>  ← 피처·학습·평가 로직을 바꿨을 때만
```
> TOFIX: 기본 줄의 '- [ ] 모델 성능 확인: <무엇을>  ← 피처·학습·평가 로직을 바꿨을 때만'을 뺀다 — agent에는 배포 뒤 라벨이 확정되어 성능을 다시 재는 흐름이 없다. agent는 추천 품질을 배포 전에 평가셋으로 확인하고 PR의 「모델 평가 결과」에 적는다(`31_커밋_푸시_PR_컨벤션.md` §4.4 '실험·성능 결과 쓰는 법').

- **구현 PR** — PR을 올리면 번호를 적고, 머지되면 체크한다. PR이 여러 개면 줄을 늘린다.
- **main 반영** — 스택 PR(다른 기능 브랜치를 base로 올린 PR)은 머지되어도 **main에 들어가지 않는다.** 스택 PR이면 이 줄을 반드시 둔다.
- **운영 배포** — 재시작·재빌드할 대상(MLOps 시스템, 파이프라인 이미지, Triton 전처리), 적용되는 마이그레이션을 미리 적는다. 배포하는 사람이 이 줄만 보고 범위를 알 수 있어야 한다. 배포하면 날짜와 서버 커밋을 붙여 체크한다.
- **운영 확인** — 무엇을 눌러서 무엇이 보이면 끝인지 적는다. "화면 확인"만 적지 않는다.
  예: `운영 확인: 재학습을 일부러 실패시켜(데이터 기간 0건) 학습 이력에 '데이터 검증 실패' 사유가 보이는지`
- **모델 성능 확인** — 라벨이 확정되는 2주 뒤에 볼 지표와 기준을 적는다. 이 줄이 있으면 운영 확인이 끝나도 이슈를 열어 둔다.
  예: `모델 성능 확인: 배포 2주 뒤 확정 라벨 기준 mLogloss가 배포 전 운영 모델보다 낮은지`
> TOFIX: 목록을 세 곳 바꾼다. (1) '운영 배포'의 재시작·재빌드 대상 '(MLOps 시스템, 파이프라인 이미지, Triton 전처리)'를 '(agent 앱 컨테이너, vLLM 컨테이너, `config/`의 설정 파일)'로 바꾸고, '적용되는 마이그레이션'을 뺀다 — agent는 DB를 관리하지 않는다. (2) '운영 확인'의 예 '재학습을 일부러 실패시켜...'를 agent 예로 바꾼다(안: '발등 개방성 골절 예시 요청을 보내 정형외과 진료가 불가능한 병원이 추천에 없고 "직접의료지도 필요" 표시가 있는지' — `docs/PRD_v0.1.md` F-11 '결과 반환'의 완료조건). (3) '모델 성능 확인' 항목을 뺀다 — 위 코드 블록에서 그 줄을 빼는 것과 같은 이유다. PRD §9 '결정 필요'의 '`transport_case` 적재'가 정해지면 실제 이송 결과로 확인하는 줄을 다시 넣을지 정한다.

배포가 필요 없는 작업(문서, 로컬 개발 도구 등)은 배포·확인 줄을 뺀다.

### 6.2 PR과 연결

PR 본문에는 이렇게 적는다.

```markdown
관련 이슈: #12
```

**`Closes #N`·`Fixes #N`은 쓰지 않는다.** PR이 머지되는 순간 이슈가 자동으로 닫혀, 배포·확인 단계가 추적에서 사라진다. 컨벤션 §4.3 예외대로 **배포가 필요 없는 작업**에만 쓴다.

### 6.3 배포 기록은 댓글로

운영에 배포하면 이슈에 댓글로 기록을 남긴다. 한 번 배포에 여러 이슈가 들어갔으면 각 이슈에 같은 기록을 남긴다.

```markdown
운영 배포 완료(2026-11-02, 서버 `37b83d6b` → `ea10ad40`)

- 재시작: <대상과 순서>. health 결과, 치명 로그 여부
- 마이그레이션: <적용된 버전>
```

### 6.4 닫는 시점

| 상황 | 처리 |
|---|---|
| PR은 머지됐지만 배포 전 | **열어 둔다** |
| 배포는 했지만 운영 확인 전 | **열어 둔다** |
| 운영 확인은 끝났지만 모델 성능 확인 전 | **열어 둔다** |

## 7. gh CLI로 등록·갱신하기

웹에서 등록해도 된다. 터미널에서 할 때는 아래처럼 한다.

### 7.1 등록

본문은 **파일로 넘긴다.** `--body "..."`에 여러 줄 마크다운을 넣으면 셸에서 백틱이 명령으로 실행되거나 따옴표가 깨진다.

```bash
gh issue create -R adm-winitech-cto/mlops \
  --title "[재학습] 재학습 결과를 성공과 실패로 나누고 실패 사유를 남긴다" \
  --label enhancement \
  --assignee @me \
  --body-file issue.md
```
> TOFIX: `-R adm-winitech-cto/mlops`를 `-R adm-winitech-cto/aimp`로 바꾸고, 제목 예시 `[재학습] 재학습 결과를 성공과 실패로 나누고 실패 사유를 남긴다`를 agent 예시(안: `[병원조회] Postgres에서 병원 기본 정보와 실시간 가용병상을 조회한다`)로 바꾼다.

### 7.2 진행 갱신

`gh issue edit --body-file`은 본문을 **통째로 바꾼다.** 현재 본문을 받아서 고친 뒤 올린다.

```bash
gh issue view 12 --json body --jq .body > issue.md
# issue.md에서 체크리스트를 고친다
gh issue edit 12 --body-file issue.md
```

### 7.3 배포 기록·닫기

```bash
gh issue comment 12 --body-file deploy.md

gh issue close 12 --comment "운영 확인·모델 성능 확인 완료"
gh issue close 13 --reason "not planned" --comment "<하지 않기로 한 이유>"
gh issue close 14 --duplicate-of 12
```
> TOFIX: 닫기 예시의 코멘트 '운영 확인·모델 성능 확인 완료'에서 '모델 성능 확인'을 뺀다 — 이 문서 §6.1 '진행 체크리스트'에서 그 줄을 빼기 때문이다.

## 8. WINI-IDP 일감과 이어질 때

이 저장소가 WINI-IDP의 프로젝트에 소스 저장소로 연결되면 WINI-IDP 이슈 등록가이드 §8을 따른다. 요약:

- 이슈를 IDP 일감으로 가져올 수 있다. 제목·본문·담당자가 일감명·배경·작업자로 옮겨지므로 §3~§5 형식과 담당자 지정이 중요하다.
- IDP가 만든 이슈(제목 `[WBS-1.2.3] 일감명`)는 이 가이드의 형식을 적용하지 않는다. **제목·본문·마감일·담당자는 IDP에서 고친다** — GitHub에서 고치면 다음 동기화 때 덮인다.
- PR 제목이나 브랜치 이름에 WBS 코드를 넣으면 PR이 그 일감에 연결된다. 예: PR 제목 `[WBS-1.2.3] ...`, 브랜치 `feat/wbs-1.2.3-...`

## 9. 올리지 않을 것

저장소가 비공개여도 이슈는 팀 전체와 연동된 시스템(IDP 일감 배경 등)으로 퍼진다. 아래는 이슈·코멘트·PR 어디에도 올리지 않는다.

- 토큰·비밀번호·`.env` 값, 접속 키
- **구급 원본 데이터와 그 안의 환자 정보** — 이송완료·병원 수용결과 데이터의 행, 출동ID와 환자 정보를 함께 적은 것
- **데이터셋·예측 로그·확정 라벨의 행** — 필요하면 건수·비율·분포 같은 집계 값만 적는다
- **모델 파일** — 모델 레지스트리의 버전·경로만 적는다
- 고객·기관이 준 원본 파일과 그 안의 데이터 — 구조와 현상만 설명한다
- 개인정보(이름·연락처 등)가 보이는 스크린샷 — 가려서 올린다
> TOFIX: 목록의 예를 agent 데이터로 바꾼다. (1) '구급 원본 데이터와 그 안의 환자 정보 — 이송완료·병원 수용결과 데이터의 행, 출동ID와 환자 정보를 함께 적은 것'을 '병원선정서비스가 보낸 요청 본문과 그 안의 환자 정보, `incidentId`와 환자 정보를 함께 적은 것, 평가셋을 만든 과거 이송 기록의 행'으로 바꾼다. (2) '데이터셋·예측 로그·확정 라벨의 행'을 '평가셋·요청 로그·추천 결과의 행'으로 바꾸고, `main.py`가 요청 본문(환자 정보 포함)을 INFO 로그로 남기므로 로그를 그대로 붙이지 않는다는 문장을 추가한다. (3) '모델 파일 — 모델 레지스트리의 버전·경로만 적는다'를 'LLM 모델 파일 — `config/settings.yaml`의 `vllm_model` 이름만 적는다'로 바꾼다.
