## 1. 왜 이슈부터 등록하나

PR은 머지되는 순간 닫힌다. 그런데 **PR이 머지되어도 일은 끝나지 않는다** — 운영 배포, 운영 확인이 남는다.

그래서 **이슈를 추적 단위로 쓴다.** 이슈 하나가 요청 → 구현 PR → main 반영 → 운영 배포 → 운영 확인까지 따라간다.

등록하는 시점:

- **새 기능·수정 작업을 시작할 때** — 브랜치를 만들기 전에 등록한다.
- **이미 진행 중인 작업** — 지금 등록한다. 진행한 만큼 체크리스트에 표시한다.
- **작업 중에 발견한 빈틈** — 지금 PR에서 고치지 않을 것이면 따로 이슈로 남긴다(§5.4).
- **평가셋 실행([PRD_v0.1.md](../00_기획/PRD_v0.1.md) F-12 '모델 평가')에서 지표가 나빠졌거나 현장에서 추천 품질 문제가 보고되어 조치하기로 했을 때** — 프롬프트·규칙 설정·LLM 모델을 바꿔야 하면 이슈로 남긴다(§5.5).

## 3. 제목 — `[도메인] 한 줄 요약`

### 3.1 도메인 접두어

접두어는 커밋·브랜치 모듈(컨벤션 §1.3 '모듈 목록')과 하나씩 짝을 맞췄다. '범위' 열에는 각 접두어가 맡는 [PRD_v0.1.md](../00_기획/PRD_v0.1.md) §5 '기능 요구사항'의 기능을 적었다.

| 접두어 | 범위 | 커밋·브랜치 모듈 |
|---|---|---|
| `[API]` | F-01 요청 수신과 검증, F-11 결과 반환 — 라우터, 요청 스키마, 응답 스키마 | `api` |
| `[환자분류]` | F-02 중증·특수 자원 판단, F-03 환자 상태 판단, F-04 중증도 판정과 특수상황 판정 | `classification` |
| `[규칙엔진]` | F-05 119구급대 운영지침 규칙 엔진, F-13 진료 역량 규칙 엔진, F-14 ML 모델 규칙 엔진, F-15 도착시간·거리 규칙 엔진 — 분류별 규칙 표, 활력징후 임계치 | `engines` |
| `[처리흐름]` | F-07 규칙 엔진 적용과 레벨 진행 — 처리 단계 호출 순서, 규칙 엔진 활성화, 실패 처리, 경고 수집 | `pipeline` |
| `[최종선정]` | F-08 최종 선정, F-09 최종 선정 fallback — LLM 출력 검증, 우회 판정 | `selection` |
| `[외부연동]` | F-06 병원정보 조회, F-10 ETA 계산, LLM·ML 모델 호출 — `ports/`의 인터페이스와 `adapters/`의 구현(병원정보 검색 API, Tmap ETA API, vLLM, ML 모델), 사용할 모델 이름(`vllm_model`) | `adapters` |
| `[모델평가]` | F-12 모델 평가 — 평가셋 생성, 평가 실행, 리포트 | `eval` |
| `[공통]` | 단계 사이에 주고받는 데이터 타입, 설정 읽기, 로깅 설정 | `shared` 또는 모듈 생략 |
| `[인프라]` | 앱 이미지(`Dockerfile`), `compose.yaml`, 의존성 목록, vLLM 컨테이너 구성, 모델 가중치 반입 | `infra` |
| `[문서]` | `docs/` 아래 문서만 바꾸는 일 — PRD, 개발 가이드 | `docs` |

- 여러 도메인에 걸치면 **주 도메인 하나**만 쓰고, 영향받는 도메인은 본문에 적는다.
- 목록에 없다고 새 접두어를 지어내지 않는다. 필요하면 이 표를 먼저 고친다.
- `[외부연동]`은 시스템이 외부 시스템을 어떻게 호출하는지(`vllm_model`, `ports/`의 인터페이스, `adapters/`의 구현)다. vLLM 컨테이너 구성과 모델 가중치 반입은 `[인프라]`다. 프롬프트 내용을 바꾸는 일은 그 프롬프트를 쓰는 단계의 접두어(`[환자분류]`, `[최종선정]`)다.

### 3.2 요약 쓰는 법

- **기능(enhancement)은 완료됐을 때의 결과**를 적는다.
  - `[외부연동] 병원정보 검색 API로 병원 기본 정보와 실시간 가용병상을 조회한다`
  - `[API] 추천 병원마다 ETA를 응답에 넣는다`
- **버그(bug)는 지금 벌어지는 현상**을 적는다. 원인이 아니라 현상이다.
  - `[최종선정] 거절한 병원이 추천 목록에 다시 들어감`
  - `[처리흐름] 활력징후가 없는 요청에 '활력징후 없음' 경고가 빠짐`
- 제목만 보고 무슨 일인지 알 수 있어야 한다. 아래와 같은 제목은 쓰지 않는다.
  - `확인 필요한사항`, `수정`, `개선 필요`, `버그`, `성능 이슈` — 무엇에 대한 것인지 없다.
  - `○○ 추천 개선 사항` 아래에 여러 건을 나열 — 한 이슈에 한 가지만 담는다. 3건이면 이슈 3개로 나눈다.

## 4. 라벨·담당자

### 4.1 라벨

저장소의 기본 라벨만 쓴다. **도메인 라벨은 만들지 않는다** — 제목 접두어가 그 역할을 한다.

| 라벨 | 쓰는 경우 |
|---|---|
| `enhancement` | 새 기능, 기존 기능 확장, 동작 범위 변경, 추천 품질 개선(프롬프트·규칙 설정·LLM 모델 변경) |
| `bug` | 의도한 동작과 다르게 동작함(지침을 위반한 추천, LLM 출력 스키마 검증 실패 포함) |
| `documentation` | 문서만 바뀌는 작업 |
| `question` | 방향이 정해지지 않아 결정이 먼저 필요함(지표 기준·임계값 등) |

라벨이 애매하면 "작업이 끝났을 때 사용자가 새로 할 수 있게 되는 것이 있나"로 가른다. 있으면 `enhancement`, 원래 됐어야 하는 것이면 `bug`다.

### 4.2 담당자

- **작업하는 사람**을 지정한다. 본인이 할 일이면 본인을 지정한다.
- 누가 할지 정해지지 않았으면 비워 두고 등록한다. 담당이 정해지면 그때 지정한다.
- 이슈는 **본인 GitHub 계정**으로 등록한다. 공용 계정의 토큰으로 등록하면 누가 올렸는지 남지 않는다.
- AI 작업자(Claude 등)가 등록할 때는 작업을 맡긴 사람을 담당자로 지정한다.

## 5. 본문 템플릿

공통 원칙:

- **배경은 "왜"를 쓴다** — 지금 무엇이 안 되고, 그래서 누가 무엇을 못 하거나 번거롭게 하고 있는가.
- **요구사항은 확인할 수 있는 문장으로 쓴다** — "~할 수 있다", "~한다". "잘 되게", "개선", "성능 향상" 같은 말은 확인할 수 없다. 성능이면 지표와 기준을 적는다.
- **하지 않는 것도 적는다.** 범위 밖을 적어 두지 않으면 리뷰·확인 단계에서 매번 다시 논의하게 된다.
- **위치를 구체적으로 적는다** — [PRD_v0.1.md](../00_기획/PRD_v0.1.md)의 기능 요구사항 ID와 처리 단계 코드(A0~G), API 경로와 요청·응답 필드 이름([interface.md](../10_설계/interface.md)), 모듈·클래스 이름.

### 5.1 기능 (`enhancement`)

```markdown
## 배경
<지금 무엇이 안 되는가. 그래서 누가 어떤 불편을 겪는가.>

## 요구사항
- <확인할 수 있는 문장 1>
- <확인할 수 있는 문장 2>
- <하지 않는 것 — 예: ○○는 대상이 아니다, ○○는 지금처럼 둔다>

## 구현 요약
<선택. 구현이 끝난 뒤 채운다. 모듈별로 무엇을 바꿨는지 한두 줄씩.>

## 진행
- [ ] 구현 PR #
- [ ] 운영 배포: <재시작·재빌드할 대상, 설정 파일(`config/settings.yaml`, `config/transfer_rules.yaml`) 변경 여부>
- [ ] 운영 확인: <어떤 요청을 보내 응답에서 무엇을 확인할지>
```

예시 — 요구사항 부분:

```markdown
## 요구사항
- 진료 역량 규칙 엔진은 필수 진료과 진료가 불가능한 병원을 후보에서 뺀다.
- L0 조건으로 후보가 0곳이면 L1 조건으로 다시 거른다.
- L1 조건으로도 0곳이면 직접의료지도 요청(L2)을 보내지 않고 추천하지 않는다 — PRD §1.3 '범위 밖'에 두었다.
```

마지막 줄이 "하지 않는 것"이다. 이유도 함께 적는다.

**기능 이슈와 구현 일감**

- PRD §5 '기능 요구사항'의 기능(F-xx)마다 기능 이슈를 하나 만든다. 요구사항에 기능 ID를 적는다.
- 구현 일감은 그 기능 이슈의 sub-issue로 만든다.
- 운영 배포와 운영 확인은 기능 이슈에서 추적한다. 구현 일감 sub-issue의 `## 진행`에는 배포·확인 줄을 두지 않고, 구현 PR이 머지되면 sub-issue를 닫는다(§6.2).
- 일감 사이의 선행 관계는 GitHub 이슈의 dependency(blocked by)로 건다. 본문에 선행 일감을 따로 적지 않는다.
- 일감의 진행 상태는 이슈에만 남기고, PRD에는 적지 않는다.

### 5.2 버그 (`bug`)

```markdown
## 현상
<무엇이 어떻게 동작하는가. 기대한 동작과 실제 동작.>

## 재현
<필수. 요청 본문(환자 정보를 가린 것)과 단계를 적는다.>
- 환경: 로컬 / 운영
- 대상: <프롬프트 버전, `vllm_model`, `config/transfer_rules.yaml`의 `version`>
- 절차:
  1. <단계·동작>
  2. <동작>
- 기대: <...>
- 실제: <...>

## 영향
<에어갭 현장에 납품된 버전에 영향이 있는가.>

## 수정 방향
<알고 있으면 적는다. 모르면 생략한다.>

## 진행
- [ ] 수정 PR #
- [ ] 운영 배포: <...>
- [ ] 운영 확인: <재현 절차를 다시 해서 기대대로 나오는지>
```

### 5.3 결정이 먼저 필요한 일 (`question` 또는 해당 라벨)

방향이 정해지지 않았으면 선택지를 나열하고, 각 선택지의 **대가**를 적는다. [PRD_v0.1.md](../00_기획/PRD_v0.1.md) §8 '결정 필요' 표의 항목(2단계 응답, 거절 병원 정보 경로, 규칙 엔진의 통과 조건 등)은 이 형식으로 등록한다.

```markdown
## 현상
<무엇이 정해지지 않았는가. 그래서 무엇을 만들 수 없는가.>

## 검토할 방향
- <방향 A>: <무엇을 바꾸는가. 그 결과 함께 바꿔야 하는 곳, 영향받는 기능 요구사항.>
- <방향 B>: <...>

## 결정
<정해지면 채운다. 누가, 언제, 어느 쪽으로.>
```

예: "2단계 응답"(PRD §8 '결정 필요') — 직선거리 순 추천을 먼저 반환하면 병원선정요청이 LLM 응답을 기다리는 지연이 사라지지만, 병원선정요청이 응답을 두 번 받아 화면을 갱신해야 한다. 응답을 1회 보내면 병원선정요청은 그대로지만 LLM 호출 시간만큼 기다린다.

### 5.4 작업 중 발견한 빈틈

리뷰나 구현 중에 발견했지만 지금 PR의 범위가 아닌 것은 따로 이슈로 남긴다. 본문 끝에 **어디서 발견했는지** 한 줄을 붙인다.

```markdown
작업 중 발견(#15 리뷰 중).
```

지금 PR에 끼워 넣지 않는다 — PR의 범위가 흐려지고, 그 수정만 따로 되돌리거나 배포할 수 없게 된다.

### 5.5 추천 품질 (`enhancement` 또는 `bug`)

평가셋 실행([PRD_v0.1.md](../00_기획/PRD_v0.1.md) F-12 '모델 평가')에서 지표가 나빠졌거나 현장에서 추천 품질 문제가 보고되어 **프롬프트·규칙 설정·LLM 모델을 바꿔** 조치할 때 쓴다. 원인이 버그(지침을 위반한 추천, 출력 스키마 불일치 등)면 `bug`, 프롬프트·LLM 모델을 바꾸는 개선이면 `enhancement`다. 원인을 모르는 채 등록하면 `bug`로 두고, 원인이 밝혀지면 라벨을 고친다.

```markdown
## 현상
```

## 6. 진행 체크리스트와 닫는 시점

### 6.1 진행 체크리스트

`## 진행`은 모든 작업 이슈에 둔다. 기본 줄은 아래와 같다.

```markdown
## 진행
- [ ] 구현 PR #
- [ ] main 반영                ← 스택 PR일 때만
- [ ] 운영 배포: <무엇을>
- [ ] 운영 확인: <무엇을>
```

- **구현 PR** — PR을 올리면 번호를 적고, 머지되면 체크한다. PR이 여러 개면 줄을 늘린다.
- **main 반영** — 스택 PR(다른 기능 브랜치를 base로 올린 PR)은 머지되어도 **main에 들어가지 않는다.** 스택 PR이면 이 줄을 반드시 둔다.
- **운영 배포** — 재시작·재빌드할 대상(agent 앱 컨테이너, vLLM 컨테이너, `config/`의 설정 파일)을 미리 적는다. 배포하는 사람이 이 줄만 보고 범위를 알 수 있어야 한다. 배포하면 날짜와 현장 이름, 릴리즈 태그를 붙여 체크한다.
- **운영 확인** — 어떤 요청을 보내 응답에서 무엇을 확인하면 끝인지 적는다.
  예: `운영 확인: 발등 개방성 골절 예시 요청을 보내 정형외과 진료가 불가능한 병원이 추천에 없고 "직접의료지도 필요" 표시가 있는지`

배포가 필요 없는 작업(문서, 로컬 개발 도구 등)과 구현 일감 sub-issue(§5.1)는 배포·확인 줄을 뺀다.

### 6.2 PR과 연결

PR 본문에는 이렇게 적는다.

```markdown
관련 이슈: #12
```

**`Closes #N`·`Fixes #N`은 쓰지 않는다.** PR이 머지되는 순간 이슈가 자동으로 닫혀, 배포·확인 단계가 추적에서 사라진다. 컨벤션 §4.3 예외대로 아래 두 경우에만 쓴다.

- **배포가 필요 없는 작업**
- **구현 일감 sub-issue**. 배포·확인은 상위 기능 이슈에서 추적한다(§5.1). 기능 이슈는 `Closes`로 걸지 않고 `상위 이슈: #N`으로 적는다.

```markdown
Closes #41
상위 이슈: #25
```

### 6.3 배포 기록은 댓글로

운영에 배포하면 이슈에 댓글로 기록을 남긴다. 한 번 배포에 여러 이슈가 들어갔으면 각 이슈에 같은 기록을 남긴다.

```markdown
운영 배포 완료(2026-11-02, <현장 이름>, `v0.1.0` → `v0.2.0`)

- 재시작: <대상과 순서>. health 결과, 치명 로그 여부
- 이미지: <반입한 agent 앱 이미지·vLLM 이미지 태그, 롤백용 이미지>
- 모델: <`vllm_model` 값, 프롬프트 버전, `config/transfer_rules.yaml`의 `version`>

남은 것: <운영 확인 항목과 확인 가능한 날짜>
```

첫 줄 괄호 안에는 날짜, 납품한 현장, 이전·새 릴리즈 태그를 적는다. 반입한 이미지 목록은 「이미지」 줄에 적는다.

### 6.4 닫는 시점

| 상황 | 처리 |
|---|---|
| PR은 머지됐지만 배포 전 | **열어 둔다** |
| 배포는 했지만 운영 확인 전 | **열어 둔다** |
| 확인할 것이 모두 끝남 | 닫는다(완료) |
| 배포가 필요 없는 작업이 머지됨 | 닫는다(`Closes #N`으로 자동으로 닫혀도 된다) |
| 구현 일감 sub-issue의 PR이 머지됨 | 닫는다(`Closes #N`으로 자동으로 닫힌다). 상위 기능 이슈는 열어 둔다 |
| 하지 않기로 함 | 이유를 댓글로 남기고 "not planned"로 닫는다 |
| 다른 이슈와 같은 일 | 원 이슈를 지정해 "duplicate"로 닫는다 |

## 7. gh CLI로 등록·갱신하기

웹에서 등록해도 된다. 터미널에서 할 때는 아래처럼 한다.

### 7.1 등록

본문은 **파일로 넘긴다.** `--body "..."`에 여러 줄 마크다운을 넣으면 셸에서 백틱이 명령으로 실행되거나 따옴표가 깨진다.

```bash
gh issue create -R adm-winitech-cto/aimp \
  --title "[외부연동] 병원정보 검색 API로 병원 기본 정보와 실시간 가용병상을 조회한다" \
  --label enhancement \
  --assignee @me \
  --body-file issue.md
```

### 7.2 진행 갱신

`gh issue edit --body-file`은 본문을 **통째로 바꾼다.** 현재 본문을 받아서 고친 뒤 올린다.

```bash
gh issue view 12 --json body --jq .body > issue.md
# issue.md에서 체크리스트를 고친다
gh issue edit 12 --body-file issue.md
```

### 7.3 배포 기록·닫기

```bash
gh issue comment 12 --body-file deploy.md

gh issue close 12 --comment "운영 확인 완료"
gh issue close 13 --reason "not planned" --comment "<하지 않기로 한 이유>"
gh issue close 14 --duplicate-of 12
```

## 8. 올리지 않을 것

저장소가 비공개여도 이슈는 팀 전체와 연동된 시스템으로 퍼진다. 아래는 이슈·코멘트·PR 어디에도 올리지 않는다.

- 토큰·비밀번호·`.env` 값, 접속 키
- **병원선정요청이 보낸 요청 본문과 그 안의 환자 정보** — `incidentId`와 환자 정보를 함께 적은 것, 평가셋을 만든 과거 이송 기록의 행
- **평가셋·요청 로그·추천 결과의 행** — 필요하면 건수·비율·분포 같은 집계 값만 적는다. `main.py`가 요청 본문(환자 정보 포함)을 INFO 로그로 남기므로 로그를 그대로 붙이지 않는다
- **LLM 모델 파일** — `config/settings.yaml`의 `vllm_model` 이름만 적는다
- 고객·기관이 준 원본 파일과 그 안의 데이터 — 구조와 현상만 설명한다
- 개인정보(이름·연락처 등)가 보이는 스크린샷 — 가려서 올린다

## 9. 고쳐 쓰기 예시

### 9.1 여러 건을 한 이슈에 묶은 경우

고치기 전:

```text
제목: 병원 추천 확인 필요사항
본문: 1. 거절한 병원이 추천 목록에 다시 나옴
      2. 추천 사유에 가용병상 수도 보여 주면 좋겠음
      3. 우회 판정 거리 기준을 몇 km로 할지
```

고친 후 — 이슈 3개:

```text
[최종선정] 거절한 병원이 추천 목록에 다시 들어감                               (bug)
[최종선정] 추천 사유에 가용병상 수를 함께 적는다                               (enhancement)
[최종선정] 우회 판정 거리 기준 X km 결정                                       (question)
```

셋은 담당자도, 끝나는 시점도 다르다. 하나로 묶으면 하나가 끝나도 이슈를 닫을 수 없다.
