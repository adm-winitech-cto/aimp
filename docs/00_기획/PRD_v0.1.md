## 1. 배경과 목표

### 1.1 배경

- **시스템이 하는 일**
    - 입력: 병원선정요청이 보낸 환자 정보, 환자의 현재 위치
    - 출력: 환자를 이송할 병원 후보 N개와 추천 근거를 병원선정요청에 반환
- **이송병원 선정 기준: 다음 네 가지**
    - 119구급대 운영지침의 이송병원 선정 기준
        - 개발팀이 규칙 엔진의 설정 파일로 작성하고, 설정 파일의 버전을 관리
    - 병원의 진료 역량
        - 병원정보 검색 API로 파악
        - 병원 정보는 Postgres가 아니라 병원정보 검색 API로 조회
    - ML 모델이 과거의 유사한 사례에 추천한 병원 후보
        - ML 모델: multiclass classification task 수행
    - 병원까지의 도착 예정 시간 또는 직선거리
        - 도착 예정 시간: Tmap ETA API로 구함
        - 직선거리: 환자의 현재 위치에서 병원까지의 직선거리, 병원정보 검색 API로 구함
- **최종 이송 병원 결정: 사람**
    - 시스템은 병원을 추천만 함
    - 구급대원이 최종 이송 병원을 결정

### 1.3 범위 밖

- **헬기 이송 판단**
    - 헬기 이송을 우선 고려하지 않음
    - 헬기 이송이 필요한지 판단하지 않음
    - 응답에 헬기 이송 검토 권고를 넣지 않음
- **신생아에게 필요한 특수 자원**
    - 신생아를 우선 고려하지 않음
    - `specialPatientInfo.newbornInfo` 값을 특수 자원 판단에 쓰지 않음
- **비고에서 뇌졸중 선별검사 결과 추출**
    - 비고에서 뇌졸중 선별검사 결과를 추출하지 않음
    - 병원선정요청이 선별검사 결과를 보낼 경로가 정해지기 전까지, 뇌졸중 환자에게 '뇌졸중 의증' 규칙을 적용 ([§8 결정 필요](#8-결정-필요)의 '뇌졸중 선별검사 결과 경로')
- **직접의료지도 요청(L2)**
    - 대상: L0 조건과 L1 조건 모두에서 후보 병원이 0곳일 때 시스템이 반환하는 응답
        - L0 조건: 지침의 원칙 조건
        - L1 조건: 의료지도를 받아야 적용할 수 있는 완화 조건
    - 범위 밖으로 둠 (2026-10-28 결정)
    - 후보 병원이 0곳이면 병원을 추천하지 않음 ([F-07 규칙 엔진 적용과 레벨 진행](#f-07-규칙-엔진-적용과-레벨-진행))
- **감사 로그, 사례 집계, 지역에 따라 달라지는 지침**
    - 세 항목은 중요하지만, 개발팀이 나머지 처리 흐름을 모두 정리한 뒤에 추가
    - 지금은 이 항목들의 모듈을 만들지 않음
    - 항목별 내용: 아래 '나중에 추가할 항목'

**나중에 추가할 항목**

- **감사 로그**
    - 필요한 이유
        - vLLM은 여러 요청을 묶어 처리하므로, temperature를 0으로 설정해도 같은 입력에 같은 출력이 나온다는 보장이 없음
        - 그래서 시스템이 판단에 사용한 데이터를 요청마다 저장해야 함
    - 쓰임: 병원선정요청이 적재한 실제 이송 결과를 해당 요청과 연결할 근거. `transport_case` 적재는 병원선정요청의 책임
    - 위치: `pipeline.py`의 마지막 단계
    - 저장 항목: 프롬프트 버전, LLM 입력 객체, LLM 원문 출력
- **사례 집계 (추후 고려)**
    - 후보 병원별 과거 수용률을 계산해 최종 선정 LLM에 참고 정보로 넣는 기능
        - 과거 수용률: 이 유형의 환자를 각 후보 병원이 과거에 얼마나 수용했는가
- **지역에 따라 달라지는 지침 (응급의료 취약지역, 지역이송지침)**
    - 전제: 시스템이 환자 위치의 지역(시·군·구)을 판별해야 함. 시스템은 지금 지역을 판별하지 않음
    - 응급의료 취약지역의 병원 조건 (지침 원문)
        - 중증외상: 가장 가까운 지역응급의료기관 이상 (지침의 헬기 이송 선택지는 제외)
        - 비외상 중증: 가장 가까운 응급의료기관 이상
        - 뇌졸중 의증, 뇌졸중 선별검사 양성: 가장 가까운 지역응급의료기관
        - 경증외상, 비외상 경증, 심폐정지: 취약지역이 아닌 지역과 같은 조건
    - 지역이송지침
        - 적용 조건: 환자가 지역이송지침을 운영하는 지역에 있고, 그 지침의 적용 대상일 때
        - 적용 방식: 119구급대 운영지침 규칙 엔진이 분류별 규칙 표 대신 지역이송지침의 규칙을 적용
    - 추가할 곳: `engines/guideline`, `config/transfer_rules.yaml`

## 3. 시스템 구성

**핵심 원칙과 설계 방향**

- **규칙 엔진**
    - 구성: [§1.1](#11-배경)의 이송병원 선정 기준 네 가지를 기준마다 규칙 엔진 하나로 적용
        - 119구급대 운영지침 규칙 엔진
        - 진료 역량 규칙 엔진
        - ML 모델 규칙 엔진
        - 도착시간·거리 규칙 엔진
    - 활성화: 개발팀이 규칙 엔진마다 활성화 여부를 `config/`에서 설정
    - 통과 조건: ML 모델 규칙 엔진과 도착시간·거리 규칙 엔진의 통과 조건은 정해지지 않음 ([§8 결정 필요](#8-결정-필요)의 '규칙 엔진의 통과 조건')
- **LLM의 역할**
    - 환자 상태 판단 LLM
        - 판단 항목: 외상 여부, 필요한 진료과, 중증응급질환, 환자에게 해당하는 중증외상 기준 항목
        - 병원은 고르지 않음
    - 최종 선정 LLM
        - 선정 범위: 119구급대 운영지침 규칙 엔진을 통과한 병원 중에서만 선정
        - 출력: 병원 N개와 추천 근거
        - ML 모델이 추천한 병원 후보
            - 참고 정보로 받음
            - 규칙 엔진을 통과하지 못한 병원은 고르지 않음
- **순위 기준: 거리보다 진료 여건 우선**
    - 우선 기준: 가용병상, 진료과 같은 병원의 진료 여건
    - 보조 기준: 환자 위치와 병원 사이의 직선거리
    - 예외: 심폐정지 환자는 직선거리가 가장 짧은 병원을 1순위에 둠
    - 우회: 최종 선정 LLM이 직선거리가 가장 짧은 병원이 아닌 병원을 1순위에 둘 때
        - 시스템: 그 추천에 우회 표시를 넣음
        - 최종 선정 LLM: 우회 사유를 반드시 작성
- **후보 병원이 0곳일 때: 조건을 임의로 낮추지 않음**
    - 지침이 허용하는 모든 완화 단계를 적용해도 0곳이면, 시스템은 병원을 추천하지 않음
- **실패 처리: LLM이나 외부 시스템의 호출이 실패해도 항상 응답**
    - 환자 상태 판단 LLM 실패 (출력 검증 실패, 제한 시간 초과)
        - 환자를 외상 환자로 간주하지 않음
        - 필수 진료과 조건과 중증응급질환 조건 없이 후보 병원 선정
    - 최종 선정 LLM 실패 (출력 검증 실패, 제한 시간 초과)
        - 직선거리가 짧은 순서로 병원 N개를 골라 응답
        - 이 문서는 이 처리를 최종 선정 fallback이라고 부름
    - 일부 시스템만 동작하지 않을 때
        - fallback을 사용해 그 시점에 낼 수 있는 최선의 결과를 반환
        - 어떤 fallback을 사용해도 활성화된 규칙 엔진의 조건을 통과한 병원만 추천
        - 그래서 활성화된 규칙 엔진의 조건이 결과 품질의 하한
- **처리 흐름의 분기: 다음 여섯 곳뿐**
    - 환자 상태 판단 LLM 실패 → 외상 환자로 간주하지 않음, 필수 진료과 조건과 중증응급질환 조건 없이 진행
    - 4대 중증 환자 → 중증도 판정을 하지 않음
    - 후보 병원 0곳 → 다음 레벨의 조건으로 규칙 엔진 재실행
    - ML 모델 호출 실패 → ML 모델의 병원 후보 없이 최종 선정 진행
    - 최종 선정 LLM 실패 → 최종 선정 fallback으로 응답
    - Tmap ETA API 호출 실패 → ETA 대신 병원정보 검색 API가 준 직선거리를 응답에 넣음
- **모듈과 인터페이스**
    - 모듈: 처리 단계 단위로 나눔
        - 처리 단계, 코드 모듈, 테스트가 같은 단위로 대응
        - 지침이나 설계가 바뀌면 개발팀이 고칠 모듈을 바로 찾을 수 있음
    - 인터페이스: 구현 교체가 정해진 다음 네 곳에만 둠
        - `HospitalRepository`
            - 운영: 병원정보 검색 API로 병원 정보 조회
            - 테스트, 구현 초기: mock 병원 데이터
        - `EtaProvider`
            - 운영: Tmap ETA API로 ETA 계산 (에어갭 현장에서 예외적으로 호출 가능)
            - 테스트: 가짜 구현
        - `LlmClient`
            - 환자 상태 판단과 최종 선정이 같은 인터페이스를 씀
            - 평가: 두 후보 모델 비교
            - 테스트: LLM 호출 실패와 제한 시간 초과를 일부러 일으킴
        - ML 모델 클라이언트(이름 미정)
            - 운영: ML 모델에서 병원 후보를 받음
            - 테스트: ML 모델 호출 실패를 일부러 일으킴
    - 설정 데이터: 코드 수정 없이 바꿔야 하는 데이터는 `src/` 밖 `config/`에 둠
        - 119구급대 운영지침이 개정되면 개발팀이 `config/`의 규칙 설정 파일을 수정

```mermaid
    A2["A2. 중증도 판정<br/>외상: 중증외상 지침 기준<br/>비외상: Pre-KTAS 단계 + 활력징후, 판정이 갈리면 더 중증인 쪽을 택함"]
    B["B. 119구급대 운영지침 규칙 엔진<br/>환자 분류 → 레벨별 병원 등급 조건"]
    C0["C0. 병원정보 조회 (HospitalRepository, 병원정보 검색 API)<br/>시·도 구분 없이 병원 기본 정보 + 실시간 데이터 + 환자 위치에서의 직선거리"]
    C["C. 규칙 엔진 적용 (활성화된 엔진만, 레벨 진행)<br/>119구급대 운영지침: 병원 등급<br/>진료 역량: 특수 자원, 중증응급질환, 필수 진료과(진료불가 메시지는 LLM이 판단), 가용병상(오래된 값에는 태그만 붙임)<br/>ML 모델: ML 병원 후보 표시 · 도착시간·거리: 직선거리 상위 M개"]
    ML["ML. 병원 후보 추천 (ML 모델 호출)<br/>과거 유사 사례에 추천한 병원 후보"]
    E["E. 최종 선정 (LLM 호출)<br/>규칙 엔진을 통과한 직선거리 상위 M개 + ML 병원 후보 + 비고 원문<br/>→ 최종 후보 N개, 순위, 추천 사유 → 검증<br/>순위: 가용병상·진료과 등 조건 우선, 직선거리는 보조"]
    FB["최종 선정 fallback<br/>직선거리 순 N개 + 정해진 문장 틀의 근거 + fallback 사유"]
    F["F. ETA 계산 (Tmap ETA API)<br/>선정된 N개 병원만"]
    G["G. 결과 반환<br/>추천 N개 + ETA를 병원선정요청에 반환"]

    IN --> A0 --> A1 --> Q0
    Q0 -- 예 --> B
    Q0 -- 아니오 --> A2 --> B
    B --> C
    A0 -. 특수 자원 목록 .-> C
    A1 -. 필수 진료과·중증응급질환 코드 .-> C
    IN -. 환자 위치 .-> C0
    C0 -. 병원 데이터·직선거리 .-> C
    IN -. 비고 원문 .-> A1
    IN -. 비고 원문 .-> E
    IN -. 환자 정보 .-> ML
    ML -. ML 병원 후보 .-> C
    C --> E
    E -- 검증 실패·제한 시간 초과 --> FB --> F
    E --> F --> G
```

- **LLM 호출 횟수:** 요청 한 건당 최대 2회
    - 환자 상태 판단(A1): 1회
    - 최종 선정(E): 1회
- **레벨:** 레벨별 조건은 [F-05 119구급대 운영지침 규칙 엔진](#f-05-119구급대-운영지침-규칙-엔진)의 분류별 규칙 표에 있음
    - L0: 지침의 원칙 조건
    - L1: 의료지도를 받아야 적용할 수 있는 완화 조건
- **거리와 ETA: 두 값을 함께 씀**
    - 직선거리
        - 출처: 병원정보 검색 API
        - 쓰는 곳: ETA 계산 전 단계 전부 (후보 정렬, 최종 선정 LLM에 넣을 상위 M개 선택, 우회 판정, 최종 선정 fallback의 병원 순서)
    - ETA
        - 출처: Tmap ETA API
        - 계산 대상: 최종 선정이나 최종 선정 fallback으로 고른 병원 N개만
- **G단계:** 결과 반환만 함

**처리 순서** — `pipeline.py`는 다음 순서로 처리 단계를 호출한다.

```python
warnings   = []                                                    # 각 단계가 경고를 이 목록에 추가
if not req.vital_signs:                                            # 4대 중증 환자를 포함한 모든 환자
    warnings.append("활력징후 없음")
judgment   = severe_resource.judge(req)                            # A0
assessment = patient_assessment.assess(req, llm_client, warnings)  # A1, 모든 환자. LLM이 실패하면 None
category   = judgment.category or severity.judge(req, assessment)  # A2, 4대 중증이 아닐 때만. assessment가 None이면 비외상 기준
special    = severity.special_situations(req, category, assessment)  # 외상 환자만. 항목이 있으면 "직접의료지도 필요"
levels     = guideline.levels_for(category)                        # B: [L0 조건, L1 조건]
hospitals  = hospital_repository.find(req.location, categories_of(levels))  # C0: 병원정보 검색 API, L0·L1 병원 분류를 합쳐 한 번 조회, 직선거리 포함
engines    = enabled_engines()                                     # config에서 활성화된 규칙 엔진. 걸러내는 엔진이 먼저
for level in levels:                                               # C: 후보가 0곳이면 다음 레벨
    candidates = hospitals
    for engine in engines:                                         # 모든 엔진이 같은 인터페이스를 따름
        candidates = engine.apply(candidates, judgment, assessment, level, warnings)
    if candidates:
        break
else:                                                              # L1 조건으로도 0곳이면 추천하지 않음 (직접의료지도 요청은 범위 밖)
    return Recommendation(...)                                     # 추천 병원 없음
picked = selection.select(candidates, ...)                # E, 실패하면 최종 선정 fallback
etas   = eta_provider.estimate(picked)                    # F: Tmap ETA API, 선정된 N개만. 실패하면 직선거리로 대체
return Recommendation(...)                                # api/가 응답 JSON으로 변환
```

## 4. 기술 스택

**서비스** — 개발팀이 새로 추가하는 인프라는 vLLM 하나다. 개발팀은 나머지 기능을 애플리케이션 코드와 외부 시스템(병원정보 검색 API, Tmap ETA API, ML 모델)으로 구현한다.

| 구성 | 역할 | 기술 | 버전·비고 |
|---|---|---|---|
| 앱 | 병원 추천 API | **Python**, FastAPI, Pydantic | 앱 이미지의 기반 이미지는 `python:3.12-slim`이고, 앱은 root가 아닌 사용자로 실행한다. 패키지 이름은 `aimp`다 |
| LLM 서빙 | 환자 상태 판단, 진료불가 메시지 판단, 최종 선정의 LLM 호출 처리 | **vLLM** (로컬 서버) | 후보 모델은 qwen 3.8 flash next와 solar2 int4 GlobalPruned다(세부 사양 미확인). 시스템은 vLLM structured outputs(JSON 스키마)로 LLM 출력 형식을 제한하고, temperature를 0으로 둔다 |

**외부 시스템**

| 외부 시스템 | 역할 | 비고 |
|---|---|---|
| 병원정보 검색 API | 병원 기본 정보, 실시간 데이터, 환자 위치에서 병원까지의 직선거리 제공 | 에어갭 현장망 안에 같은 API가 있다 (2026-10-29 확인) |
| Tmap ETA API | 선정된 병원 N개의 도착 예정 시간 제공 | 에어갭 현장에서 예외적으로 호출 가능 |
| ML 모델 | 과거의 유사한 사례에 추천한 병원 후보 제공 | 에어갭 현장망 안에 있는지 확인 필요 |

- 개발팀은 `compose.yaml`에 앱만 정의한다. vLLM은 앱과 따로 실행하고, 앱은 `config/settings.yaml`의 `vllm_url`로 vLLM을 호출한다.
- 시스템은 LLM을 호출할 때 LangChain(`langchain-openai`)을 쓴다. LangChain은 `adapters/`의 vLLM 구현(`LlmClient` 구현) 안에서만 쓰고, 다른 모듈은 LangChain을 import하지 않는다.
- 시스템은 꼭 필요하기 전에는 LangGraph, LangMem, 외부 프롬프트 관리 서비스, 임베딩 모델을 쓰지 않는다.
- 의존성: 개발팀은 실행 의존성(FastAPI, uvicorn, Pydantic, `langchain-openai`, PyYAML)을 `requirements.txt`에, 테스트 의존성(pytest, FastAPI TestClient용 httpx2)을 `requirements-dev.txt`에 둔다. 운영 이미지는 `requirements.txt`의 의존성만 설치한다.
- 외부 API 호출: 시스템은 외부 API(병원정보 검색 API, Tmap ETA API, ML 모델)를 `requests`로 호출한다.
- 거리: 최종 선정 전까지 시스템은 병원정보 검색 API가 준 직선거리로 후보 병원을 정렬하고, LLM에 넣을 상위 M개 병원을 고르고, 우회를 판정하고, 최종 선정 fallback의 병원 순서를 정한다. 시스템은 Tmap ETA API로 최종 선정된 병원 N개의 ETA만 구한다([F-10 ETA 계산](#f-10-eta-계산)).

**코드 구조** — 모듈 단위로만 적는다. 모듈 안의 파일 구성은 코드와 각 모듈의 docstring을 따른다.

```
src/
├── main.py            # 앱 진입점: FastAPI 앱 생성, 인터페이스에 구현을 연결
├── api/               # 요청 수신과 검증(F-01), 결과 반환(F-11)
├── pipeline.py        # 처리 흐름: 단계 호출 순서, 레벨 진행, 실패 처리, 경고 수집
├── domain/            # 단계 사이에 주고받는 데이터 타입
├── classification/    # 환자 판단: A0 중증·특수 자원 판단, A1 환자 상태 판단(LLM, 프롬프트 포함), A2 중증도 판정
├── engines/           # 규칙 엔진: §1.1 이송병원 선정 기준 하나에 엔진 하나, config로 켜고 끔
│   ├── guideline      #   119구급대 운영지침 규칙 엔진 (분류별 규칙, 레벨별 병원 등급)
│   ├── capability     #   진료 역량 규칙 엔진 (특수 자원, 진료과, 중증응급질환, 가용병상). 진료불가 메시지 판단(LLM, 프롬프트 포함)
│   ├── ml             #   ML 모델 규칙 엔진 (ML 모델이 추천한 병원 후보)
│   └── travel         #   도착시간·거리 규칙 엔진
├── selection/         # E 최종 선정(LLM, 프롬프트 포함), 출력 검증, 우회 판정, 최종 선정 fallback
├── ports/             # 외부 시스템 인터페이스: HospitalRepository, EtaProvider, LlmClient, ML 모델 클라이언트(이름 미정)
├── adapters/          # 인터페이스 구현: 병원정보 검색 API, Tmap ETA API, vLLM, ML 모델, mock
└── common/            # 공통 설정: 설정 읽기, 로깅 설정
config/                # settings.yaml(설정값, 엔진별 활성화 여부, 외부 시스템 주소), 엔진별 규칙 파일(지금은 guideline용 transfer_rules.yaml)
tests/                 # src/와 같은 구조. 외부 시스템은 가짜 adapter로 대체
eval/                  # 평가셋 생성, 평가 실행. 리포트는 eval/reports/에 두고 커밋하지 않는다
eval_set/              # 평가셋. 이름에 synthetic이 들어간 합성 평가셋만 커밋한다
Dockerfile             # 앱 이미지 (python:3.12-slim, root가 아닌 사용자로 실행)
compose.yaml           # 앱 (vLLM은 따로 실행)
```

**모듈 규칙**

- **의존 방향: 한쪽으로만**
    - `api` → `pipeline` → `classification`·`engines`·`selection` → `domain`·`ports`
    - `adapters`는 `ports`의 인터페이스를 구현만 함
    - 구현을 인터페이스에 연결하는 곳은 `main.py` 하나
    - 판단 로직(`classification`, `engines`, `selection`)은 `adapters`를 import하지 않음
    - 효과: 외부 시스템을 바꾸면 `adapters/`의 구현 하나와 `config/`만 바뀜
- **규칙 엔진: 모두 같은 인터페이스**
    - 입력: 후보 병원 목록, 환자 판단 결과
    - 출력: 걸러낸 후보 병원 목록, 또는 순위용 정보를 붙인 후보 병원 목록
    - `pipeline.py`는 `config/`에서 활성화된 엔진을 차례로 호출만 함
    - 효과: 선정 기준을 추가·삭제·비활성화하면 엔진 모듈 하나와 `config/`만 바뀜
    - [§8 결정 필요](#8-결정-필요)의 '규칙 엔진의 통과 조건'이 정해져도 엔진 안쪽만 바뀜
- **LLM 단계: 규칙 엔진이 아님**
    - A1 환자 상태 판단은 `classification/`, E 최종 선정은 `selection/`에 둠. 프롬프트도 각 단계에 둠
    - 이유: A1은 엔진에 넘길 환자 판단 결과를 만들고, E는 엔진을 통과한 후보 중에서 N개를 고름. 둘 다 엔진 인터페이스와 맞지 않음
    - 두 단계가 함께 쓰는 것: `ports/`의 `LlmClient`, `adapters/`의 vLLM 구현
- **같은 개념은 모든 층에서 1:1로 대응**
    - §1.1 선정 기준 ↔ §3 규칙 엔진 ↔ `engines/` 모듈 ↔ `config/` 활성화 키 ↔ `tests/engines/`

    - 일감의 진행 상태는 PRD에 적지 않음
- **구현 순서:** 개발팀은 구현을 다음 4단계로 나눠 진행한다.
    - 1단계(요청 검증·환자 분류·규칙 엔진): F-01 요청 수신과 검증, F-02 중증·특수 자원 판단, F-03 환자 상태 판단, F-04 중증도 판정과 특수상황 판정, F-05 119구급대 운영지침 규칙 엔진
    - 2단계(병원 조회·규칙 엔진 적용·전체 흐름): F-06 병원정보 조회(병원정보 검색 API 구현 제외), F-07 규칙 엔진 적용과 레벨 진행, F-13 진료 역량 규칙 엔진, F-15 도착시간·거리 규칙 엔진, F-09 최종 선정 fallback, F-10 ETA 계산, F-11 결과 반환
    - 3단계(LLM 최종 선정·ML 모델): F-08 최종 선정, F-14 ML 모델 규칙 엔진
    - 4단계(모델 평가): F-12 모델 평가
    - 개발팀은 최종 선정 fallback을 3단계(LLM 최종 선정)가 아니라 2단계에서 구현한다. 2단계의 전체 흐름 검증에도 병원을 고르는 단계가 필요하기 때문이다.
    - 개발팀은 F-06 병원정보 조회의 병원정보 검색 API 구현을 구현 순서와 별도로 진행한다. 2단계는 mock 구현으로 진행한다.
- **기준 예시: 65세 남성, 발등 개방성 골절, Pre-KTAS 2단계.** 이 환자는 `majorSevereType` 값이 없으므로 중증도 판정(A2)을 거친다. 환자 상태 판단 LLM은 이 환자를 "외상, 정형외과 필수"로 판단한다. 발등 개방성 골절은 신체검사 소견 기준(두 개 이상의 근위부 긴뼈 골절, 압궤·벗겨진·썰린 사지 등)에 해당하지 않는다. Pre-KTAS 평가내용과 비고에 손상기전 기준에 해당하는 내용(예: 6m 이상 추락)이 없으면, LLM은 중증외상 기준 항목을 고르지 않는다. 이 환자는 활력징후가 안정적이고 의식이 명료하므로 생리학적 기준에도 해당하지 않는다. 그래서 시스템은 이 환자에게 경증외상 규칙을 적용한다. 다만 환자가 65세이므로 특수상황의 위험한 나이(55세 이상)에 해당하고, 시스템은 응답에 "직접의료지도 필요" 표시를 넣는다. 진료 역량 규칙 엔진은 정형외과 진료가 불가능한 병원을 후보에서 제거한다. 최종 선정 LLM은 남은 후보 중 가용병상과 정형외과 여건이 더 나은 병원을 직선거리가 가장 짧은 병원보다 앞 순위에 둘 수 있고, 이때 시스템은 그 추천에 우회 표시를 넣는다.

### F-01 요청 수신과 검증

**요구사항**

- 병원선정요청은 환자 정보와 환자 위치를 담아 시스템에 병원 추천을 요청한다. 요청의 형식(필드명, 타입, 필수 여부)은 [interface.md](../10_설계/interface.md)의 '병원 추천 요청' 섹션이 정한다.
- 시스템은 interface.md의 '필수 여부 규칙'대로 요청을 검증한다.
    - 필수 필드의 키가 없거나 `null`을 허용하지 않는 필드의 값이 `null`이면, 시스템은 400을 반환한다. FastAPI는 요청 검증 오류에 기본으로 422를 반환하므로, `main.py`는 검증 오류 처리기를 등록해 400을 반환한다.
    - 시스템은 타입에 `null`이 있거나 '생략 시 처리' 값이 `null`인 필드에만 `null`을 받는다. '생략 시 처리' 값이 `[]`인 optional 필드(`vitalSigns`, `medicalHistory`, `medications`)에 `null`이 오면, 시스템은 400을 반환한다.
    - 시스템은 숫자 필드에 JSON 숫자만 받는다. 숫자 필드에 불리언, 문자열(예: `"65"`), `NaN`, `Infinity`가 오면, 시스템은 400을 반환한다.
    - 명세에 없는 키가 오면, 시스템은 400을 반환한다. 이 규칙은 키 이름의 오타 때문에 필드 값이 기본값으로 바뀌는 것을 막는다.
    - 시스템은 `patientInfo.age`에 소수(예: 생후 6개월 0.5세)도 받는다. interface.md가 이 필드의 타입을 number로 정했기 때문이다.
    - 시스템은 `majorSevereType`에 4대 중증 4종(심정지, 중증외상, 뇌졸중, 심근경색)만 받는다. 다른 값이 오면 시스템은 400을 반환한다. 시스템이 모르는 값을 무시하면 4대 중증 환자를 일반 환자로 분류하기 때문이다.
    - optional 필드의 키가 생략되면, 시스템은 interface.md '생략 시 처리' 열의 값을 그 필드에 넣는다.
    - `specialPatientInfo` 키가 없으면, 시스템은 400을 반환한다. `specialPatientInfo`의 하위 필드 값이 `null`이면, 시스템은 그 하위 필드를 "해당 없음"으로 간주한다.
- 시스템은 검증 오류 응답에 필드 위치(`loc`), 메시지(`msg`), 오류 종류(`type`)만 넣는다. Pydantic 기본 오류의 `input` 항목은 환자 정보가 담긴 요청 본문을 그대로 되돌려 주므로, 시스템은 `input` 항목을 응답에서 뺀다.
- 시스템은 각 입력 필드를 다음과 같이 사용한다.

| 입력 필드 | 시스템이 이 필드를 사용하는 목적 | 처리 방식 |
| --- | --- | --- |
| `majorSevereType` (4대중증구분) | 지침의 환자 분류(심정지, 중증외상, 뇌졸중, 심근경색)를 바로 결정 | 규칙, 다른 필드보다 우선 적용 |
| `preKtas.assessmentDetail` (Pre-KTAS 평가내용) | Pre-KTAS(병원 전 단계 중증도 분류)의 평가 항목 문구. 외상 여부, 필수·보조 진료과, 중증응급질환 코드, 중증외상 기준 항목(신체검사 소견, 손상기전)을 판단하는 데 사용. 사례 집계 키 | LLM 입력 (환자 상태 판단) |
| `preKtas.level` (Pre-KTAS 단계) | 비외상 환자의 중증도 판정 (1~2단계면 중증 후보). 외상 환자는 활력징후 측정값이 없을 때만 중증외상 판정에 사용. 환자 상태 판단 시 참고 | 규칙 + LLM 입력 |
| `vitalSigns` (활력징후) | 중증외상의 생리학적 기준 판정, 환자 상태 판단과 최종 선정 시 참고 | 규칙 + LLM 입력 |
| `consciousnessLevel` (의식상태) | 중증외상 기준 판정, 환자 상태 판단과 최종 선정 시 참고 | 규칙 + LLM 입력 |
| `patientInfo.age` (나이) | 15세 미만이면 소아응급 진료 가능 조건을 진료 역량 규칙 엔진에 추가. 외상 환자가 55세 이상이거나 10세 이하이면 "직접의료지도 필요" 표시(중증외상 지침의 위험한 나이). 환자 상태 판단 시 참고 | 규칙 + LLM 입력 |
| `specialPatientInfo` (특수환자정보) | 임산부면 진료 역량 규칙 엔진이 분만이 가능한 병원에 "분만 가능" 태그를 붙임(병원을 거르지 않음). 임산부 정보(`pregnancyInfo`)는 환자 상태 판단 LLM에도 넣어 임신 20주 이상인지 판단(중증외상 지침의 특수상황). 신생아 정보는 우선 고려하지 않음 | 규칙 (완화 불가 조건) + LLM 입력 |
| `medicalHistory` (과거력), `medications` (투여약물) | 환자 상태 판단 LLM이 진료과와 중증외상 지침의 특수상황(항응고·출혈성 질환, 투석이 필요한 말기신장질환)을 판단할 때, 최종 선정 LLM이 선정 근거를 쓸 때 참고 (예: 당뇨 + 혈당 210 → 감염 위험 언급) | LLM 입력만 |
| `patientLocation` (환자위치, WGS84 경도·위도) | 병원정보 검색 API(직선거리)와 Tmap ETA API(ETA)에 넘김, 사례 집계의 지역 키 | 외부 API 입력 |
| `remark` (비고) | 환자 상태 판단 LLM이 중증외상 기준 항목(손상기전, 신체검사 소견)을 판단할 때, 최종 선정 LLM이 최종 후보, 순위, 추천 사유를 정할 때 참고 (예: 3층 높이에서 추락, 환자가 희망하는 병원). 비고에 적힌 거절 병원은 후보에서 제거하지 않음 | LLM 입력만 |

### F-02 중증·특수 자원 판단

**요구사항**

- 시스템은 요청을 받으면 가장 먼저 환자가 4대 중증에 해당하는지와 환자에게 특수 자원이 필요한지 판단한다. 이 단계에서 시스템은 LLM을 쓰지 않고 입력 필드 값만 본다.
- 입력 필드: `majorSevereType`, `patientInfo.age`, `specialPatientInfo.pregnancyInfo`
- 출력
    - `severe_type`: 4대 중증 구분 (심정지, 중증외상, 뇌졸중, 심근경색 중 하나, 또는 없음)
    - `required_resources[]`: 환자에게 필요한 특수 자원 목록. 목록이 비어 있으면 환자에게 특수 자원이 필요 없다.
- 출력을 쓰는 단계
    - `severe_type` 값이 있으면, 시스템은 중증도 판정(A2)을 건너뛰고 아래 판정 규칙 표의 적용 규칙을 지침 규칙 엔진(B)에 넘긴다.
    - `severe_type` 값이 없으면, 시스템은 중증도 판정(A2)에서 Pre-KTAS 단계와 활력징후로 적용 규칙을 정한다.
    - `severe_type` 값과 관계없이 모든 환자는 환자 상태 판단(A1)을 거친다.
    - 진료 역량 규칙 엔진(C)은 `required_resources[]`의 자원 중 분만을 뺀 자원(뇌경색 재관류중재술 또는 뇌출혈수술, 심근경색 재관류중재술, 소아 응급 진료)을 완화할 수 없는 조건으로 적용한다. 분만은 병원을 거르지 않고 태그로 표시한다([F-13](#f-13-진료-역량-규칙-엔진)의 '분만 자원').
- 시스템은 소아와 임산부 여부로 처리 흐름을 나누지 않는다. 소아와 임산부도 중증일 수 있고 경증일 수 있어서, 시스템은 이 환자들도 Pre-KTAS로 분류해야 한다. 예를 들어 7세 손목 골절 환자에게는 소아 응급 진료 자원이 필요하지만, 시스템은 이 환자에게 경증외상 규칙을 적용한다.

| 판정 근거 | 적용 규칙 | 특수 자원 | 병원 데이터 (병원정보 검색 API 병원 상세) |
| --- | --- | --- | --- |
| `majorSevereType` = 심정지 | 심폐정지 | 없음 | - |
| `majorSevereType` = 중증외상 | 중증외상 | 없음 | - |
| `majorSevereType` = 뇌졸중 | 뇌졸중 | 뇌경색 재관류중재술 또는 뇌출혈수술 (둘 중 하나라도 가능하면 충족) | `acceptanceCapabilities`의 `mkioskty2`(뇌경색 재관류), `mkioskty3`(거미막하출혈 수술), `mkioskty4`(기타 뇌출혈 수술) 중 하나라도 `Y` |
| `majorSevereType` = 심근경색 | 비외상 중증 | 심근경색 재관류중재술 | `acceptanceCapabilities`의 `mkioskty1`(심근경색 재관류)이 `Y` |
| `patientInfo.age` < 15 | - | 소아 응급 진료 | `specialty`에 소아청소년과가 있음. API가 소아 응급실 병상(`hv28`)을 주지 않아 실시간 값이 아니라 진료과 보유로 판정한다 |
| `specialPatientInfo.pregnancyInfo` 값 있음 | - | 분만 | `acceptanceCapabilities`의 `mkioskty16`(분만)이 `Y`이거나, `availableFacilities`의 `hv42`(분만실)가 가용. 병원을 거르지 않고 태그로 표시한다 |

- `acceptanceCapabilities` 값은 `Y`일 때만 조건을 만족한다. `불가능`, `정보미제공`, 항목이 없는 병원은 조건을 만족하지 않는다.
- 이송지침은 심정지 환자를 병원 규모(등급) 조건을 만족하는 병원 중 가장 가까운 병원으로 이송하도록 정한다. 그래서 심정지 행에는 특수 자원이 없다.
- 환자가 적용 규칙 열이 '-'인 행에 해당해도, 시스템은 그 환자의 적용 규칙을 바꾸지 않는다. 이 환자의 적용 규칙은 4대 중증 구분이나 중증도 판정(A2)이 정한다.
- 시스템은 중증외상 환자의 권역외상센터 조건을 특수 자원으로 두지 않는다. 지침은 의료지도를 받으면 지역응급의료센터로 이송하는 것을 허용하므로, 시스템은 이 조건을 지침 규칙 엔진의 병원 등급 조건(L0 권역외상센터, L1 지역응급의료센터)으로 다룬다.
- 병원선정요청이 뇌졸중 선별검사 결과를 보낼 경로가 없으므로, 시스템은 뇌졸중 환자에게 '뇌졸중 의증' 규칙을 적용한다.

**완료조건**

- [ ] 판정 규칙 표의 각 행에 대한 단위 테스트가 있다.
- [ ] 판정 규칙 표의 여러 행에 해당하는 환자에 대한 단위 테스트가 있다(예: 임산부 뇌졸중 환자에게 특수 자원 2개).

### F-03 환자 상태 판단

**요구사항**

- 모든 환자가 이 단계를 거친다. 시스템은 Pre-KTAS 평가 결과, 활력징후, 나이, 비고 같은 환자 정보를 LLM에 넣고, LLM은 환자의 외상 여부, 필수·보조 진료과, 중증응급질환 코드, 중증외상 기준 항목을 판단한다.
- 시스템은 외상 여부와 중증외상 기준 항목을 중증도 판정(A2)과 특수상황 판정에 넘기고, 필수 진료과와 중증응급질환 코드를 진료 역량 규칙 엔진(C)의 조건으로 넘기고, 보조 진료과를 최종 선정(E) LLM의 입력으로 넘긴다.
- 4대 중증 환자도 이 단계를 거친다. 예를 들어 Pre-KTAS 평가내용이 "개방성 골절"인 중증외상 환자에게는 '정형외과 필수' 조건이 붙는다.
- 시스템은 Pre-KTAS 조회 테이블(평가내용 문구별 외상 여부·진료과·중증응급질환 코드를 미리 적어 둔 표)을 쓰지 않고, 요청마다 LLM으로 판단한다. 의료진이 판단 결과를 미리 검토하지 않으므로, 개발팀은 평가셋으로 판단 정확도를 확인한다([F-12 모델 평가](#f-12-모델-평가)).
- 입력: Pre-KTAS 단계·평가내용, 나이, 성별, 주호소, 증상, 의식상태, 활력징후, 과거력, 투여약물, 임산부 정보, 비고
    - 손상기전과 신체검사 소견은 Pre-KTAS 평가내용이나 비고에만 적힐 수 있다. 그래서 시스템은 비고도 LLM 입력에 넣는다.
- 출력

| 항목 | 값 | 쓰는 단계 | 예시 (발등 개방성 골절) |
| --- | --- | --- | --- |
| `is_trauma` (외상 여부) | true 또는 false | 중증도 판정(A2) | true |
| `required_depts` (필수 진료과) | 진료과 목록에서 0개 이상 | 진료 역량 규칙 엔진(C)의 완화할 수 없는 조건 | 정형외과 |
| `supportive_depts` (보조 진료과) | 진료과 목록에서 0개 이상 | 최종 선정(E) LLM 입력 | 성형외과, 혈관외과 |
| `severe_disease_code` (중증응급질환 코드) | `mkioskty1`~`mkioskty27` 중 하나, 또는 null | 진료 역량 규칙 엔진(C)의 완화할 수 없는 조건 | null |
| `trauma_criteria` (중증외상 기준 항목) | "다발성/중증손상" 지침의 신체검사 소견, 손상기전, 특수상황 항목 중 0개 이상. 시스템이 나이로 판정하는 위험한 나이 항목은 뺀다 | 중증도 판정(A2), 특수상황 판정 | 없음 |

- 값 제한: 시스템은 vLLM structured outputs(JSON 스키마)로 LLM이 진료과, 중증응급질환 코드, 중증외상 기준 항목을 정해진 값 목록 안에서만 고르게 한다.
    - 진료과 목록은 「전문의의 수련 및 자격 인정 등에 관한 규정」 제3조가 정한 전문의 전문과목 26개다.
    - 진료과 목록은 병원정보 검색 API가 주는 진료과목(병원 상세의 `specialty`, `/specialties`의 진료과목 명칭)과 같은 이름을 써야 한다. 그래야 진료 역량 규칙 엔진이 두 값을 비교할 수 있다. 그래서 조문과 표기가 다른 두 과는 API 명칭을 쓴다. 조문의 "핵의학"은 "핵의학과"로, "직업환경의학과"는 "작업환경의학과"로 쓴다. API에는 옛 과목명(산업의학과, 치료방사선과, 해부병리과)도 있지만, 지금 전문과목이 아니어서 진료과 목록에 넣지 않는다.
    - 중증응급질환 코드는 병원정보 검색 API 병원 상세의 `acceptanceCapabilities`가 주는 `key` 중 `mkioskty1`~`mkioskty27`이다. API는 `mkioskty28`(응급실)도 주지만, 이 값은 중증응급질환이 아니어서 코드 목록에 넣지 않는다.
    - 중증외상 기준 항목은 [severe-trauma-criteria.md](../90_domain/severe-trauma-criteria.md)의 신체검사 소견, 손상기전, 특수상황 항목이다.
- 개발팀은 출력 스키마를 `domain/`의 환자 상태 판단 결과 Pydantic 모델 하나에서만 만든다. 중증도 판정과 진료 역량 규칙 엔진도 이 모델을 결과 타입으로 받는다.
- 시스템 프롬프트의 지시문: LLM은 Pre-KTAS 평가내용, 주호소, 증상, 비고에 적힌 내용에 해당하는 항목만 고른다. LLM은 적혀 있지 않은 손상기전이나 소견을 추측해 고르지 않는다.
- `classification/`의 환자 상태 판단은 [N-01 프롬프트 관리](#n-01-프롬프트-관리)에 적은 방식으로 system·user 메시지를 만들고 `LlmClient`를 호출한다.
    - `LlmClient`는 OpenAI chat 형식의 메시지 목록(`messages`), 출력 모델(`response_format`), 제한 시간(`timeout`)을 받는다. `LlmClient`는 파싱한 출력과 LLM 원문 출력을 반환하거나, 실패 사유(호출 실패, 검증 실패, 제한 시간 초과, vLLM 대기 요청 초과)를 반환한다. 호출 실패는 연결 오류처럼 vLLM이 응답하지 못한 경우다. 매개변수 이름은 OpenAI SDK의 `chat.completions.parse()`와 같다.
    - 개발팀은 테스트용 가짜 `LlmClient`를 `tests/`에 만든다. 가짜 클라이언트는 테스트 설정에 따라 정상 출력이나 실패 사유를 반환한다.
- 제한 시간: 시스템은 환자 상태 판단 LLM 호출에 3초(임시값)의 제한 시간을 둔다.
- 실패 처리
    - 실패 조건: LLM 호출이 실패함(연결 오류 등), LLM 출력이 스키마 검증을 통과하지 못함, LLM 호출이 제한 시간을 넘김, vLLM 대기 요청 수가 정해진 값을 넘음(이때 시스템은 LLM을 호출하지 않는다)
    - `LlmClient`가 실패 사유를 반환하면, `classification/`의 환자 상태 판단은 결과 없음(`None`)을 반환한다.
    - 중증도 판정(A2)은 환자를 외상 환자로 간주하지 않는다. 중증도 판정은 환자를 비외상 환자로 보고 Pre-KTAS 단계와 비외상 임계치로 판정한다.
    - 특수상황 판정은 4대 중증 구분이 중증외상인 환자에게만 위험한 나이 항목을 판정한다.
    - 진료 역량 규칙 엔진(C)은 필수 진료과 조건과 중증응급질환 조건을 적용하지 않는다.
    - 시스템은 응답에 "환자 상태 판단 실패" 경고를 넣는다.

**완료조건**

- [ ] 발등 개방성 골절 예시로 만든 메시지를 기대 파일과 비교하는 테스트가 있다.
- [ ] LLM 입력 객체에 비고와 임산부 정보가 들어가는지 확인하는 테스트가 있다.
- [ ] 가짜 클라이언트가 실패 사유를 반환하면, 실패 사유마다 결과 없음과 "환자 상태 판단 실패" 경고가 나오는지 확인하는 테스트가 있다.
- [ ] 출력 모델이 목록 밖의 중증외상 기준 항목을 거부하는지 확인하는 테스트가 있다.
- [ ] 환자 상태 판단 LLM 호출 실패를 일부러 일으키면, 시스템이 필수 진료과 조건과 중증응급질환 조건 없이 "환자 상태 판단 실패" 경고와 함께 응답한다.

### F-04 중증도 판정과 특수상황 판정

**요구사항**

- 4대 중증이 아닌 환자(중증·특수 자원 판단(A0)에서 `severe_type` 값이 없는 환자)만 중증도 판정을 거친다. `pipeline.py`는 이 환자에게만 `severity.judge`를 호출한다.
- 외상 환자: 시스템은 "다발성/중증손상" 지침([severe-trauma-criteria.md](../90_domain/severe-trauma-criteria.md))의 기준 중 하나라도 해당하면 환자를 중증외상으로 판정한다.
    - 생리학적 기준: 시스템은 활력징후와 의식상태로 판정한다. 기준은 의식상태 V(언어 반응) 이하, 수축기혈압 90mmHg 미만, 호흡수 분당 10회 미만 또는 29회 초과다.
        - 시스템은 `consciousnessLevel` 값이 `명료`가 아니면 의식상태를 V 이하로 간주한다. 값이 없으면, 시스템은 의식상태 기준을 적용하지 않는다.
        - 요청에 GCS(글라스고우 혼수척도)가 없으므로, 시스템은 GCS 기준을 쓰지 않는다.
        - 지침에 산소포화도 기준이 없으므로, 시스템은 외상 환자의 판정에 산소포화도를 쓰지 않는다.
    - 신체검사 소견 기준과 손상기전 기준: 환자 상태 판단 결과의 중증외상 기준 항목에 이 두 분류의 항목이 하나라도 있으면, 시스템은 환자를 중증외상으로 판정한다. 시스템은 특수상황 항목을 중증외상 판정에 쓰지 않는다.
        - 요청에는 이 기준들의 정형 필드가 없고, 병원선정요청은 입력 필드를 바꾸지 않는다. 그래서 LLM은 Pre-KTAS 평가내용, 주호소, 증상, 비고에 적힌 내용으로만 판단한다. 텍스트에 내용이 적혀 있지 않으면, 시스템은 생리학적 기준만으로 판정한다.
        - 그래서 시스템은 손상기전 정보가 없는 중증외상 환자(예: 6m 높이에서 추락했지만 활력징후가 정상이고 비고에 추락 높이가 없는 환자)를 경증외상으로 분류할 수 있다.
    - 수축기혈압과 호흡수 측정값이 하나도 없으면, 시스템은 Pre-KTAS 1~2단계인 외상 환자도 중증외상으로 판정한다.
    - 환자 상태 판단 결과가 없으면, 시스템은 환자를 외상 환자로 간주하지 않고 아래 비외상 환자의 기준으로 판정한다.
- 비외상 환자: 시스템은 Pre-KTAS 단계(1~2단계면 중증)와 비외상 임계치로 각각 중증도를 판정하고, 두 판정이 다르면 더 중증인 쪽을 택한다.
- 시스템은 외상 여부와 중증도로 적용 규칙(중증외상, 경증외상, 비외상 중증, 비외상 경증)을 정해 지침 규칙 엔진(B)에 넘긴다.
- **판정이 갈리면 시스템은 더 중증인 쪽을 택한다.** 개발팀은 활력징후 임계치를 "측정값이 이 값을 넘으면 중증으로 판정한다"는 조건으로 규칙 설정 파일에 작성한다.
    - 외상 환자의 임계치(수축기혈압, 호흡수, 의식 수준)는 "다발성/중증손상" 지침의 값이다.
    - 비외상 환자의 임계치는 임시값이다: 수축기혈압 90mmHg 미만, 산소포화도 90% 미만, 의식상태가 "명료"가 아님.
    - 시스템은 요청에서 활력징후 기록을 한 건만 받는다.
    - 의식상태는 `vitalSigns`와 별개인 필수 필드다. 그래서 `vitalSigns`가 `null`이어도 시스템은 의식상태로 중증도를 판정한다.
- 요청의 `preKtas`에는 Pre-KTAS 평가 결과가 한 건만 들어간다. `preKtas.assessmentRound`는 그 평가의 차수다. 평가를 여러 차례 했을 때 병원선정요청이 어느 차수의 결과를 보내는지는 정해지지 않았다([§8 결정 필요](#8-결정-필요)의 'Pre-KTAS 평가 차수').
- **특수상황 판정:** 적용 규칙이 중증외상이나 경증외상인 환자(4대 중증 구분이 중증외상인 환자 포함)가 "다발성/중증손상" 지침의 '의학적 질병상태 및 특수상황'에 해당하면, 시스템은 응답에 "직접의료지도 필요" 표시와 해당 항목을 넣는다.
    - 지침은 이 환자의 이송병원을 직접의료지도로 정하라고 규정한다. 시스템은 추천을 그대로 반환하고 표시만 넣는다. 직접의료지도 절차는 시스템의 범위 밖이다.
    - 위험한 나이(55세 이상, 10세 이하): 시스템은 `patientInfo.age`로 판정한다.
    - 나머지 항목(항응고·출혈성 질환, 화상과 외상 동반, 투석이 필요한 말기신장질환, 시간 지연에 민감한 사지 손상, 임신 20주 이상, 구급대원의 판단): 시스템은 환자 상태 판단 결과의 중증외상 기준 항목 중 특수상황 항목을 가져온다. 환자 상태 판단 결과가 없으면, 시스템은 위험한 나이만 판정한다.
    - `pipeline.py`는 4대 중증 환자에게도 특수상황 판정을 호출한다. 4대 중증 구분이 중증외상인 환자는 중증도 판정을 건너뛰지만 특수상황 판정의 대상이기 때문이다.

**완료조건**

- [ ] Pre-KTAS 단계는 경증인데 활력징후가 임계치를 넘으면, 시스템이 중증으로 판정하는지 확인하는 테스트가 있다.
- [ ] 시스템이 발등 개방성 골절 예시를 경증외상으로 판정하고, 특수상황 항목으로 위험한 나이를 반환하는지 확인하는 테스트가 있다.
- [ ] Pre-KTAS 3~5단계 외상 환자도 외상 임계치를 넘으면, 시스템이 중증외상으로 판정하는지 확인하는 테스트가 있다(호흡수 10회 미만, 29회 초과 각각).
- [ ] 외상 환자의 산소포화도가 90% 미만이어도 다른 기준에 해당하지 않으면, 시스템이 경증외상으로 판정하는지 확인하는 테스트가 있다.
- [ ] 활력징후가 정상이어도 신체검사 소견이나 손상기전 항목이 있으면 중증외상으로, 특수상황 항목만 있으면 경증외상으로 시스템이 판정하는지 확인하는 테스트가 있다.
- [ ] 환자 상태 판단 결과가 없으면, 시스템이 환자를 비외상 환자의 기준으로 판정하는지 확인하는 테스트가 있다.
- [ ] 특수상황 판정 테스트가 있다: 나이 경계값(10, 10.5, 54.9, 55), 적용 규칙이 비외상이면 빈 목록 반환, 4대 중증 구분이 중증외상인 환자의 판정.

### F-05 119구급대 운영지침 규칙 엔진

**요구사항**

- 지침은 환자 분류에 따라 병원의 최소 등급을 정하고, 그 등급 이상인 병원 중 가장 가까운 병원으로 이송하라고 규정한다. 규칙 엔진은 이 기준을 설정 파일로 표현하므로, 지침이 개정되면 개발팀은 코드 대신 설정 파일만 수정한다.
- 규칙 엔진은 환자 분류만 입력으로 받는다. 시스템은 환자 위치의 지역을 판별하지 않으므로, 개발팀은 지역에 따라 달라지는 지침을 나중에 추가한다([§1.3 범위 밖](#13-범위-밖)의 '나중에 추가할 항목').

| 환자 분류 | L0 원칙 조건 | L1 완화 조건 (의료지도 필요) |
| --- | --- | --- |
| 중증외상 | 가장 가까운 권역외상센터 (시·도와 관계없음) | 지역응급의료센터 |
| 경증외상 | 가장 가까운 지역응급의료기관 | 없음 |
| 비외상 중증 | 지역응급의료센터 이상 | 지역응급의료기관 |
| 비외상 경증 | 가장 가까운 지역응급의료기관 | 없음 |
| 심폐정지 | 가장 가까운 지역응급의료기관 이상 | 없음 |
| 뇌졸중 의증 | 지역응급의료센터 이상 | 지역응급의료기관 |
| 뇌졸중 선별검사 양성 | 즉시 혈전용해 치료가 가능한 지역응급의료기관 이상 | 지역응급의료기관 |

- 이 규칙 엔진은 후보 병원 중 레벨의 병원 등급 조건을 만족하지 않는 병원을 제거한다. 레벨이 L0에서 L1로 내려가면 병원 등급 조건도 낮아진다.
- 표의 "가장 가까운"은 이 규칙 엔진의 조건이 아니다. 등급 조건을 만족한 병원 사이의 순위는 최종 선정 LLM이 정하고, 최종 선정 LLM은 직선거리를 보조 기준으로 쓴다.
- 시스템은 지침의 "권역외상센터가 지정되지 않은 지역은 지역응급의료센터 이상" 조항을 적용하지 않는다. 시스템은 시·도와 관계없이 가장 가까운 권역외상센터를 찾는다. 거리 상한이 없으므로, 권역외상센터가 먼 지역에서도 중증외상 환자의 L0 후보는 권역외상센터뿐이다.
- 시스템은 비고에서 뇌졸중 선별검사 결과를 추출하지 않는다. 병원선정요청이 선별검사 결과를 보낼 경로가 정해지기 전까지, 규칙 엔진은 뇌졸중 환자에게 '뇌졸중 의증' 규칙을 적용한다.
- 개발팀은 분류별 규칙 표의 7행을 설정 파일(`config/transfer_rules.yaml`)에 작성한다. 각 행은 적용 규칙, L0 병원 등급 조건, L1 병원 등급 조건(없으면 비움)을 가진다.
- 개발팀은 레벨마다 병원 등급 조건을 허용하는 병원 분류(`HospitalCategory`) 목록으로 적는다. 예: "지역응급의료센터 이상" = 권역응급의료센터, 지역응급의료센터
    - 병원 분류는 권역응급의료센터, 지역응급의료센터, 지역응급의료기관, 권역외상센터 4종이다. 병원 하나가 여러 분류에 속할 수 있다(예: 권역응급의료센터이면서 권역외상센터). 전문응급의료센터는 소아, 화상처럼 특정 환자군만 맡으므로 병원 분류에 넣지 않는다.
    - 지침 문구에 "이상"이 없는 조건(예: 경증외상의 "지역응급의료기관")은 그 등급만 허용한다.
    - 뇌졸중 선별검사 양성 규칙의 "즉시 혈전용해 치료 가능" 조건에 해당하는 필드가 병원 데이터에 없다. 그래서 개발팀은 이 규칙에 등급 목록만 적는다.
- 설정 파일에는 버전 필드가 있다. 시스템은 응답의 적용 규칙 정보에 이 버전을 넣는다.
- `engines/guideline`은 앱 시작 시 설정 파일을 읽고 형식을 검사한다(필수 키 누락, 정의되지 않은 병원 분류). 설정 파일의 형식이 틀리면 앱이 기동되지 않는다.
- `engines/guideline`은 적용 규칙을 받아 [L0 조건, L1 조건] 목록을 반환한다. 레벨 진행은 `pipeline.py`가 맡는다([F-07 규칙 엔진 적용과 레벨 진행](#f-07-규칙-엔진-적용과-레벨-진행), [§8 결정 필요](#8-결정-필요)의 '레벨 진행 루프 위치').

**완료조건**

- [ ] 분류별 규칙 표의 각 행에 대한 단위 테스트가 있다.
- [ ] 레벨마다 병원 등급 조건을 만족하지 않는 mock 병원이 제거되는지 확인하는 테스트가 있다.
- [ ] 형식이 틀린 설정 파일을 읽으면 `engines/guideline`이 실패하는지 확인하는 테스트가 있다.

### F-06 병원정보 조회

**요구사항**

- 시스템은 `HospitalRepository`로 병원 정보를 조회한다. 운영 구현은 병원정보 검색 API를 호출하고, 테스트와 구현 초기에는 mock 구현을 쓴다.
- 시스템은 시·도 구분 없이 병원을 조회한다. 병원정보 검색 API는 병원마다 환자 위치에서의 직선거리를 함께 준다. 규칙 엔진(C)과 최종 선정(E)이 이 데이터를 쓴다.
- 시스템은 환자 위치의 시·도를 판별하지 않는다. 시스템은 직선거리로 가까운 병원을 고르므로, 지침의 "타 시·도 권역외상센터가 더 가까우면 그곳으로 이송할 수 있다"는 조항은 별도 처리 없이 지켜진다.
- `HospitalRepository`는 환자 위치와 병원 분류 목록을 받아, 그 분류 중 하나 이상에 속하는 병원을 시·도 구분 없이 반환한다. `pipeline.py`는 적용 규칙의 L0 조건과 L1 조건에 나오는 병원 분류를 합쳐 한 번만 조회하고, 조회한 목록 안에서 레벨을 진행한다.
- `domain/`의 `Hospital`은 병원의 진료과를 환자 상태 판단 결과와 같은 진료과 열거형으로 나타낸다. 그래야 진료 역량 규칙 엔진이 두 값을 비교할 수 있다.
- 병원정보 검색 API의 접속 정보, 검색 조건, 응답 필드는 [interface_hospital_api.md](../10_설계/interface_hospital_api.md)에 있다. 운영 구현은 응급실 목록(`/emergency-rooms`)을 환자 위치·반경·응급의료기관 등급으로 조회하고, 후보 병원마다 병원 상세(`/{id}`)를 호출한다. 아래 표는 규칙 엔진과 최종 선정이 쓰는 데이터와 그 API 필드다.

| 데이터 | 쓰는 곳 | API 필드 |
| --- | --- | --- |
| 응급의료기관 등급, 진료과목, 병원 좌표 | 119구급대 운영지침 규칙 엔진의 병원 등급 조건, 진료 역량 규칙 엔진의 필수 진료과 조건 | 응급실 목록의 `type`, 병원 상세의 `specialty`, `coordinates`(`[경도, 위도]`) |
| 권역외상센터 지정 여부 | 119구급대 운영지침 규칙 엔진의 병원 등급 조건 (권역외상센터) | API에 없다. 시스템은 `config/trauma_centers.yaml`의 hpid 목록으로 정한다. API의 응급의료기관 등급은 권역외상센터 지정과 관계없다 |
| 환자 위치에서의 직선거리 | 도착시간·거리 규칙 엔진, 우회 판정, 최종 선정 fallback | 응급실 목록의 `distance`(km). 요청의 `longitude`·`latitude`에서 병원까지의 거리다 |
| 응급실·중환자실 가용병상, 갱신 시각 | 진료 역량 규칙 엔진의 가용병상 조건, 실시간 데이터 신선도 판정, 최종 선정 | 병원 상세의 `availableBeds`(응급실 `hvec`, 중환자실 `hvicc`·`hvcc`·`hvccc`·`hvncc`), `lastUpdatedAt`. 소아 응급실(`hv28`) 등 나머지 병상 종류는 API에 없다 |
| 중증질환 수용가능 여부 | 진료 역량 규칙 엔진의 중증응급질환·특수 자원 조건, 최종 선정 | 병원 상세의 `acceptanceCapabilities`(`key` `mkioskty1`~`mkioskty28`, `value` `Y`·`불가능`·`정보미제공`) |
| 응급실·중증질환 진료불가 메시지 | 진료 역량 규칙 엔진의 필수 진료과 조건, 최종 선정 | 병원 상세의 `statusMessages`, `publicStatusMessages`. 병원이 등록한 메시지 중 지금 활성화된 것을 모두 주고, 원소는 정해진 구조 없는 자연어 문장이다. 그래서 진료과나 중증질환 코드를 필드로 읽을 수 없고, 진료 역량 규칙 엔진은 LLM으로 메시지가 막는 진료과를 판단한다([F-13](#f-13-진료-역량-규칙-엔진)의 '진료불가 메시지') |

- 주의: API의 `mkioskty` 키는 중증질환환자수용가능정보 기준이다(예: `mkioskty1` = 심근경색 재관류). [erd_hospital.mmd](../10_설계/erd_hospital.mmd)의 응급의료기관기본정보조회에는 같은 이름에 다른 뜻의 컬럼이 있다(`mkioskty1` = 뇌출혈수술). 그래서 ERD 컬럼과 API 키를 섞어 쓰지 않는다.
- 개발팀은 mock 병원 데이터(`tests/`)를 다음과 같이 만든다.
    - 개발팀은 예시 환자 위치(경도 128.5911, 위도 35.8714) 주변 병원 15곳 정도를 넣는다.
    - 개발팀은 규칙 엔진의 조건마다 그 조건으로 제거되는 병원을 1곳 이상 넣는다.
    - 개발팀은 다른 시·도의 권역외상센터와 병상 데이터가 오래된 병원을 넣는다.
    - 개발팀은 병원마다 예시 환자 위치에서의 직선거리를 넣는다.

**완료조건**

- [ ] mock 데이터에 규칙 엔진 조건마다 제거 대상 병원이 있는지 확인하는 테스트가 있다.
- [ ] mock 구현에 쓴 인터페이스 테스트를 병원정보 검색 API 구현도 통과한다.

### F-07 규칙 엔진 적용과 레벨 진행

**요구사항**

- 시스템은 [§1.1](#11-배경)의 이송병원 선정 기준 네 가지를 규칙 엔진 네 개로 적용한다.
    - [F-05 119구급대 운영지침 규칙 엔진](#f-05-119구급대-운영지침-규칙-엔진)
    - [F-13 진료 역량 규칙 엔진](#f-13-진료-역량-규칙-엔진)
    - [F-14 ML 모델 규칙 엔진](#f-14-ml-모델-규칙-엔진)
    - [F-15 도착시간·거리 규칙 엔진](#f-15-도착시간거리-규칙-엔진)
- **공통 인터페이스:** 모든 규칙 엔진은 같은 인터페이스를 따른다.
    - 입력: 후보 병원 목록, 환자 판단 결과(4대 중증 구분, 특수 자원 목록, 환자 상태 판단 결과, 적용 규칙), 레벨
    - 출력: 걸러낸 후보 병원 목록, 또는 순위용 정보를 붙인 후보 병원 목록
    - ML 모델 규칙 엔진과 도착시간·거리 규칙 엔진이 병원을 걸러내는지는 정해지지 않았다([§8 결정 필요](#8-결정-필요)의 '규칙 엔진의 통과 조건').
- **활성화:** 개발팀은 엔진마다 활성화 여부를 `config/settings.yaml`에 적는다. `pipeline.py`는 활성화된 엔진만 호출한다.
- **호출 순서:** `pipeline.py`는 레벨마다 병원을 걸러내는 엔진을 먼저 호출하고, 순위용 정보를 붙이는 엔진을 나중에 호출한다.
- **레벨 진행:** L0 조건으로 후보 병원이 0곳이면, `pipeline.py`는 L1 조건으로 규칙 엔진을 다시 실행하고 결과에 "의료지도 필요" 표시를 넣는다. L1 조건으로도 후보 병원이 0곳이거나 적용 규칙에 L1 조건이 없으면, 시스템은 병원을 추천하지 않고 응답한다(직접의료지도 요청은 범위 밖 — [§1.3 범위 밖](#13-범위-밖)).

```text
레벨 진행 (규칙 엔진 결과가 0곳이면 다음 레벨 조건으로 규칙 엔진을 다시 실행)

  L0 원칙 조건 ──후보 0곳──▶ L1 완화 조건
       │                         │
       ▼                         ▼
  추천 반환              추천 반환 +
                         "의료지도 필요" 표시
```

**완료조건**

- [ ] 활성화하지 않은 엔진을 `pipeline.py`가 호출하지 않는지 확인하는 테스트가 있다.
- [ ] L0 조건으로 후보 병원이 0곳이면, 시스템이 L1 조건의 후보 병원을 "의료지도 필요" 표시와 함께 추천한다.
- [ ] L1 조건으로도 후보 병원이 0곳이면, 시스템이 병원을 추천하지 않는다.

### F-13 진료 역량 규칙 엔진

**요구사항**

- 이 규칙 엔진은 병원정보 검색 API로 파악한 병원의 진료 역량을 기준으로, 조건에 맞지 않는 병원을 코드로 제거한다. 이 엔진은 다음 조건을 적용한다.

| 조건 | 적용 대상 환자 | 레벨이 내려갈 때 조건을 낮출 수 있는지 |
| --- | --- | --- |
| 해당 질환의 중증응급질환 수용가능 = Y | 중증응급질환 코드가 있는 환자 | 낮추지 않음 |
| 필수 진료과 보유 + 해당 진료과의 실시간 진료불가 메시지 없음 | 필수 진료과가 있는 환자 | 낮추지 않음 |
| 특수 자원 보유 (중증·특수 자원 판단(A0)의 `required_resources[]` 중 분만을 뺀 자원. 병원 데이터는 [F-02](#f-02-중증특수-자원-판단)의 판정 규칙 표) | 뇌졸중, 심근경색, 소아 환자 | 낮추지 않음 |
| 응급실 가용병상 > 0 | 심폐정지를 제외한 모든 환자 | 낮추지 않음 |
| 중환자실 가용병상 > 0 | 중증 환자 (적용 여부는 설정 항목, 의료진 확인 필요) | 설정에 따름 |

- **심폐정지 환자:** 이 규칙 엔진은 심폐정지 환자에게 조건을 적용하지 않는다. 심폐정지 환자에게는 119구급대 운영지침 규칙 엔진의 병원 등급 조건만 적용된다. 이송지침은 심정지 환자를 병원 규모(등급) 조건을 만족하는 병원 중 가장 가까운 병원으로 이송하도록 정하기 때문이다.
- **환자 상태 판단이 실패한 경우:** 이 규칙 엔진은 중증응급질환 수용가능 조건과 필수 진료과 조건을 적용하지 않는다.
- **진료불가 메시지:** 필수 진료과 조건의 "해당 진료과의 실시간 진료불가 메시지 없음"은 LLM이 판단한다. 메시지는 병원이 쓴 자유 문장이라 진료과 필드가 없기 때문이다([er-block-messages.md](../90_domain/er-block-messages.md)).
    - 이 규칙 엔진은 필수 진료과가 있는 환자에게만 LLM을 호출한다. 다른 조건을 통과한 후보 병원에 메시지가 하나도 없으면 호출하지 않는다.
    - LLM 입력은 남은 후보 병원의 메시지 문장(여러 병원의 같은 문장은 한 번), 환자의 필수 진료과, 조회 시각(요일과 평일·주말 구분 포함), 진료과 목록이다. "평일 9A~6P만 가능"처럼 시간대로 제한하는 메시지가 있어서 조회 시각을 넣는다. 공휴일인지는 LLM이 알 수 없다.
    - LLM은 필수 진료과 중 하나라도 지금 진료할 수 없다고 알리는 메시지를 고르고, 고른 메시지의 번호만 출력한다. 진료할 수 있다고 알리는 메시지, 특정 시술·수술·입원·중증질환·세부 분과·나이만 제한하는 메시지, 응급실 전체에 대한 메시지, 진료과를 알 수 없는 메시지는 고르지 않는다. 중증질환 수용 여부는 중증응급질환 수용가능 조건이 따로 확인한다.
    - 이 규칙 엔진은 LLM이 고른 메시지가 하나라도 있는 병원을 뺀다.
    - LLM 호출이 실패하거나 제한 시간(`config/settings.yaml`의 `block_message_timeout_seconds`, 임시값 3초)을 넘기면, 이 규칙 엔진은 메시지로 병원을 빼지 않고 경고도 넣지 않는다.
    - 필수 진료과만 묻고 메시지 번호만 받는 이유: LLM이 메시지마다 막힌 진료과를 출력하면 출력이 메시지 수만큼 길어진다. 2026-10-30 개발서버 수원 후보의 메시지로 로컬 vLLM을 잰 결과는 다음과 같다. 29문장은 메시지마다 출력하면 3초를 넘겼다. 194문장은 진료과를 고른 메시지만 출력해도 3.6~7.0초 걸렸고, 진료과를 번호로 고르게 해도 4.7~4.9초였다. 필수 진료과만 묻고 막힌 메시지 번호만 받자 194문장이 0.4~0.9초 걸렸다.
- **분만 자원:** 환자에게 분만 자원이 필요하면, 이 규칙 엔진은 분만이 가능한 병원(F-02 판정 규칙 표의 분만 행)에 "분만 가능" 태그를 붙이고 병원을 거르지 않는다.
    - 최종 선정은 "분만 가능" 태그를 LLM 입력에 넣는다. LLM은 이 태그를 참고해 순위를 정한다.
    - 분만을 조건으로 거르지 않는 이유: 중증·특수 자원 판단(A0)은 임산부 정보가 있는 모든 환자에게 분만 자원을 붙인다. 그런데 경증외상과 비외상 경증 환자의 병원 등급 조건은 지역응급의료기관뿐이고 L1 조건이 없다. 2026-10-30 개발서버에서 경기도 지역응급의료기관 31곳을 조회했을 때 `mkioskty16`이 `Y`인 병원은 2곳, 분만실이 가용인 병원은 3곳이었다. 그래서 분만을 조건으로 거르면 경증 임산부 환자는 대부분 추천을 받지 못한다.
    - 이 규칙 엔진은 심폐정지 환자에게 이 태그도 붙이지 않는다.
- **실시간 데이터가 오래된 경우:** 시스템은 병원 데이터에 병원별 병상 데이터 갱신 시각(`beds_updated_at`, API 병원 상세의 `lastUpdatedAt`)을 담는다. 병원정보를 조회한 시각과 이 갱신 시각의 차이가 신선도 임계치보다 크거나 갱신 시각이 없으면, 이 규칙 엔진은 그 병원에 "병상 정보 오래됨" 태그를 붙인다. 병원의 갱신 시각은 하나뿐이므로 태그는 응급실 병상과 중환자실 병상에 함께 적용된다.
    - 이 규칙 엔진은 태그가 붙은 병원의 병상 값을 바꾸지 않고 그대로 둔다. 그리고 그 병원에는 가용병상 조건(응급실, 중환자실)을 적용하지 않는다. 그래서 오래된 병상 값이 0이어도 그 병원은 후보에 남는다.
    - 최종 선정은 태그가 붙은 병원의 병상 값을 태그와 함께 LLM 입력에 넣는다. LLM은 그 병상 값이 지금과 다를 수 있다는 점을 참고해 순위를 정한다.
    - 시스템은 응답에 "병상 정보 오래됨" 경고를 넣는다.
    - 신선도 임계치는 `config/settings.yaml`의 `bed_data_max_age_minutes`(분 단위)이고, 15분으로 둔다. 2026-10-30 개발서버에서 전국 응급실 414곳을 조회했을 때 병원의 99%는 갱신 시각이 조회 시각보다 6~16분 앞섰다(중앙값 9분). 그래서 임계치를 10분으로 두면 정상적으로 갱신되는 병원의 36%가 오래됨으로 판정되고, 15분이면 2%가 판정된다.

**완료조건**

- [ ] 조건마다 mock 데이터의 제거 대상 병원이 후보에서 제거되는지 확인하는 테스트가 있다.
- [ ] 이 규칙 엔진이 심폐정지 환자에게 조건을 적용하지 않는지 확인하는 테스트가 있다.
- [ ] 환자 상태 판단 결과가 없으면 이 규칙 엔진이 중증응급질환 조건과 필수 진료과 조건을 적용하지 않는지 확인하는 테스트가 있다.
- [ ] 진료불가 메시지 판단 LLM이 필수 진료과를 고른 병원은 빠지고, LLM 호출이 실패하면 메시지로 병원을 빼지 않는지 확인하는 테스트가 있다.
- [ ] 이 규칙 엔진이 병상 값이 오래된 병원에 "병상 정보 오래됨" 태그를 붙이고, 병상 값을 바꾸지 않으며, 그 병원을 후보에 남기는지 확인하는 테스트가 있다.

**요구사항**

- [ ] ML 모델 호출 실패를 일부러 일으키면, 시스템이 ML 모델의 병원 후보 없이 "ML 모델 호출 실패" 경고와 함께 응답한다.

### F-08 최종 선정

**요구사항**

1. 시스템은 도착시간·거리 규칙 엔진([F-15](#f-15-도착시간거리-규칙-엔진))이 고른 상위 M개(10~15개) 병원의 데이터를 LLM 프롬프트에 넣는다. LLM 입력 객체는 다음을 담는다.
    - 환자 상태: 나이, 성별, 주호소, 증상, 의식상태, 활력징후, 과거력, 투여약물, Pre-KTAS 평가 결과
    - 환자 상태 판단 결과: 외상 여부, 필수·보조 진료과. 환자 상태 판단이 실패했으면 시스템은 이 키를 넣지 않는다.
    - 적용 규칙과 레벨
    - 직선거리 상위 M개 후보: 병원 ID, 병원명, 등급, 직선거리, 가용병상, 중증질환 수용가능, 진료불가 메시지
    - 비고 원문: 비고가 비어 있거나 생략되면 시스템은 비고 키를 넣지 않는다.
    - ML 모델이 추천한 병원 후보: 참고 정보. ML 모델 호출이 실패했거나 ML 모델 규칙 엔진이 비활성화되어 있으면 시스템은 이 키를 넣지 않는다.
2. LLM은 병원 N개를 고르고 순위를 정한 뒤, 병원마다 구조화된 추천 사유를 출력한다: `reasons: [{type: rule|realtime|remark, ref, text}]`.
    - LLM은 순위를 정할 때 가용병상, 진료과 같은 조건을 직선거리보다 우선하고, 직선거리를 보조 기준으로 쓴다. 심폐정지 환자는 예외다.
    - `type`은 추천 사유의 출처(규칙, 실시간 데이터, 비고)다.
    - `ref`는 그 추천 사유가 가리키는 입력 데이터의 항목이다. 프롬프트는 LLM이 `ref`를 LLM 입력 객체 안의 경로(예: `candidates.<병원ID>.er_beds`)로 쓰게 한다. `type`이 `remark`이면 `ref`는 비고 원문에서 인용한 문구다.
    - 출력 모델(`selection/`)은 추천 병원마다 병원 ID, 순위, 추천 사유 목록을 담는다. LLM은 1순위 병원이 우회일 때 우회 사유 필드를 채운다. 출력 모델은 우회 사유 값을 가용병상 여건, 진료과 적합성, 환자 희망, 거절 이력 4개로 제한한다.
3. 시스템은 LLM 출력을 검증한다. `LlmClient`가 스키마를 검사하고, `selection/`의 출력 검증은 파싱된 출력만 받아 다음을 확인한다.
    - 병원 ID: 병원 ID가 LLM 입력 객체의 후보 목록에 있고, 중복이 없고, 개수가 N개인지
    - 우회 규칙: 우회이면 우회 사유가 있는지, 심폐정지 환자의 추천이 우회가 아닌지
    - 추천 사유 `ref`: LLM 입력 객체에 그 경로가 있는지. `type`이 `remark`면 인용 문구가 비고 원문에 있는지
4. 검증 실패, 제한 시간 초과, vLLM 대기 요청 초과 중 하나가 생기면, 시스템은 최종 선정 fallback으로 응답한다([F-09 최종 선정 fallback](#f-09-최종-선정-fallback)).
5. LLM 출력이 검증을 통과하면, 시스템은 `selection/`의 우회 판정 결과를 우회 표시로 넣어 응답한다.

- **우회 판정 기준:** 시스템은 1순위 병원의 직선거리가 후보 중 직선거리가 가장 짧은 병원보다 X km 넘게 멀 때만 우회로 판정한다. 직선거리 차이가 X km 이하면 시스템은 우회로 판정하지 않는다. 직선거리는 실제 이동 거리와 차이가 크기 때문에 시스템은 이 기준을 둔다. X 값은 정해지지 않았다([§8 결정 필요](#8-결정-필요)의 '설정값').
    - 시스템은 심폐정지 환자를 제외한 모든 환자(중증 환자 포함)에게 우회를 허용한다. 지침이 심폐정지 환자에게 "가장 가까운" 병원을 요구하므로, 시스템은 심폐정지 환자의 우회를 금지한다.
    - LLM은 우회 사유를 가용병상 여건, 진료과 적합성, 환자 희망, 거절 이력 중에서만 고를 수 있다.
- **비고 처리:** 시스템은 비고에 적힌 거절 병원을 후보에서 제거하지 않는다.
- **제한 시간:** 시스템은 최종 선정 LLM 호출에 5초(예시값)의 제한 시간을 둔다. 환자 상태 판단의 제한 시간 3초를 더하면, 시스템이 응답하기까지 최대 약 8초가 걸린다.
- **vLLM 연동:** 환자 상태 판단, 진료불가 메시지 판단, 최종 선정은 `adapters/`의 LangChain 기반 vLLM 구현을 함께 쓴다.
    - 이 구현은 `ChatOpenAI`에 vLLM 주소, 모델 이름, `temperature=0`, 제한 시간, `max_retries=0`을 지정한다. `max_retries`를 0으로 두지 않으면 재시도 때문에 호출이 제한 시간을 넘길 수 있다. 이 구현은 호출하는 단계마다 `config/settings.yaml`의 제한 시간 값을 쓴다.
    - 이 구현은 `with_structured_output(출력 모델, method="json_schema", include_raw=True)`로 구조화 출력을 요청한다. `include_raw=True`는 나중에 감사 로그에 저장할 LLM 원문 출력을 보존한다. LangChain이 파싱에 실패하면(`parsing_error` 값이 있으면), 이 구현은 실패 사유 '검증 실패'를 반환한다.
    - 이 구현은 LLM 호출 전에 vLLM `/metrics`의 `vllm:num_requests_waiting` 값을 읽는다. 값이 상한을 넘으면, 이 구현은 LLM을 호출하지 않고 실패 사유 '대기 요청 초과'를 반환한다. 이 규칙은 다수사상자 사고처럼 요청이 몰리는 상황에 대비한다.

**완료조건**

- [ ] 비고가 비어 있으면 LLM 입력 객체에 비고 키가 없는지 확인하는 테스트가 있다.
- [ ] 출력 검증의 검증 항목마다 실패 사례 테스트가 있다.

### F-09 최종 선정 fallback

**요구사항**

- 최종 선정 LLM 출력이 검증을 통과하지 못하거나, LLM 호출이 실패하거나 제한 시간을 넘기거나, vLLM 대기 요청 수가 상한을 넘으면, 시스템은 최종 선정 fallback으로 응답한다.
- 최종 선정 fallback은 후보 병원을 직선거리 순으로 정렬해 N개를 고른다.
- 최종 선정 fallback은 병원마다 정해진 문장 틀로 추천 근거를 만든다.
    - 문장 틀에는 규칙 ID, 직선거리, 응급실 가용병상 수가 들어간다. 예: "지역응급의료센터 이상 조건 충족, 직선거리 4.2km, 응급실 가용병상 4"
    - 병원에 "병상 정보 오래됨" 태그가 있으면, 최종 선정 fallback은 병상 수 뒤에 "(병상 정보 오래됨)"을 붙인다. 예: "응급실 가용병상 4(병상 정보 오래됨)"
- 최종 선정 fallback은 최종 선정 fallback 사유(호출 실패, 검증 실패, 제한 시간 초과, vLLM 대기 요청 초과)를 결과에 넣는다.
- 최종 선정 fallback은 LLM을 거치지 않으므로 비고를 반영하지 않는다. `remark` 값이 있으면, 시스템은 응답에 "비고 미반영" 경고를 넣는다.
- 최종 선정 LLM을 연동하기 전(구현 순서 2단계, 병원 조회·규칙 엔진 적용·전체 흐름)에는 `pipeline.py`가 최종 선정 대신 최종 선정 fallback을 호출한다.

**완료조건**

- [ ] 최종 선정 fallback의 직선거리 정렬, 문장 틀, "비고 미반영" 경고에 대한 단위 테스트가 있다.
- [ ] LLM 호출 실패와 제한 시간 초과를 일부러 일으키면, 시스템이 최종 선정 fallback으로 응답한다.

### F-10 ETA 계산

**요구사항**

- 시스템은 최종 선정이나 최종 선정 fallback으로 고른 병원 N개에만 ETA를 구한다.
- `EtaProvider`의 운영 구현은 Tmap ETA API를 호출한다. Tmap ETA API는 에어갭 현장에서 예외적으로 호출할 수 있다.
- Tmap ETA API 호출이 실패하면, 시스템은 ETA 대신 병원정보 검색 API가 준 직선거리를 응답에 넣고 "ETA 계산 실패(직선거리 대체)" 경고를 넣는다.
- `EtaProvider`는 ETA와 함께 계산 방식 이름(Tmap ETA API, 직선거리 대체)을 반환한다. 시스템은 응답에 이 이름으로 ETA 계산 방식을 표시한다.

**완료조건**

### N-01 프롬프트 관리

**요구사항**

- 개발팀은 환자 상태 판단 프롬프트와 최종 선정 프롬프트를 같은 방식으로 관리한다. 두 프롬프트에서 같은 역할을 하는 파일은 다음과 같다.

| 역할 | 환자 상태 판단 | 최종 선정 |
|---|---|---|
| 시스템 프롬프트 | `classification/prompts/patient_assessment_v1.md` | `selection/prompts/final_selection_v1.md` |
| LLM 입력 객체 생성과 메시지 조립 | `classification/`의 환자 상태 판단 | `selection/`의 메시지 조립 |
| 출력 스키마 | `domain/`의 환자 상태 판단 결과 모델 | `selection/`의 출력 모델 |

- **개발팀은 시스템 프롬프트 파일에 고정 지시문만 적고, 요청 데이터는 코드가 JSON으로 만든다.**
    - 개발팀은 `final_selection_v1.md`에 요청마다 바뀌지 않는 지시만 적는다: 순위 원칙, 심폐정지 예외, 우회 사유 선택지, "병상 정보 오래됨" 태그가 붙은 병상 값 처리, "분만 가능" 태그 처리, `ref` 작성법.
    - 메시지 조립 코드는 LLM 입력 객체를 JSON 문자열로 바꿔 user 메시지에 넣는다. 비고가 비어 있으면 메시지 조립 코드는 비고 키를 넣지 않는다.
    - 메시지 조립 코드는 `string.Template`으로 템플릿 자리표시자(`$n`, `$output_schema`)를 채운다. `str.format`과 LangChain `ChatPromptTemplate`의 기본 형식은 중괄호를 자리표시자로 해석해서, 프롬프트 파일에 JSON 예시를 넣으면 치환 오류가 난다. 그래서 메시지 조립 코드는 이 둘을 쓰지 않는다.
    - 메시지 조립 코드는 LangChain을 import하지 않고, OpenAI chat 형식의 메시지 목록(`[{"role": "system", "content": ...}, {"role": "user", "content": ...}]`)을 반환한다. 이 형식은 vLLM `/v1/chat/completions`가 받는 형식이라, 개발팀은 감사 로그에 남긴 메시지 목록을 vLLM에 그대로 다시 보내 호출을 재현할 수 있다. LangChain `ChatOpenAI`도 이 형식의 메시지 목록을 그대로 받는다.
- **프롬프트와 출력 검증은 같은 LLM 입력 객체를 쓴다.** 프롬프트는 LLM이 추천 사유의 `ref`를 LLM 입력 객체 안의 경로로 쓰게 하고, `selection/`의 출력 검증은 그 경로가 LLM 입력 객체에 있는지 확인한다.
- **개발팀은 출력 스키마를 Pydantic 모델 하나에서만 만든다.** vLLM structured outputs는 생성되는 토큰을 스키마에 맞게 제한할 뿐, 스키마를 모델에게 보여 주지 않는다. 그래서 메시지 조립 코드는 `model_json_schema()`로 만든 스키마를 프롬프트에도 넣고, `adapters/`의 vLLM 구현은 같은 Pydantic 모델을 `with_structured_output()`에 넘긴다.
- **개발팀은 프롬프트 버전을 파일 이름으로 구분한다.** 개발팀은 프롬프트를 고칠 때 기존 파일을 덮어쓰지 않고 `final_selection_v2.md`처럼 새 파일을 만든다. `config/settings.yaml`은 시스템이 사용할 프롬프트 버전을 정한다.
    - 예외: 2026-10-22에 중증외상 기준 항목을 추가할 때 개발팀은 `patient_assessment_v1.md`를 바로 고쳤다. v1은 아직 평가셋으로 평가하지 않은 프롬프트라서 비교할 이전 버전이 없었기 때문이다. 개발팀은 이 예외를 이번 한 번만 적용한다.
- **개발팀은 프롬프트를 바꾸면 평가셋으로 결과를 확인한 뒤 배포한다.** 최종 선정 프롬프트를 바꾸면 개발팀은 지침 위반 건수, 스키마 검증 실패율, 비고 반영 정확도를 확인한다. 환자 상태 판단 프롬프트를 바꾸면 개발팀은 환자 상태 판단 정확도와 스키마 검증 실패율을 확인한다.

## 9. 용어

| 용어 | 뜻 |
|---|---|
| 단계 코드 | A0, A1, A2, B, C0, C, ML, E, F, G. [§3 시스템 구성](#3-시스템-구성)의 처리 흐름에서 단계 이름 앞에 붙은 코드 |
| L0, L1 | L0은 지침의 원칙 조건, L1은 의료지도를 받아야 적용할 수 있는 완화 조건 |
| N | 시스템이 추천하는 병원 수(기본 10) |
| M | 시스템이 최종 선정 LLM 프롬프트에 넣는 후보 병원 수(10~15) |
| X | 우회 판정 거리 기준(km, 미정) |
| 4대 중증 | 심정지, 중증외상, 뇌졸중, 심근경색. 요청의 `majorSevereType` 필드 값 |
| 적용 규칙 | 119구급대 운영지침 규칙 엔진이 입력으로 받는 환자 분류 7종: 중증외상, 경증외상, 비외상 중증, 비외상 경증, 심폐정지, 뇌졸중 의증, 뇌졸중 선별검사 양성 |
| 특수 자원 | 환자에게 필요한 병원 자원 4종: 뇌경색 재관류중재술 또는 뇌출혈수술, 심근경색 재관류중재술, 소아 응급 진료, 분만. 진료 역량 규칙 엔진은 분만을 뺀 3종을 완화하지 않는 병원 조건으로 적용하고, 분만은 "분만 가능" 태그로 표시한다 |
| 중증응급질환 코드 | 병원이 실시간으로 공개하는 "중증응급질환 수용가능 정보"(질환별로 지금 환자를 받을 수 있는지 여부)의 질환 항목. 시스템은 병원정보 검색 API 병원 상세의 `acceptanceCapabilities`가 주는 질환 항목 키(`mkioskty1`~`mkioskty27`, 예: `mkioskty1` = 심근경색 재관류)를 중증응급질환 코드로 쓴다 |
| 환자 상태 판단 | 환자 정보로 외상 여부, 필수·보조 진료과, 중증응급질환 코드, 중증외상 기준 항목을 판단하는 LLM 호출 단계(A1). 입력과 출력은 [F-03 환자 상태 판단](#f-03-환자-상태-판단)에 있다 |
| LLM 입력 객체 | 시스템이 LLM에 넣을 요청 데이터를 모은 객체. 시스템은 이 객체를 JSON 문자열로 바꿔 user 메시지에 넣는다 |
| 규칙 엔진 | [§1.1](#11-배경)의 이송병원 선정 기준 하나를 적용하는 모듈. 119구급대 운영지침, 진료 역량, ML 모델, 도착시간·거리 4개이고, 개발팀이 엔진마다 `config/`에서 켜고 끈다 |
| fallback | 일부 시스템이 동작하지 않을 때, 시스템이 그 시점에 낼 수 있는 최선의 결과를 반환하는 처리. 어떤 fallback도 활성화된 규칙 엔진의 조건을 통과한 병원만 추천한다 |
| 최종 선정 fallback | 최종 선정 LLM 출력이 검증을 통과하지 못하거나 LLM 호출이 실패하거나 제한 시간을 넘기면, 시스템이 직선거리 순으로 병원 N개를 골라 응답하는 처리 |

| 예시값 | 설계할 때 예로 적은 값. 개발팀은 값이 정해지기 전까지 이 값을 쓴다 |
| 임시값 | 예시값이 없어서 개발팀이 정해 둔 값. 개발팀은 값이 정해지거나 의료진이 확인하기 전까지 이 값을 쓴다 |
